# Dashboard

The Dashboard is a Next.js App Router/TypeScript application using Tailwind and shadcn/ui. It provides the overview and routed Finance, Tasks, Inbox, Calendar, Activity, and Status pages. It consumes generated TypeScript OpenAPI types under `src/lib/api/generated`, not hand-written transport copies. The service clients (`src/lib/api/*-client.ts`) act for the owner: every request, from the browser or the server, sends `X-Life-OS-Actor: user`, which the services require on writes. The local `/api/<service>` proxy used without the gateway passes on only `user` and `dev:<name>` actors, like the gateway.

The shell is deliberately compact: a slim header with the Life OS home link and the theme switch, a sidebar on desktop, and a seven-item bottom bar on phones that fits a 360 px screen without sideways scrolling. The current page's link carries `aria-current="page"`, and a skip link jumps to the main content.

The theme switch offers Light, Dark, and System (the default, following the device). [next-themes](https://github.com/pacocoursey/next-themes) stores the choice in `localStorage` under `theme` and sets the `dark` class on `<html>` before the first paint, so there is no flash of the wrong theme; the switch shows the selected option only after hydration, so server and browser markup agree. All colors come from the tokens in `src/app/globals.css`, defined for both themes: the shadcn/ui neutrals, `canvas` (the page area behind cards), and the status colors `success`, `warning`, `info`, and `destructive`. Use `text-warning` for status text and icons, `bg-warning-subtle border-warning/30` for a tinted status surface, and `bg-warning text-warning-foreground` for a solid fill. Raw palette classes such as `bg-red-50` or `text-amber-600` are not used: they become unreadable in dark mode.

Home (`/`) is capture-first: opening it lets the owner type or dictate immediately, without scrolling, on desktop and phone. The capture card comes first (`src/components/capture-card.tsx`): a chat-like composer (`src/components/capture-composer.tsx`, also used to edit a Human Review capture) where Enter captures and Shift+Enter adds a line (one Enter is exactly one capture; a second submit while one is in flight and Enter during IME composition are ignored), the Voice **Record** control beside the Capture button, and the text captures made on the page during this visit (by the composer or by a Human Review edit) listed under it with their live Inbox state (Received, Processing, Retry at a time, Needs review, Failed, Processed), polled until they settle. When one settles, the page loads its server data again in place (`router.refresh()`, keeping what is typed and listed), so Home's Human Review card and Task summaries, and the `/inbox` sections, include it without a reload. The composer clears and keeps focus after each capture, and is focused on load on desktop (not on touch devices). A line under it counts automatic work still in Inbox, from Inbox `GET /v1/backlog`: pending captures (`raw` or `processing`, with retries and the next scheduled retry) and failed ones, each linking to its `/inbox` section. Human Review is counted once, in its own card. When something needs the user's attention (see `/status` below), one alert linking to `/status` follows the capture card; when everything works, it shows nothing. The rest of Home is a read-only projection over the owning services' list APIs (`src/lib/home-attention.ts`) in four compact cards:

- **Human Review** — how many captures wait in `human_review` (the backlog's true count), with up to two previews, linking to `/inbox`.
- **Urgent tasks** — open Tasks that are overdue or due today (day boundaries in the owner's timezone, via the Tasks `dueBefore` filter with `includeUndated=false`), overdue first, previewing five, linking to `/tasks`.
- **Next on your calendar** — the next relevant Calendar event in the coming 30 days: the first active (not cancelled) event or occurrence of a recurring event that has not started yet. Events under way, including today's all-day events, are not "next". Imported events count too and show their source's name (for example "ZAW"). "Open Calendar" opens `/calendar` at that event's day (`/calendar?date=…`, in the owner's timezone). Home reads Calendar's list API page by page (20 events, at most 3 pages) until it finds one, since events under way are listed first.
- **Unscheduled tasks** — up to three open Tasks without a date, linking to `/tasks`. Home asks Tasks for undated Tasks only (`undated=true`), so any number of dated Tasks cannot crowd them out.

Counts carry a `+` when there are more rows than Home shows: the Tasks list returns `nextCursor` when more Tasks match than Home fetched (100), and Unscheduled also when it has more than its three previews. The Inbox list does not page, so a full page of Human Review previews (10) counts as more; that only shows when the backlog's true count is unavailable. Each card distinguishes an empty source (“Nothing waiting for review.”) from an unreachable one (“Inbox is unavailable right now.”); a stopped service never fails the whole page. Finance, full Task lists, and the Calendar agenda live only in their workspaces.

`/inbox` shows every unfinished capture exactly once, in the section for its state (`src/lib/inbox-summary.ts`). The header counts come from `GET /v1/backlog` and link to their sections; the same capture card sits below it.

`/finance` shows the current month (in the owner's timezone) from the Finance monthly summary: balance, income, expenses, net, and spending by category. **Import CSV** uploads a transaction file (see [Finance CSV import](../finance-csv-import.md)) and reports the created, skipped, and failed counts with row errors; files over 4 MB, the Finance service's request limit, are refused in the browser. Individual transactions and accounts are not listed or editable here yet. When Finance is unreachable the page says so instead of showing zeros.

- **Human Review** (`human_review`): each review offers its candidate Tasks, **Edit**, and **Discard**. A capture with no candidates, where Codex found nothing to do, can be discarded or edited. Edit turns the card into the capture composer, prefilled with the capture's text (for a voice capture, its transcript), with Record, **Cancel**, and **Capture**. Capture (or Enter) sends the edit through the normal capture path: text to Inbox `POST /v1/inbox-items` (source `manual`), or a recording to Voice, which transcribes it into a new Inbox item. Either way `sourceMetadata` carries `replacesItemId` (the original's id) next to `timeZone`; Voice passes the upload's metadata on to the item. Only once the new capture was accepted (the item created, or the recording accepted by Voice) is the original discarded with the same Inbox operation as Discard, so it leaves review and stays in Inbox history. A failed capture keeps the editor and its text; a failed discard closes the editor and leaves the card with an error, to be discarded by hand. A text edit then shows under the composer like any capture. Cancel (or Esc) sends nothing and leaves the capture in review; a recording not yet stopped is dropped. This queue and the Failed section take the page's refreshed data when a capture followed by the capture card settles.
- **Pending** (`raw` and `processing`), newest first, each marked Received, Retrying, Retry at a time (the reason, such as the Codex usage limit, is in the tooltip and the section note), or Processing.
- **Failed**: automatic processing gave up. Shows the latest attempt error; the capture can be discarded.
- **Recently processed**: up to ten recently resolved captures, latest resolution first, each linking to its workflow in the Event Log (`/activity?correlationId=…`).

Sections list up to 50 rows and say “Showing 50 of N” when more exist; empty sections are hidden, and an unreadable one says so instead of looking empty. Times use the owner's timezone.

`/calendar` is the Calendar workspace: [FullCalendar](https://fullcalendar.io/) Standard month, week, day, and list views over the Calendar API (`src/components/calendar-workspace.tsx`, helpers in `src/lib/calendar-workspace.ts`; see [Calendar](../services/calendar.md)). Calendar stays the only source of truth: FullCalendar renders the events the browser loads for the range on screen (following `nextCursor`, up to 1000). A compact header holds the title, the search box, and **New event**; below it are Today, previous and next, the period, **Show cancelled**, and the view switch. Phones (narrower than 640 px) open in the list, a 30-day agenda from the day in focus; wider screens open in the month. Once the owner moves, the view and day are kept in the URL (`/calendar?view=week&date=2026-10-14`), so a reload or bookmark returns there. FullCalendar is themed with the Dashboard's tokens in a stylesheet scoped to the calendar (`src/components/calendar-workspace.css`), so it follows the light and dark themes and fits a 360 px screen.

Clicking an event opens its details in a dialog: when (labelled with the zone; a timed event scheduled in another zone also shows its time there), location, notes, reminders ("Default reminders", "No reminders", or each one, such as "30 minutes before" or "1 day before at 19:00"), recurrence, and status. **New event**, or selecting days or a time range on the calendar, opens the event form: title, all day, start and end, an optional time zone the times are entered in (saved as the event's `timeZone` display hint), location, notes, and reminders (default, none, or up to ten, each minutes, hours, or days before the start, or N days before at HH:MM). An all-day event's last day is inclusive in the form and the API; FullCalendar's exclusive end is converted at the boundary. Changing the start moves the end with it. The form checks only what it can see (a title, filled-in dates and times, complete reminders); Calendar validates the rest, and its 400 message is shown at the field it concerns, for example "The end must be after the start." Saving uses `POST` or `PATCH` (null clears a field), Delete asks first and removes the event permanently, and Life OS events can also be dragged or resized to reschedule them (a refused change snaps back with a note). Everything is saved in Calendar, so it survives a reload.

Imported events (source `ics` or `google`) carry their source's label and are read-only: their details show, Edit and Delete are disabled with the reason, and only **Edit reminders** (a `PATCH` of `reminders` alone) is offered. Cancelled events are hidden unless **Show cancelled** is on (`includeCancelled`); they then show struck through, and a cancelled Life OS event can be restored. Recurring events show as the list API returns them and cannot be dragged; editing one edits the stored series.

The search box finds events on any date, past or future, containing every word typed in their title, notes, or location (`GET /v1/events/search`), like Google Calendar's search. It searches once typing pauses and lists the 50 most relevant matches as dated results, upcoming events soonest first and then past ones most recent first, or says nothing matched. Arrow keys and Enter, or a tap, open a result: the calendar goes to its date (and time, in week and day) and the event's details open.

Times on `/calendar` are in the browser's timezone: FullCalendar runs with `timeZone: "local"`, and the labels, the form, and the list's `timeZone` (which decides the days all-day events fall on) use the browser's zone once the page has hydrated, before that the zone the server rendered in. FullCalendar renders only after hydration, so the server HTML and the hydrated page agree.

Every "today", day, date, and time in the Dashboard is in the owner's timezone: the browser's own timezone once it has reported it, else `LIFE_OS_TIMEZONE`, else UTC. A client component in the root layout (`src/components/time-zone-sync.tsx`) stores the browser's IANA zone in the `lifeos-tz` cookie (path `/`, one year, `SameSite=Lax`). The server reads and validates the cookie on every request (`src/lib/user-time-zone.ts`), renders in that zone with the fixed `en-GB` locale, and passes the zone to client components as a prop, so the server HTML and the hydrated page always agree, whatever the browser's language. On a first visit, or after the device changed zone, the page is rendered in the previous zone; the component then stores the new zone and refreshes once. It never refreshes twice for a zone, nor when the cookie could not be stored or the server cannot use the zone. Stored data and API payloads stay UTC instants; only the display follows the browser. Text and voice captures also send the browser's zone as `sourceMetadata.timeZone`, so "tomorrow at 10" means 10:00 where the owner was (see [MCP and AI](../services/mcp.md#dates-and-the-owners-timezone)).

`/tasks` is the Tasks control workspace. Its List view groups open work into Overdue, Today, Upcoming, Unscheduled / No date, and Completed, and lists each Task once. An undated Task remains visible rather than being assigned a made-up deadline. The date picker is the stock shadcn/ui Calendar (weeks start on Monday, a dot marks days with open Tasks). It is only a Tasks control: picking another day lists that day's Tasks first, and Schedule shows the picked day's Monday-to-Sunday week of dated Tasks. Unscheduled / No date stays listed in both views. This projection does not turn Tasks into Calendar Events. On screens narrower than `lg` the picker collapses behind a button, and Task rows wrap the date and actions under the title. In wider lists the due date sits in a fixed column. A Task can be edited in place, rescheduled, returned to Unscheduled, completed, and reopened using the Tasks API; all mutations survive reload.

The page loads every open Task, following the Tasks list's `nextCursor` 100 at a time up to a safety cap of 1000; if more exist, a note above the lists says so and the No date count carries a `+`. Completed Tasks load separately, most recently completed first, until the last seven days are covered (today and the six days before, in the owner's timezone). Unscheduled / No date is always shown with its full count; it lists the five newest undated Tasks, then **Show all N** / **Show fewer**. Completed is collapsed by default, with a heading that counts the Tasks completed in the last seven days (“Completed 4 this week”). Expanded, it lists them, and **Show older** reveals older completed Tasks 20 at a time, loading further pages from the Tasks API when the loaded ones run out. This is display only: completed Tasks are never deleted. Both toggles are remembered per section in localStorage (`lifeos.tasks.undated.expanded`, `lifeos.tasks.completed.expanded`). The server always renders them collapsed and the browser applies the remembered state right after hydration, so the hydrated page matches the server HTML. Both are buttons with `aria-expanded` and `aria-controls`.

Every day on the page (today, grouping, the picker, labels, and the edit form's date and time) is in the owner's timezone. The server passes that timezone and today's date to the client component, keyed by the zone, so the refresh into the browser's zone starts the workspace over on the new today. Labels use fixed English text, so the hydrated page matches the server HTML in any browser language. A due time at local midnight, or a UTC midnight on the same day, is shown as a date without a time.

`/activity` is the Event Log, a read-only view over the Activity API (`src/lib/activity-log.ts`; see [Activity](../services/activity.md)). It lists events newest first with human-readable labels, outcome, time, domain, and actor. The owner is "You", the Life OS AI is named (for example "Inbox processor (Codex)"), and development tools such as Claude Code, Playwright, or `tools/` scripts appear as "Developer tool (<name>)" with an outline badge, so test and maintenance work is never mistaken for the owner's. Times are shown in the owner's timezone with its abbreviation, for example `9 Oct 2026, 23:21:30 CEST`. Filters are plain URL parameters set from a form, so any filtered view can be bookmarked or shared: domain (`source`), entity (`subjectType`), event type, status (`outcome`), and a date range (`fromDate`/`toDate`, both inclusive, as calendar days in the owner's timezone). "Older events" pages with the API's cursor. The filters wrap into two columns on a phone.

The **Calendar** domain (`source=calendar`) holds Calendar event changes, labelled with the event's title ("Event created: Dentist", "Event rescheduled: Dentist", also updated, cancelled, restored, and deleted) and attributed to whoever made them ("You" in the Dashboard, the agent through MCP, "Developer tool (…)"), and one entry per refresh of a subscribed feed that says what it changed ("Source refreshed: ZAW — 3 added, 1 cancelled", "— no changes", "— unchanged", or "Source refresh failed: ZAW"), attributed to the feed as "Calendar feed (zaw)". A selected Calendar entry links to the Calendar: **Open in Calendar** goes to the event's day (not for a deleted event), **Open Calendar** for a feed refresh.

The log starts when the Activity service was deployed; nothing earlier was backfilled. The **Agent changes** domain (`source=mcp`) holds only the changes the AI made through MCP mutation tools: Task create, update, complete, and reopen, Calendar create, and Finance manual transactions. The agent's reads and searches are not recorded. Its decisions, such as Human Review requests, and its processing attempts are Inbox events attributed to "Inbox processor (Codex)". When the domain is selected, the list explains this. If it is empty, the list says the agent hasn't changed anything in the range and links to Inbox activity for the same range. The Activity API has no actor filter, so "everything the agent did" is not a single view: use Agent changes plus Inbox. Opening an entry (`?event=<id>`) loads its whole workflow (same `correlationId`) and its subject's history, then shows:

- **What led here**: the causation chain back to the start of the workflow.
- **What it led to**: everything caused by it, directly or indirectly.
- **Same <entity> in other workflows**: for example, the user completing a Task that the agent created earlier.
- **Whole workflow**: the causation tree, with the selected entry highlighted.
- **Diagnostics**: a collapsed section with ids, correlation, causation, actor, timestamps, and the raw event data. **Copy diagnostics** copies the event data JSON exactly as shown and announces "Copied"; over plain http, where the Clipboard API is unavailable, it falls back to a hidden-textarea copy, and if that fails too it selects the JSON for copying by hand.

Every entry in these sections opens its own trace, so a chain such as Inbox capture → processing → MCP `task_create` → Task created → Task later completed can be followed click by click. A workflow and a subject history are each read as up to 500 events. If an event's cause was recorded in another workflow, the Event Log links to it instead of guessing. The Event Log never writes; like the gateway, its `/api/activity` proxy allows only GET/HEAD.

Services shorten long text in summaries with "…" (for example a retry's Codex error) and keep a longer copy in the event data (`errorSummary`, `reason`, `content`, …). The selected entry shows the short summary with a **Show more** toggle that expands it in place to the longer text, and **Show less** collapses it again; list rows stay short. On desktop the selected entry sticks below the header and never grows past the bottom of the screen, so a tall entry scrolls on its own without moving the list; on a phone it follows the list in the normal page flow.

`/status` answers "is Life OS working, and if not, what do I do?" It is built only from supported runtime state (`src/lib/runtime-status.ts`), never from UI behaviour. Five checks are shown, each as OK, Needs attention, or Problem, with the runtime's own error text and a suggested action:

- **Automatic processing**: the processor's private `/status` endpoint (see [MCP and AI](../services/mcp.md)). It reports when the processor is not running, when it cannot read Inbox through MCP, when Codex is signed out (from `codex login status` or a 401), when Codex has hit its usage limit (Codex's own "try again at …" text is shown verbatim, plus the reset time Codex reports for the exhausted bucket), and when Codex runs are failing for any other reason. It also shows the Codex run in progress, counts of completed, failed, timed-out, cancelled, and crash-recovered runs, the Codex plan, and each usage bucket's used percentage and reset time, exactly as the Codex CLI reports them, or "unavailable".
- **Inbox backlog**: Inbox `GET /v1/backlog`. Shows captures that failed and are being retried, with the latest error and the next scheduled retry and its reason, for example "after the Codex usage limit resets". It reports captures that automatic processing gave up on (`failed`) as a problem, and flags a capture that has waited more than 15 minutes.
- **Voice transcription**: Voice `GET /v1/backlog`. Reports Whisper not ready, a stalled Voice worker, and recordings waiting for a retry, with the next scheduled retry time.
- **Calendar sources**: Calendar `GET /v1/sources`. One entry per subscribed feed with its last refresh (outcome, time, and what it changed), last success, failures in a row, the error of a failed refresh, and the next refresh (or "disabled"); never the feed URL, which can be personal. A failed refresh is shown at once but retried automatically, so the check stays OK; a feed that has failed 3 refreshes in a row (`SOURCE_FAILURE_ALERT`) makes the check Needs attention and so raises the Home alert. Unreadable sources are a problem; no feeds is OK.
- **Services**: every owning service's `/ready`.

Times on Status are shown in the owner's timezone with its abbreviation (for example "9 Oct 2026, 20:22 CEST"). Automatic processing also lists the planning timezone: each capture's browser timezone, else the processor's `LIFE_OS_TIMEZONE`. Viewing Status from a browser in another zone is expected; only a processor configured with a different `LIFE_OS_TIMEZONE` than the Dashboard is pointed out. Each probe has a 2.5 s timeout. An unreachable source shows as a problem rather than failing the page. The Dashboard reaches the processor at `PROCESSOR_STATUS_URL` (`http://processor:8081` in Compose) on the private network; the processor is never exposed through the gateway. `make runtime-status-smoke` stops Whisper, the processor, MCP, Tasks, and the Voice worker, and signs Codex out inside the processor container, one at a time on the disposable verification stack. It then checks in the browser that Status and the Home alert explain each problem and that Status recovers. It also adds a calendar feed whose host does not exist and checks that it reaches Home only after three failed refreshes.

The browser tests for Calendar feeds (`e2e/calendar-feed.ts`) use a feed host that never resolves for failures. Feeds that import need the verification overlay `tools/fixtures/calendar-ics.compose.yaml`, which serves the files the tests write to `LIFE_OS_E2E_ICS_DIR` at `http://ics-fixture/` and sets `CALENDAR_ICS_ALLOW_PRIVATE_URLS=true` for that stack's Calendar only; without `LIFE_OS_E2E_ICS_DIR` those tests are skipped:

```sh
export LIFE_OS_E2E_ICS_DIR=$(mktemp -d) LIFE_OS_VERIFY_OVERLAYS=tools/fixtures/calendar-ics.compose.yaml
./tools/verify-compose up --detach --no-build
LIFE_OS_E2E_URL=http://127.0.0.1:13001 npm --prefix apps/dashboard run test:e2e -- e2e/activity-log.spec.ts e2e/home-attention.spec.ts e2e/runtime-status.spec.ts
./tools/verify-compose down --volumes --remove-orphans
```

Browser requests use `/api/finance`, `/api/tasks`, `/api/inbox`, `/api/calendar`, `/api/voice`, and `/api/activity` relative to the current origin. Server-side rendering uses Docker service DNS internally. Loading/error handling is page-scoped so an unavailable service does not require exposing direct service ports.

The Voice control in the capture card uses the browser `MediaRecorder` API. Stopping a recording uploads it to the asynchronous Voice job API (only Stop sends it: leaving the control mid-recording, for example by navigating away or cancelling a Human Review edit, drops the recording) and keeps the returned job ID in component state; it never waits for Whisper. “Accepted” means the audio has been durably queued, not that it was transcribed. The generated Voice client polls the persisted job and shows queued, processing, automatic-retry, succeeded, failed, or expired status; polling stops on terminal states and component cleanup clears the timer. Failed/expired uploads offer a re-record or re-send flow. A successful job means transcription completed and has been handed to Inbox; `/inbox` is the place to see later AI processing. Run `make dashboard-check` for format/lint/test/type/build and `make life-smoke` for browser-facing behavior.
