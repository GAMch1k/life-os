# Dashboard

The Dashboard is a Next.js App Router/TypeScript application using Tailwind and shadcn/ui. It provides the overview and routed Finance, Tasks, Inbox, Calendar, Food, Activity, Status, and Notifications pages. It consumes generated TypeScript OpenAPI types under `src/lib/api/generated`, not hand-written transport copies. The service clients (`src/lib/api/*-client.ts`) act for the owner: every request, from the browser or the server, sends `X-Life-OS-Actor: user`, which the services require on writes. The local `/api/<service>` proxy used without the gateway passes on only `user` and `dev:<name>` actors, like the gateway.

The shell is deliberately compact: a slim header with the Life OS home link, the notification bell, and the theme switch, a sidebar on desktop, and an eight-item bottom bar on phones that fits a 360 px screen without sideways scrolling, every label in full. The current page's link carries `aria-current="page"`, and a skip link jumps to the main content.

The theme switch offers Light, Dark, and System (the default, following the device). [next-themes](https://github.com/pacocoursey/next-themes) stores the choice in `localStorage` under `theme` and sets the `dark` class on `<html>` before the first paint, so there is no flash of the wrong theme; the switch shows the selected option only after hydration, so server and browser markup agree. All colors come from the tokens in `src/app/globals.css`, defined for both themes: the shadcn/ui neutrals, `canvas` (the page area behind cards), and the status colors `success`, `warning`, `info`, and `destructive`. Use `text-warning` for status text and icons, `bg-warning-subtle border-warning/30` for a tinted status surface, and `bg-warning text-warning-foreground` for a solid fill. Raw palette classes such as `bg-red-50` or `text-amber-600` are not used: they become unreadable in dark mode.

UI controls are [shadcn/ui](https://ui.shadcn.com/docs/components) components in its Base UI flavour (`components.json`: style `base-nova`, lucide icons), and they come only from the shadcn CLI. Before building any control, check the component list (pick the Base UI variant) and add what it offers from `apps/dashboard` with `npx shadcn add <name>` (for example `npx shadcn add popover`), then format the new files with the repo's Prettier. `src/components/ui/` holds exactly what the CLI writes and is never edited by hand: `npx shadcn add <name> --diff` must report no changes beyond Prettier's formatting. Life OS's own styling and behaviour live in wrapper components next to it, such as `src/components/app-dialog.tsx` (the dialog's page background, screen-height cap with inner scrolling, and wider default; dialogs import from it) and `src/components/date-picker.tsx`. If a component would need an npm package the Dashboard does not have yet, or would overwrite an existing file, stop and decide that explicitly rather than letting the CLI do it. The installed set is button, badge, calendar, card, checkbox, dialog, field (with label and separator), input, native-select, popover, progress, radio-group, skeleton, table, tabs, textarea, and toggle-group (with toggle). Form selects are `NativeSelect`, a styled native `<select>` that keeps the phone's own picker and plain form posts; checkboxes are `Checkbox`, choices such as Ends never / on / after are `RadioGroup`, toggle buttons (the calendar and Tasks view switches, the theme switch, Repeat on weekdays) are `ToggleGroup`, labels, legends, descriptions, and field errors are `Field` parts, and status chips are `Badge`.

Every date field is the shadcn date picker (`DatePicker` in `src/components/date-picker.tsx`), composed as [shadcn's Base UI Date Picker](https://ui.shadcn.com/docs/components/base/date-picker) shows: an outline button showing the day in the browser's own format ("Wed, 21 Oct 2026" in en-GB, "Wed, Oct 21, 2026" in en-US), opening a `Popover` with the month `Calendar` (weeks start on Monday as on the Tasks page, month and year dropdowns reaching 100 years either side of today, today marked in the owner's zone). Picking a day closes it; the grid takes arrow keys and Escape closes it, and its days are larger on a phone. Its accessible name is the field's label followed by the day ("Start date, Wed, 21 Oct 2026"), and the button carries the day in `data-value`. It holds plain `YYYY-MM-DD` days, never instants, so forms send exactly what the native date inputs sent; `min` and `max` disable days outside a range (an event's end and a series' Ends on date cannot come before its start), `required` keeps a day chosen (otherwise picking the chosen day again clears it), and `name` posts the day with a plain form, as the Event Log filters do. shadcn has no time picker: times use `TimeInput`, the time `Input` from shadcn's date and time example with the browser's clock indicator hidden (phones still open their time wheel); values stay `HH:mm`. The browser suite picks days through `e2e/date-picker.ts` (`pickDate` chooses the year and month in the dropdowns, then the day) and finds checkboxes by role, since a Base UI checkbox is a labelled `span` beside a hidden input.

Home (`/`) is capture-first: opening it lets the owner type or dictate immediately, without scrolling, on desktop and phone. The capture card comes first (`src/components/capture-card.tsx`): a chat-like composer (`src/components/capture-composer.tsx`, also used to edit a Human Review capture) where Enter captures and Shift+Enter adds a line (one Enter is exactly one capture; a second submit while one is in flight and Enter during IME composition are ignored), the Voice **Record** control beside the Capture button, and the text captures made on the page during this visit (by the composer or by a Human Review edit) listed under it with their live Inbox state (Received, Processing, Retry at a time, Needs review, Failed, Processed), polled until they settle. When one settles, the page loads its server data again in place (`router.refresh()`, keeping what is typed and listed), so Home's Human Review card and Task summaries, and the `/inbox` sections, include it without a reload. The composer clears and keeps focus after each capture, and is focused on load on desktop (not on touch devices). A line under it counts automatic work still in Inbox, from Inbox `GET /v1/backlog`: pending captures (`raw` or `processing`, with retries and the next scheduled retry) and failed ones, each linking to its `/inbox` section. Human Review is counted once, in its own card. When something needs the user's attention (see `/status` below), one alert linking to `/status` follows the capture card; when everything works, it shows nothing. The rest of Home is a read-only projection over the owning services' list APIs (`src/lib/home-attention.ts`) in compact cards:

- **Human Review** — how many captures wait in `human_review` (the backlog's true count), with up to two previews, linking to `/inbox`.
- **Urgent tasks** — open Tasks that are overdue or due today (day boundaries in the owner's timezone, via the Tasks `dueBefore` filter with `includeUndated=false`), overdue first, previewing five, linking to `/tasks`.
- **Next on your calendar** — the next relevant Calendar event in the coming 30 days: the first active (not cancelled) event or occurrence of a recurring event that has not started yet. Events under way, including today's all-day events, are not "next". Imported events count too and show their source's name (for example "ZAW"). "Open Calendar" opens `/calendar` at that event's day (`/calendar?date=…`, in the owner's timezone). Home reads Calendar's list API page by page (20 events, at most 3 pages) until it finds one, since events under way are listed first.
- **Unscheduled tasks** — up to three open Tasks without a date, linking to `/tasks`. Home asks Tasks for undated Tasks only (`undated=true`), so any number of dated Tasks cannot crowd them out.
- **Over budget** — only when a category of this month's budget spent more than planned: how many, each with how far over, linking to `/finance?tab=budget`.
- **Low balance** — only when a bank account is below the low-balance alert (`lowBalance` from Finance `GET /v1/accounts`; Finance never marks Cash or other manual accounts): how many, each with its balance, linking to `/finance`.
- **Renewing soon** — only when confirmed subscriptions renew within the renewal reminders' lead days (Finance `GET /v1/subscriptions?state=confirmed`, `renewal: upcoming`): up to three, soonest first, each with its amount and "today", "tomorrow", or "in 3 days", linking to `/finance?tab=subscriptions`.
- **Food** — only when there is something to say: how many items are on the shopping list (Food `GET /v1/shopping-items?state=needed`, "200+" past the first 200), linking to `/food`, and up to three in-stock items that expire today or tomorrow in the owner's timezone (Food `GET /v1/pantry-items?state=in_stock&expiringWithinDays=2`, one day more than needed since Food counts days in its own zone), each such as "Milch · Expires today" linking to `/food?tab=pantry`, and today's planned meals in one line, "Today: Porridge (breakfast) · Pasta Bolognese (dinner)" (Food `GET /v1/meal-plan` for today in the owner's timezone), linking to `/food?tab=plan`, and what is running low, "Running low: Milch, Brot and 2 more" (one name per normalised name, Food `GET /v1/pantry-items?state=in_stock&runningLow=true`), linking to `/food?tab=pantry`. Food that already expired is left to the pantry. Nothing is shown when Food cannot be read.
- **<Month> budget** (`src/components/home-budget.tsx`) — this month's spending against the plan (booked and pending, from Finance `GET /v1/budgets/{month}` in the owner's timezone) as a progress bar, the days left, the three categories closest to their amount with their percentage, and uncategorized spending; "No budget for October yet." with **Plan your month** when there is no plan.

Counts carry a `+` when there are more rows than Home shows: the Tasks list returns `nextCursor` when more Tasks match than Home fetched (100), and Unscheduled also when it has more than its three previews. The Inbox list does not page, so a full page of Human Review previews (10) counts as more; that only shows when the backlog's true count is unavailable. Each card distinguishes an empty source (“Nothing waiting for review.”) from an unreachable one (“Inbox is unavailable right now.”, “Finance is unavailable right now.”); a stopped service never fails the whole page. Accounts and transactions, full Task lists, and the Calendar agenda live only in their workspaces.

`/inbox` shows every unfinished capture exactly once, in the section for its state (`src/lib/inbox-summary.ts`). The header counts come from `GET /v1/backlog` and link to their sections; the same capture card sits below it.

`/finance` is the Finance workspace (`src/components/finance-workspace.tsx`, logic in `src/lib/finance-workspace.ts`, `finance-money.ts`, `finance-summary.ts`, `finance-budget.ts`, and `finance-subscriptions.ts`). The server renders the first view (accounts, categories and rules, the latest 50 transactions, the current month's summary, the budget, the subscriptions, and the alert settings, in the owner's timezone); after that every change is read back from Finance in the browser, so balances, the list, the summary, the budget, and the subscriptions stay in step. The tab is kept in the URL (`/finance?tab=summary`, `/finance?tab=budget&month=2026-09`, `/finance?tab=subscriptions`), so a reload, a bookmark, or a budget or renewal notification opens it. When Finance is unreachable the page says so instead of showing zeros; a part that fails (the summary, categories) says so in its own place.

- **Accounts**: a card per account with its balance (opening balance plus booked transactions) and, when there are any, its pending total, the built-in **Cash** account first; a **Low balance** badge while a bank account is below the low-balance alert (never Cash or other manual accounts). A card's main part shows only that account's transactions (pressed again, all); **Edit** changes the name, kind, currency (only while the account has no transactions), and opening balance, and archives or restores the account. Archived accounts leave the list (**Archived (n)** shows them) and take no new transactions; Cash can be renamed but not archived. **Add account** creates one (a bank account by default, in Cash's currency).
- **Transactions** tab: every transaction, latest booking date first, in a table (date, counterparty and description, category, account, amount; on a phone the category and account move under the description). Search looks for every word in the counterparty, description, and notes; filters for account, category (including **Uncategorized**), date range (From/To date pickers), direction (money in or out), status (booked or pending), and source (entered here, CSV import, bank) combine with it, and **Clear filters** resets them. **Show more** loads the next 50. Amounts are in the account's currency in the browser's format, money in with a "+" in green; badges mark **Pending** transactions and imported ones (**CSV**; **Bank** once the bank connection exists). Opening a manual transaction edits every field or deletes it (after a confirmation); an imported one shows its details read-only, says why, and changes only its category and notes. Money out offers **This is a subscription** (`src/components/finance-subscription-action.tsx`): pick **Repeats** and **Add subscription**, and it says "Added “Netflix” to your subscriptions (monthly)."; a transaction that already belongs to one says "Part of the subscription “Netflix” (monthly)." (or that Finance suggests it).
- **Add transaction**: Money out/Money in, amount (either decimal mark: 12.50 or 12,50), account (Cash by default, or the account the list is filtered to), date (today), a Pending checkbox, counterparty, description, category (empty lets the rules choose), and notes. Each dialog sends one `Idempotency-Key`, so a retried request cannot add the transaction twice (the local `/api/finance` proxy passes the header on).
- **Summary** tab: a month (previous/next, **This month**) in one currency (a picker appears when accounts use several): balance now, income, spending, and net, then every category with booked transactions in the month as a bar, largest spending first, uncategorized included; transfers are listed but not counted. A category's name opens its transactions of that month.
- **Budget** tab (`src/components/finance-budget.tsx`): a month (previous/next, **This month**) with its plan and progress, live during the month: **Spent** against the planned total (with a progress bar), **Left** (or **Over plan**) with the days left, **Income** against the expected income, and **Saved** against the savings goal; then each planned category with "€260.00 of €300.00", a progress bar (the primary color, the warning color from 80%, red and an **Over budget** badge above 100%), what is left or over, the percentage, and the pending part; expense categories with spending but no amount under **Not in the plan**; and **Uncategorized** spending as its own line, so nothing hides. A category's name opens its transactions of the month (booked and pending, as the budget counts them). Notes say where the plan comes from ("The regular plan, since October 2026." or "December 2026 has its own plan; the regular plan is unchanged."), how much of the expected income is not planned, what was moved to Savings and left over, that spending counts booked and pending money out in the budget currency (refunds lower it; transfers, Savings, and income are not spending), and how many transactions in other currencies are not counted. **Plan <month>** or **Edit plan** opens the editor (`src/components/finance-budget-editor.tsx`): expected income and savings goal (with the medians of the last months as hints), an amount per active expense category (empty leaves it out) with "Suggested €320.00 (median of 3 months)" or "No history yet" under each, **Use suggestions** to fill them in (a first plan starts from them), a live line "Planned €2,100.00 · Savings €400.00 · €500.00 not planned", and **Save for**: **Only <month>** (the default once a plan exists) or **<month> and later months** (the default for the first plan; later months with their own plan follow it too). A month with its own plan offers **Use the regular plan**. See [Finance](../services/finance.md#monthly-budgets).
- **Subscriptions** tab (`src/components/finance-subscriptions.tsx`): **Subscriptions per month** (the monthly equivalent of the confirmed ones, "2 confirmed subscriptions", and how many in other currencies are not counted); **Suggested**, the recurring payments Finance found, each with how often, its category, "Next expected Thu 15 Oct", "3 payments, last on Tue 15 Sep" (a yearly one seen twice is marked **Less sure**), "€13.99 / month" (and "≈ €7.83 a month" for other cadences), **Confirm**, and **Ignore**; **Confirmed**, next payment first, with "Next on Sun 1 Nov", "Renews in 3 days" (badge **Soon**), or "Expected Tue 13 Oct, not seen yet"; **Missed** (more than a week late, badge **Missed**, with a note to ignore a cancelled one or edit a new price); and **Ignored (n)**, folded, where one can be confirmed again. **Edit** opens a dialog (`src/components/finance-subscription-dialog.tsx`) for the name, **Repeats** (weekly, monthly, every 3 months, yearly), amount, and category, and **Delete subscription** (it may be suggested again; ignoring keeps it away). The tab reads the list again when it is opened and after every money change, since detection runs in the background. Without subscriptions it explains how they are found and points to **This is a subscription**.
- **Alerts** (header button, `src/components/finance-alerts-dialog.tsx`): **Large debits** from an amount (transfers between own accounts are left out), **Low balance** below an amount (bank accounts only), and **Renewal reminders** some days before (0–30), each with a checkbox to switch it on or off, amounts in the default currency; **Save alerts** stores them and re-reads accounts and subscriptions. See [Finance](../services/finance.md#alerts).
- **Categories & rules** tab: categories by kind (expense, income, transfer) with an optional color, added, renamed, archived, and restored; rules ("Counterparty contains “REWE” → Groceries", by counterparty, description, or either, *contains* or *is exactly*, case-insensitive, with an optional priority) added, edited, and deleted. Rules categorize new transactions by themselves; **Apply rules** runs them on existing ones without a category (or also re-checks the categories rules chose) and reports how many it categorized, recategorized, cleared, and left unchanged. A category chosen by hand is never changed by a rule. A card payment no rule matches can get a default category from its merchant category code; the transaction dialog says so ("Chosen from the card's merchant category code."). Finance adds default categories and German merchant rules once; rules added without a priority come before them.
- **Import CSV**: a dialog with an account picker (the first bank account by default) and a file chooser; nothing is imported until **Import into <account>**. It reports the imported, duplicate (already in the account, skipped), failed, and rule-categorized counts with row errors (see [Finance CSV import](../finance-csv-import.md) for the columns). Files over 4 MB, the Finance service's request limit, are refused in the browser. A Deutsche Bank CSV export may need its columns renamed until the bank connection arrives.

The **Bank connection** card (`src/components/bank-connections.tsx`, `BankConnections`, with its logic in `src/lib/banking.ts`; for the Finance page, given the page's timezone) talks to the [banking integration](../services/banking.md) through `/api/integrations/banking`. Not set up, it names the missing `LIFE_OS_ENABLE_BANKING_*` settings. Not connected, **Connect Deutsche Bank** asks banking for the bank's consent page and opens it. The bank returns to `/finance/bank/callback` (`src/app/finance/bank/callback/page.tsx`, `src/components/bank-callback.tsx`), which drops the code from the address bar, posts the code and state to banking as the owner (connecting runs the first, 90-day sync), and goes on to `/finance?bank=connected`, where the card says "Deutsche Bank is connected." once; a refused or reused consent is explained with **Back to Finance**. When the bank returned an error instead of a code, the callback also posts the state, the error, and its description (never a code) to banking (`POST /v1/connections/consent-failure`), which keeps it; while no bank is connected or a reconnect is due, the card shows the newest one next to Connect or Reconnect ("Last attempt failed on 10 Oct, 20:19 CEST: server_error — Internal error") until a connection succeeds. Connected, the card lists the accounts with their masked IBANs ("Das Junge Konto (DE89…3000)"), the last sync ("Synced 10 Oct, 12:05 CEST · 3 new transactions", or the error of a failing sync and the last success), the next sync, and how long the access lasts ("Access valid until 8 Apr 2027", "Access ends in 3 days"); **Sync now** (disabled for 10 minutes after one, saying when it is available again), **Disconnect** (asks first: access ends at the bank, the accounts are archived in Finance with their history), and **Reconnect** when the access expires soon (badge **Expires soon**), has expired, or needs the owner. Session ids and full account numbers never reach the browser. The browser test `e2e/bank-connection.spec.ts` stubs the banking API in the page.

- **Human Review** (`human_review`): each review offers its candidate Tasks, **Edit**, and **Discard**. A capture with no candidates, where Codex found nothing to do, can be discarded or edited. Edit turns the card into the capture composer, prefilled with the capture's text (for a voice capture, its transcript), with Record, **Cancel**, and **Capture**. Capture (or Enter) sends the edit through the normal capture path: text to Inbox `POST /v1/inbox-items` (source `manual`), or a recording to Voice, which transcribes it into a new Inbox item. Either way `sourceMetadata` carries `replacesItemId` (the original's id) next to `timeZone`; Voice passes the upload's metadata on to the item. Only once the new capture was accepted (the item created, or the recording accepted by Voice) is the original discarded with the same Inbox operation as Discard, so it leaves review and stays in Inbox history. A failed capture keeps the editor and its text; a failed discard closes the editor and leaves the card with an error, to be discarded by hand. A text edit then shows under the composer like any capture. Cancel (or Esc) sends nothing and leaves the capture in review; a recording not yet stopped is dropped. This queue and the Failed section take the page's refreshed data when a capture followed by the capture card settles.
- **Pending** (`raw` and `processing`), newest first, each marked Received, Retrying, Retry at a time (the reason, such as the Codex usage limit, is in the tooltip and the section note), or Processing.
- **Failed**: automatic processing gave up. Shows the latest attempt error; the capture can be discarded.
- **Recently processed**: up to ten recently resolved captures, latest resolution first, each linking to its workflow in the Event Log (`/activity?correlationId=…`).

Sections list up to 50 rows and say “Showing 50 of N” when more exist; empty sections are hidden, and an unreadable one says so instead of looking empty. Times use the owner's timezone.

`/calendar` is the Calendar workspace: [FullCalendar](https://fullcalendar.io/) Standard month, week, day, and list views over the Calendar API (`src/components/calendar-workspace.tsx`, helpers in `src/lib/calendar-workspace.ts`; see [Calendar](../services/calendar.md)). Calendar stays the only source of truth: FullCalendar renders the events the browser loads for the range on screen (following `nextCursor`, up to 1000). A compact header holds the title, the search box, and **New event**; below it are Today, previous and next, the period, **Reminder defaults**, **Show cancelled**, and the view switch. Phones (narrower than 640 px) open in the list, a 30-day agenda from the day in focus; wider screens open in the month. Once the owner moves, the view and day are kept in the URL (`/calendar?view=week&date=2026-10-14`), so a reload or bookmark returns there. FullCalendar is themed with the Dashboard's tokens in a stylesheet scoped to the calendar (`src/components/calendar-workspace.css`), so it follows the light and dark themes and fits a 360 px screen.

Clicking an event opens its details in a dialog: when (labelled with the zone; a timed event scheduled in another zone also shows its time there), location, notes, reminders, recurrence, priority, and status. A **High priority** badge (warning tint) or a subtle **Low priority** badge sits beside the title; medium, the usual, shows none. On the calendar a high-priority event's title starts with a bold "!" in the event's own colour (announced as "High priority" where browsers support CSS alternative text); low and medium look as before. The reminders are every one that applies (`effectiveReminders`), one per line in Calendar's order, such as "30 minutes before" or "1 day before at 19:00"; those that come from the defaults say so ("1 day before at 19:00 · ZAW default" for an event imported from ZAW, "· default" for a Life OS event), and an event without any says "No reminders". **New event**, or selecting days or a time range on the calendar, opens the event form: title, all day, start and end, an optional time zone the times are entered in (saved as the event's `timeZone` display hint), Repeat, location, notes, **Priority** (a select: Low, Medium, High; a new event starts at Medium, and the note says "How important its reminders are."), and reminders. Reminders work like Google Calendar's notifications: **Use default reminders** (on for a new event) adds the defaults, which the form names, such as "30 minutes before (your default for timed events)" (the owner's timed or all-day defaults, following the All day box, read from `GET /v1/settings` when the form opens) or "1 day before at 19:00 (ZAW)"; when there are none it says to set them in Reminder defaults. Under **Your reminders** the event adds its own, up to ten, each minutes, hours, or days before the start, or N days before at HH:MM (**Add reminder**; an all-day event's new reminder starts as the evening before), and every one of them applies, together with the defaults. An all-day event's last day is inclusive in the form and the API; FullCalendar's exclusive end is converted at the boundary. Changing the start moves the end with it. The form checks only what it can see (a title, filled-in dates and times, complete reminders); Calendar validates the rest, and its 400 message is shown at the field it concerns, for example "The end must be after the start." Saving uses `POST` (own `reminders` only when there are some, `useDefaultReminders`, and `priority` unless it is Medium) or `PATCH` (null clears a field; `reminders`, `useDefaultReminders`, and `priority` only when they changed), Delete asks first and removes the event permanently, and Life OS events can also be dragged or resized to reschedule them (a refused change snaps back with a note). Everything is saved in Calendar, so it survives a reload.

Whether an event can be edited follows Calendar's `editable` (`isEditable` in `src/lib/calendar-workspace.ts`): Life OS events and Google events of calendars the owner may edit are edited, dragged, resized, and deleted like Life OS events (a Google event's change is saved at once and the google-calendar integration writes it to Google within seconds; a delete confirmation says "also in Google Calendar" when the event is in Google), and a recurring Google event takes the same scopes. An event in Google says where in its details: a Google calendar's event "In Google: Owner" with "Synced both ways" ("Synced from Google" when read-only), from its source (`source.integration` `google-calendar`); a Life OS event "In Google: Life OS" with "Exported", "Waiting to be exported", or in red "Export failed: … Retrying automatically.", read from the integration's `GET /v1/exports?eventId=` when the details open (`googleSyncLabel`). Imported events carry their source's badge: an integration's event (`source.kind` `external`, such as a feed of calendar-feeds) reads "<provider> · <name>" ("ZAW · Müllabfuhr" once the owner renamed the ZAW source, just "ZAW" while its name is the provider's), a Google event the same way ("Google · Owner"); its origin label is the source's name, else its provider, and a read-only one says "Imported from <label>, so it can only be changed there" unless Calendar gives its own `readOnlyReason`. Read-only events (feed events, Google calendars the owner can only read, occurrences of Google rules Calendar cannot hold) show Calendar's `readOnlyReason`: Edit and Delete are disabled with the reason, and only **Edit reminders and priority** (the Priority select and the same reminder controls, with the source's defaults; a `PATCH` of `reminders`, `useDefaultReminders`, and `priority` alone, only what changed) is offered. Its Priority note names the source's default, such as "ZAW events are high priority unless you choose another."; choosing that default makes the event follow the source's default again. Cancelled events are hidden unless **Show cancelled** is on (`includeCancelled`); they then show struck through, and a cancelled Life OS event can be restored.

Recurring events are created and changed only here, in the Dashboard, and work like Google Calendar's (`src/lib/calendar-recurrence.ts` for the rules, the scopes in `src/lib/calendar-workspace.ts`; see the Calendar API's recurrence and occurrence endpoints). **Repeat** in the event form offers Does not repeat, Daily, "Weekly on Thursday", "Every weekday (Monday to Friday)" (only for a start on a weekday), "Monthly on day 17", "Annually on September 17" (a birthday), and **Custom…**; the labels follow the start date. Custom repeats every N days, weeks, months, or years; weekly on chosen days (toggle buttons; the start's weekday is always on, disabled, with a note why); and ends **Never**, **On** a date (the end of that day in the event's zone, sent as `until`), or **After** N occurrences (`count`), with the rule spelled out below. The details say how an event repeats in plain words ("Weekly on Monday and Wednesday", "Every weekday", "Annually on September 17", "Every 2 weeks on Tuesday, until 31 Dec 2026", "Monthly on day 15, 10 times"), read from the occurrence's original start; an occurrence shows its own date and time, and one changed on its own says "Changed for this event". Calendar's 400 messages about the rule are shown at Repeat.

Saving an edit of an occurrence, dragging or resizing one (editable recurring events can be dragged), and deleting one ask which occurrences it applies to in a small dialog, **Edit recurring event** or **Delete recurring event**: **This event**, **This and following events**, or **All events**; Cancel keeps the form open or snaps a drag back. The form shows the occurrence's own values and sends only what changed (a priority change like any other field, in every scope). This event `PATCH`es the occurrence (`/v1/events/{id}/occurrences/{recurrenceId}`) and returns to its details; a change of Repeat, All day, or the time zone belongs to the series, so This event is not offered for it and the dialog says why. This and following splits the series there (`POST …/split`, on its first occurrence Calendar changes the whole series): a new time is the new series' start, and unless Repeat changed it repeats like the old one. All events `PATCH`es the series: a new time moves every occurrence by the occurrence's offset on the series' wall clock (dragging Wednesday 18:00 to Thursday 19:00 moves the series' start a day and an hour; weekly days move with it, Monday and Wednesday becoming Tuesday and Thursday). Deleting This event skips the occurrence (`status: cancelled`): it is kept as history, shown struck through with Show cancelled, and **Restore this event** brings it back (`status: active`). This and following ends the series before it (`POST …/truncate`), and All events deletes the series. After This and following or All events the dialog closes and the calendar reloads. Events that do not repeat behave as before.

`/status` answers "is Life OS working, and if not, what do I do?" It is built only from supported runtime state (`src/lib/runtime-status.ts`), never from UI behaviour. Shows captures that failed and are being retried, with the latest error and the next scheduled retry and its reason, for example "after the Codex usage limit resets". It reports captures that automatic processing gave up on (`failed`) as a problem, and flags a capture that has waited more than 15 minutes.
- **Voice transcription**: Voice `GET /v1/backlog`. Reports Whisper not ready, a stalled Voice worker, and recordings waiting for a retry, with the next scheduled retry time.
- **Calendar sources**: the calendar-feeds integration's `GET /v1/feeds` (each feed's refresh state), with each feed's current name and enabled from Calendar's `GET /v1/sources` (the owner's, in Calendar; the feed's own copies when Calendar cannot be read). One entry per subscribed feed with its last refresh (outcome, time, and what it changed), last success, failures in a row, the error of a failed refresh, and the next refresh (or "disabled"); never the feed URL, which can be personal. A failed refresh is shown at once but retried automatically, so the check stays OK; a feed that has failed 3 refreshes in a row (`SOURCE_FAILURE_ALERT`) makes the check Needs attention and so raises the Home alert. Unreadable feeds (calendar-feeds down) are a problem; no feeds is OK. **Services** also probes calendar-feeds' `/ready` ("Calendar feeds") and google-calendar's ("Google Calendar"), so the monitor notifies when either stops. With Google set up, a **Google Calendar** part follows the feeds (the google-calendar integration's `GET /v1/connection` and `GET /v1/calendars`): connected (account, when, permissions not granted, the calendars that sync, the last sync, the export of Life OS events to the Life OS calendar — "up to date in “Life OS”", "3 waiting for “Life OS”", "2 failing, retried automatically", or "off" —, the Life OS calendar's note, such as that it was created again, and "Edits to Google": "up to date", "2 on the way", or "1 failing, retried automatically") or not connected is OK; failing edits and change-feed trouble ("Calendar's changes could not be read, so Life OS events and edits made here wait to reach Google") are shown but stay OK, as do failing exports, shown ("… could not be exported to Google yet; retried automatically") but stay OK; a failed sync is shown but retried automatically, so it stays OK, while a calendar that has failed 3 syncs in a row (`GOOGLE_SYNC_ALERT`) is Needs attention with Google's error; expired, revoked, or refused access is Needs attention with "Reconnect Google in Calendar.", and so is a connection the server can no longer use because its Google settings are gone. An **Event reminders** part comes last (Calendar's `GET /v1/reminders/status`, see [Calendar](../services/calendar.md#reminder-delivery)), with the last check, the last reminder sent, and the check interval. It is OK while the last check and the last successful one are both within three check intervals and a minute (`senderStaleAfterMs`: 150 s at the default 30 s), saying "Sending normally." or "Running; nothing sent yet.". An older check is Needs attention ("Event reminders are not being sent: the last check ran at …", or "no check has run yet"), and so are a failed last check ("Event reminders may be late: the last check failed.", with Calendar's error) and checks that run but no longer succeed ("… the last successful check ran at …"); each adds the last success and makes the Calendar check Needs attention, so the monitor tells the owner, with "Check the calendar service logs (docker compose logs calendar). Reminders due meanwhile are sent when it catches up, up to 2 hours late; older ones are recorded in Activity as missed." (the grace window Calendar reports). Without Calendar's `NOTIFICATIONS_SERVICE_URL` the part is Not set up; when the health cannot be read, the part is left out, as Services already names Calendar.
- **Notifications**: Notifications `GET /v1/channels` (see [Notifications](../services/notifications.md#channel-health)). With no delivery channel configured it is Not set up: notifications are listed in Life OS only. Otherwise one part per channel, such as **ntfy (phone)**, with its last delivery, last failure, failures in the last 24 hours, and deliveries waiting for a retry. A channel whose latest delivery failed is Needs attention, with the channel's error (for example ntfy's `401 unauthorized`), and raises the Home alert until a delivery succeeds again. Unreadable channels are Needs attention. After the channels comes a **Task reminders** part (Tasks' `GET /v1/notifications/status`, see [Tasks](../services/tasks.md#notifications)): Tasks' reminders before timed Tasks and its morning summary and daily lists. It follows the same rules as Event reminders ("Task reminders are not being sent: …", with "Check the tasks service logs (docker compose logs tasks). Reminders and daily lists due meanwhile are sent when it catches up, …"), and also lists the schedule ("summary 08:00, morning list 09:00, evening list 19:00 (Europe/Berlin)", in Tasks' `LIFE_OS_TIMEZONE`), how long before a timed Task its reminder goes out, and, when Tasks has no `CALENDAR_SERVICE_URL`, that the summary lists no events. Its warning makes the Notifications check Needs attention even while no delivery channel is set up; left out when Tasks cannot be read. Last comes a **Food reminders** part (Food's `GET /v1/notifications/status`, see [Food](../services/food.md#expiry-reminders)): the daily expiry reminder, with the same rules ("Sending normally.", "Running; nothing sent yet.", "Food reminders are not being sent: …", with "Check the food service logs (docker compose logs food). Expiry reminders due meanwhile are sent when it catches up, …") and its time ("Expiry reminder: daily at 08:00 (Europe/Berlin)"); left out when Food cannot be read.
- **Bank connection**: Banking `GET /v1/connections` (see [Banking](../services/banking.md)). Not set up, or set up with no bank connected, is Not set up; an incomplete setup (a missing or unreadable Enable Banking setting, named without its value) is Needs attention. One part per live connection with its accounts (masked IBANs), last sync, next sync, and access end. An expired or refused consent and three failed syncs in a row (`BANK_FAILURE_ALERT`) are Needs attention, with "Reconnect the bank in Finance" or, for failing syncs, that transactions from the last good sync are kept and retried, so the monitor tells the owner of an ended consent. A consent that ends within 7 days is shown ("Deutsche Bank access ends on …") but stays OK, because banking's own 7-day and 1-day reminders already tell the owner; a single failed sync is shown but stays OK too. Unreadable connections are Needs attention.
- **Backups**: the backup service's `GET /v1/status` (see [Backup](../services/backup.md) and the [backups runbook](../operations/backups.md)), on the private network (`BACKUP_SERVICE_URL`, `http://backup:8080` in Compose). OK while the last successful backup of every database is less than 26 hours old (`BACKUP_RECENT_MS`) and the last restore check passed or none has been owed yet. Needs attention when the last run after it failed or was interrupted (the summary names the databases, and the action is the backup service's own advice, such as "lifeos_backup cannot connect to food_db: run make db-provision-backup", so the monitor's notification says what to do), when every database was dumped but the Inbox capture images could not be read ("The last backup of the Inbox images failed.", with the service's advice, such as setting `LIFE_OS_INBOX_MEDIA_GID`, as the action), when that backup is 26 to 50 hours old, when less than 5 GB is free where the backups are kept (`BACKUP_MIN_FREE_BYTES`), or when no restore check has run for 8 days (`RESTORE_CHECK_DUE_MS`; counted from when backups began until the first one, never while checks are `off`). A Problem when the last backup is more than 50 hours old (`BACKUP_STALE_MS`), when the last restore check failed (each database's differences are shown), or when the status cannot be read although the service answers `/ready`. When the backup service is down, Services already names it, so the Backups card is left out rather than alerting twice. Before the first backup it is Not set up and says when the first one runs; a first backup that failed Needs attention. Several issues: the worst leads and the others are listed under Also. Its facts are the last backup (in the page's timezone, and how long ago), the databases it holds (and any registry database it does not have yet), the total size, the Inbox capture images kept (files and size, and how many the last backup could not copy), the next backup, the last restore check, the retention, and the free disk, with the backup or restore check in progress. **Back up now** (`src/components/backup-now.tsx`) starts a backup of every database as the owner through the Dashboard's `/api/backups/` route (which passes on only `GET v1/status` and `POST v1/backups`; the backup service has no gateway route), shows its progress and result, and refreshes the page; while a backup or restore check is already running (409) it follows that one.
- **Server**: [host-health](../services/host-health.md)'s `GET /v1/status` and `GET /v1/history` on the private network (`HOST_HEALTH_SERVICE_URL`, `http://host-health:8080` in Compose): the server's memory, load, disks, and every container on it. host-health applies the thresholds (configurable in `.env`) and lists its findings, problems first; the check takes the first as its state, summary, and action, and lists the others under Also. Needs attention: memory available below 15% for 3 minutes, a disk with less than 10 GiB or 10% free, a 15-minute load above the CPUs, a container that died 3 times in 15 minutes or is unhealthy for 5, or container facts that cannot be read. A Problem: memory available below 7%, or a disk with less than 3 GiB free. The summary names the cause ("Memory is very low: 520 MiB available of 7.7 GiB. Biggest: lifeos-whisper-1 1.9 GiB, homeassistant 600 MiB, n8n 420 MiB.") and the action helps ("Stop heavy jobs (on this server, one at a time); docker stats shows which containers use the most."). Sizes are in GiB and MiB, as `free -h` and `df -h` show them. Its facts are memory, load (1, 5, and 15 minutes, on how many CPUs), each disk, the containers (running, unhealthy, restarting, in all), the three biggest memory users, and how long the server has been up; on the verification stack, "Source: a made-up server". A sparkline (`src/components/sparkline.tsx`, inline SVG: a 2px line over a faint wash in `--chart-2`, a hairline at the warning level, a dot at now) draws memory available over the last 24 hours, each of its 96 points the lowest of its quarter hour. Its caption says the lowest and the current value, so nothing depends on hovering; the pointer and the arrow keys move a crosshair with each point's value and time. When host-health is down, Services already names it, so the Server card is left out; when it answers `/ready` but its status cannot be read, the card is a Problem.
- **Services**: every owning service's `/ready` (Banking, Backup, Host health, and Recipe import included), and the monitor's (`MONITOR_SERVICE_URL`, `http://monitor:8080` in Compose), so a stopped monitor, which means no status notifications, shows here.

`GET /api/status` (`src/app/api/status/route.ts`) returns the same checks as JSON, evaluated on every request and never cached. The [monitor](../services/monitor.md) polls it and notifies the owner when a check breaks or recovers, so the rules above are the only ones.

From 768 px wide the cards form two columns packed tightly instead of in rows as tall as their tallest card (`src/components/masonry-grid.tsx`, with the math in `src/lib/masonry.ts`): in the checks' order, each card goes under the column that is shorter at that moment (the left one on a tie), so a short card such as Inbox backlog beside the long Automatic processing has the next card right under it instead of empty space. Only each column's last card stretches, so both columns end on the same line; every other card keeps its natural height. Nothing is dragged or reordered: the cards keep the checks' order in the page, so screen readers and Tab follow it, and reading top to bottom, left to right gives the same order. The grid uses 1 px rows without a row gap (taller rows only past 5,000 px, as Firefox ignores grid lines past 10,000), and each card gets its column and a row span as tall as it is (the 1rem gap is left as empty rows). The server renders a plain two-column grid with cards at their natural height, so the only movement is the cards below the first row moving up once as the page hydrates; the packing applies before the hydrated page is painted, again on every window resize (also across the breakpoint) in the same frame, and in the next frame whenever a card's size changes for another reason, such as new content. Phones keep one column in order.

Times on Status are shown in the owner's timezone with its abbreviation (for example "9 Oct 2026, 20:22 CEST"). Automatic processing also lists the planning timezone: each capture's browser timezone, else the processor's `LIFE_OS_TIMEZONE`. Viewing Status from a browser in another zone is expected; only a processor configured with a different `LIFE_OS_TIMEZONE` than the Dashboard is pointed out. Each probe has a 2.5 s timeout. An unreachable source shows as a problem rather than failing the page. The Dashboard reaches the processor at `PROCESSOR_STATUS_URL` (`http://processor:8081` in Compose) on the private network; the processor is never exposed through the gateway. `make runtime-status-smoke` stops Whisper, the processor, MCP, Tasks, and the Voice worker, and signs Codex out inside the processor container, one at a time on the disposable verification stack. It then checks in the browser that Status and the Home alert explain each problem and that Status recovers. It also adds a calendar feed whose host does not exist and checks that it reaches Home only after three failed refreshes.

Notifications (the Notifications API, `services/notifications/api/openapi.yaml`; presentation in `src/lib/notifications.ts`) reach the Dashboard in two places. The **bell** in the header, next to the theme switch (`src/components/notification-bell.tsx`), shows a small dot, never a number, while anything is unread; the dot is tinted red when an unread notification has high importance. Its accessible name is "Notifications" or "Notifications, N unread". It reads `GET /v1/notifications/unread-count` when the page loads, when the window regains focus or the tab becomes visible again, after any read action (in the popover or on `/notifications`; the two tell each other through a `lifeos:notifications-changed` window event), and once a minute while the tab is visible; there is no faster polling. When Notifications cannot be reached the bell shows no dot and no error. Clicking it opens a popover (shadcn/ui Popover) with the six latest notifications, newest first: an importance marker, the title (bold while unread), a two-line body preview, the source and importance, and how long ago in the owner's timezone ("Just now", "5 min ago", "3 h ago", "Yesterday, 21:30", then the date). Clicking a notification marks it read and, when it has a `link` (always a Life OS path), opens that page; **Mark all read** in the header marks everything up to the newest one shown, so one that arrives meanwhile stays unread. The empty state reads "No notifications yet."; at the bottom **All notifications**, styled like Home's "Review in Inbox", leads to `/notifications`. The bell is the way into notifications on every page and screen size, so the navigation stays at eight items and the phone bar keeps fitting 360 px.

`/notifications` lists every notification newest first, grouped by the day (in the owner's timezone) Notifications received it: an importance badge (High, Medium, Low), the title, the full body, the time (and when it happened, if that differs), source and category, **Open** for a link, and the state of each delivery channel: "ntfy: sent 14:05", "ntfy: retrying after 2 attempts, next try 14:10" or "ntfy: failed after 5 attempts" with the latest error, or "Shown in Life OS only" while no channel is configured. Unread notifications are tinted and marked "Unread", with **Mark read** each; **Mark all read** in the page header marks everything received up to when the page was loaded (whatever the filters). Filters are URL parameters set from a form: importance, source, and **Unread only** (`unread=true`). The server reads the first 50; **Show more** follows the API's cursor in the browser. **Try notifications** sends a test notification of the chosen importance (`category: test.manual`, a unique `dedupeKey`, title "Test notification (medium)", source `dashboard` from the owner's actor, linking back to `/notifications`) through the same path as every other notification, so the owner can check it end to end. The Event Log names `notification.created`, `notification.delivered`, and `notification.delivery_failed` with the notification's title and channel under a Notifications domain. Per-category settings (turning a category off or overriding its importance) are not built yet: the Notifications API has no endpoints for them.

Browser requests use `/api/finance`, `/api/tasks`, `/api/inbox`, `/api/calendar`, `/api/food`, `/api/voice`, `/api/activity`, `/api/notifications`, `/api/integrations/banking`, and `/api/integrations/recipe-import` relative to the current origin. **Photos with a capture.** The capture composer (Home, `/inbox`, and a Human Review edit) has **Add photos** (the gallery and files; on Android also offering the camera) and, on touch screens, **Take a photo** (`capture="environment"`, straight to the camera). The Voice control in the capture card uses the browser `MediaRecorder` API. ## Install on your phone

The Dashboard installs as an app on the owner's Android phone: its own home screen icon, opening full screen without Chrome's address bar, and listed in the phone's share sheet (see [Share to Life OS](#share-to-life-os)).

How to install it, in Chrome on Android:

1. Open `https://lifeos.gamch1k.com` and log in (the Cloudflare Access email code).
2. Open Chrome's menu (⋮) and tap **Install app**. On some phones it reads **Add to Home screen**; then choose **Install** (not "Create shortcut", which neither opens full screen nor appears in the share sheet).
3. Confirm. The Life OS icon (a light ring around a dot on black) appears on the home screen and in the app drawer.

Install it from the public hostname: Chrome offers installation only over https (or on localhost), so the WireGuard address `http://10.66.66.1:3001` cannot install it. `/share/about` repeats these steps on the phone.

What makes it installable:

- **Manifest.** `/app.webmanifest` (`src/lib/web-app.ts`, served by `src/app/app.webmanifest/route.ts`): name and short name "Life OS", `start_url` and `scope` `/`, `display: standalone`, the theme's page colour (`#ffffff`) as theme and splash background, a 192 and a 512 px icon and a maskable version of each, and the share target. It is a route handler rather than `app/manifest.ts`, because the link Next renders for that file cannot carry `crossorigin="use-credentials"`: the root layout links the manifest itself with it. Browsers fetch a manifest without cookies unless asked, and Cloudflare Access would answer a cookieless request with its login page, so the manifest would not load. The layout also sets the status bar colour per theme (`#ffffff` light, `#0a0a0a` dark).
- **Icons.** `public/icons/icon-{192,512}.png` (rounded square) and `icon-maskable-{192,512}.png` (full bleed, the mark within the safe circle). `node scripts/generate-icons.mjs` draws them without any package (the shapes sampled 4×4 per pixel, the PNG written with `node:zlib`); run it from `apps/dashboard` after changing the design and commit the PNGs.
- **Service worker.** `public/sw.js`, registered on every page by `src/components/service-worker.tsx` (scope `/`, `updateViaCache: "none"`, served with `Cache-Control: no-cache` so a new version reaches the app at its next start). It only installs and takes control: it has no fetch handler and no cache, so every page, API response, and photo goes to the network exactly as without it and nothing private is stored on the phone. Life OS does not work offline.

**Cloudflare Access.** The manifest, the icons, and the service worker are ordinary same-origin paths under `lifeos.gamch1k.com`, behind Access like everything else (no Access bypass, no special gateway location, no `Service-Worker-Allowed` header: the worker sits at the root). Installed while logged in, Chrome fetches them with the Access cookie. When the 24-hour Access session has expired, the app opens on the Access login: enter the email code once and Life OS opens. A share made while the session had expired is lost, since Access sends the share sheet's POST to its login and returns to `/share` without it; the app then shows `/share/about`, which says so (share it again).

## Share to Life OS

With the app installed, **Life OS** appears in the share sheet of any app: Instagram, Chrome, a notes app, the gallery. The manifest's `share_target` posts what is shared to `/share` (POST, `multipart/form-data`, fields `title`, `text`, `url`, and the photos in `images`), and `src/app/share/route.ts` saves it as an ordinary Inbox capture, which the AI processes like anything typed on Home:

- **Content.** The title, text, and URL, one per line and each once (`shareContent` in `src/lib/share.ts`): Chrome sends the page title and its address, Instagram only text with the link in it, so a part already in the text is left out and the link always stays in the capture text. A share of photos alone reads "Photo" or "3 photos". Nothing shared (all fields empty, no photo) saves nothing.
- **Photos.** The manifest's `files` param (field `images`, `image/*`): photos shared from the gallery, the camera, or any app. Up to five, each at most 10 MB, no HEIC (checked first, then by Inbox); they go to Inbox's `POST /v1/media` in one request on the private network, and the capture names them in `mediaReferences`. A share with a photo Life OS cannot keep saves nothing, not even its text (the AI would read the text without what it refers to), and `/share/saved` says why and to share a JPEG or fewer photos. The gateway lets `/share` carry 60 MB (`location = /share`, five photos of 10 MB with room), draining an over-limit upload like Voice's so the 413 arrives intact.
- **Capture.** `POST /v1/inbox-items` as the owner (`X-Life-OS-Actor: user`), source `web`, `sourceMetadata` `{shared: true, via: "share-target"}` plus the browser's timezone from the `lifeos-tz` cookie when it is known, so "tomorrow" in a shared text is the owner's tomorrow.
- **Confirmation.** The route answers 303 to `/share/saved?item=<id>`: **Saved to Inbox** with the capture and its state, **Open Inbox**, and **Follow it in the Event Log** (the capture's workflow). When nothing was saved it goes to `/share/saved?error=<code>` with the reason: nothing shared, an unreadable request, or Inbox unavailable (share it again). Opening `/share` itself (GET) shows `/share/about`.
- **Same origin.** The Dashboard has no CSRF tokens, and a share cannot carry one. `/share` instead accepts a POST only from the app itself (`isShareFromApp`): the share sheet's post is a navigation of the installed app to its own origin, so `Sec-Fetch-Site` is `none` or `same-origin` and `Origin` is the app's own host (the port is not compared; the gateway does not pass it on) or `null`. A form on another site (`cross-site`), on a sibling subdomain (`same-site`, such as `ntfy.gamch1k.com`), or with a foreign `Origin` gets 403 and nothing is saved, even if the browser would send the Access cookie with it.

`src/lib/share.test.ts` and `src/lib/web-app.test.ts` cover the capture text, the metadata, the origin rule, the error codes (also for refused photos), and the manifest; `e2e/share-target.spec.ts` checks that the manifest, its icons, and the worker are served (the manifest linked with credentials, the worker registered), posts a share the way the share sheet does and finds the capture and Saved to Inbox, and is refused from another site.
