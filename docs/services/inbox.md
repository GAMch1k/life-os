# Inbox service

Inbox is the capture queue in `inbox_db`. It stores user content, source (`manual`, `web`, `voice`, `watch`, or `email`), metadata/media references, and a lifecycle: `raw` → `processing` → `resolved` or `discarded`, with `human_review` for decisions the user must make and `failed` when automatic processing gave up. It intentionally does not decide whether a capture becomes a task, event, or transaction. Processing attempts are kept separately with a per-item idempotency key, agent/model identity, attempted actions, timestamps, and retryable/failed/processed outcome; raw content is never consumed or overwritten.

An ambiguous or low-confidence Task mutation becomes `human_review`, rather than an automatic retry. The Inbox item retains the original capture, proposed action, reason, and candidate Tasks in `processingMetadata`; it is excluded from the processor's raw-item poll. The Dashboard Human Review queue calls `POST /v1/inbox-items/{itemId}/human-review/resolve` with one retained candidate ID. Inbox verifies that selection, stores an approved action, returns the item to `raw`, and the processor resumes it through MCP and the owning Tasks API. The item resolves only after that mutation succeeds. Every review item can also be discarded from the queue (`POST /v1/inbox-items/{itemId}/discard`). That is the way out for a capture Codex found nothing to do with, which goes to Human Review with no candidates. `retryable` remains reserved for temporary technical failures; `failed` means recovery is exhausted or operator intervention is needed. `make human-review-smoke` proves the automatic ambiguous-capture → Human Review → selected Task → persisted completion → resolved Inbox chain in disposable Compose resources.

`GET /v1/backlog` summarizes unfinished work for status surfaces, from durable Inbox state only:
- pending captures (`raw` or `processing`);
- captures that already failed at least once and are being retried, with the latest failure text and time;
- the Human Review count;
- the creation time of the oldest pending capture.

The Dashboard Status page uses it to show retries and prolonged backlogs.

Inbox records `inbox.*` activity events for capture, processing attempts (started, completed, retry scheduled, failed), Human Review (requested, resolved), resolution or discard, and a notification it could not send. They are recorded under the item's workflow correlation. A caller such as the Voice worker may supply `X-Correlation-ID`, and Inbox stores it in `inbox_items.correlation_id` (migration `000006`). Otherwise the item id is the correlation. Either way it is returned as `InboxItem.correlationId`. See [Activity](activity.md).

The current dashboard captures and resolves/discards items. The automatic MCP/Codex processor reads raw items only through MCP, preserves an audit trail, handles ambiguity safely, and calls core APIs through MCP tools. Its processing lifecycle is `raw → processing → resolved`. The outcome of an attempt decides what happens next:

- **`retryable`** (a temporary technical failure) returns the item to `raw` with a durable retry schedule. `inbox_items.next_retry_at` says when it may be retried (immediately when absent), and `retry_reason` says why, for example `usage_limited` or `backoff`. The attempt keeps its own `next_retry_at`.
- **`failed`** (automatic recovery is unlikely) moves the item to `failed`. It is no longer picked up automatically but stays visible as unresolved.
- **`human_review`** (a decision for the user) never enters technical retry.

Each attempt also carries its agent runtime: `runtimeState` (`spawning`, `running`, `completed`, `failed`, `timed_out`, `cancelled`), `runtimeOwner` (the processor instance), `runtimeSessionId` (the Codex session), and `runtimeHeartbeatAt`. The processor records these with `PUT .../processing-attempts/{attemptId}/runtime`; a finished attempt answers 409. `GET /v1/stale-processing-attempts?staleAfterSeconds=N` lists unfinished attempts whose heartbeat stopped, for captures still `raw` or `processing`, so a later processor can reconcile them after a crash. `GET /v1/inbox-items?state=raw&due=true` lists only items with no schedule or whose time has come. It is the processor's only work source, so a schedule survives restarts of both the processor and Inbox. Any other state change clears the schedule. The backlog reports the next scheduled retry with its reason, and the number of failed items. Each retry creates a distinct audit attempt key (`<operation>.retry.<n>`), preserving the original attempt and avoiding the former uniqueness collision; a processed attempt for the same deterministic operation prevents later duplicates. Invalid requests return 400 and missing items 404; readiness is at `/ready`. Test with `make db-test SERVICE=inbox` and `make e2e-smoke`.

## Capture images

Inbox owns the photos attached to captures: shared to Life OS from the phone, or attached in the Dashboard's capture composer. The processor hands them to Codex with the capture's text (see [MCP and AI → Images](mcp.md#images)): photos of letters become Tasks with their deadline, appointments Calendar events, cash receipts cash spending, and card receipts and unclear documents go to Human Review (see [Letters and receipts](mcp.md#letters-and-receipts)). The image references are part of a capture's processing key, so two photo captures with the same placeholder text ("Photo") never share action keys.

- **Upload.** `POST /v1/media` (multipart, field `images`, one to five files; a write, so it needs `X-Life-OS-Actor`) stores each image and returns, in order, its `reference` (`inbox-media:<sha256>`), `sha256`, `contentType`, and `byteSize`. Images are JPEG, PNG, or WebP, recognized from their bytes (the declared type and file name are not trusted, as for Voice's audio); each is at most `INBOX_MEDIA_MAX_BYTES` (`LIFE_OS_INBOX_MEDIA_MAX_BYTES`, 10 MiB). Every image is checked before any is stored, so a refused upload stores nothing. Refusals: 400 `images_required`, `too_many_images` (more than five), `unsupported_image`, `heic_not_supported` (HEIC/HEIF photos, as iPhones and some Android cameras save them: converting them would need a heavy image library, so the owner is asked to share a JPEG instead), and 413 `image_too_large`. The request body limit leaves room for five images at the limit.
- **Storage.** One file per image on the `inbox-media` volume (`INBOX_MEDIA_DIR`, `/var/lib/lifeos/inbox-media`), named by the SHA-256 of its bytes and written aside, then renamed, so a reader never sees half a file. The same photo uploaded again returns the same reference and is stored once. Migration `000009` adds `inbox_media` (hash, content type, size, last upload time).
- **Captures.** `mediaReferences` on `POST /v1/inbox-items` names a capture's images: at most five, each a reference `POST /v1/media` returned (400 `invalid_media_reference` for anything else, `unknown_media` for an image Inbox does not have, `too_many_images`). A repeated reference is kept once; a capture without images has an empty list (never `null`). Its `inbox.item.captured` event counts them (`data.images`).
- **Reading.** `GET /v1/media/{sha256}` serves the bytes with their content type, `Cache-Control: private, max-age=31536000, immutable` (the address is the content, so it never changes), `X-Content-Type-Options: nosniff`, and a sandboxing CSP. Through the gateway it is `/api/inbox/v1/media/…`, behind Cloudflare Access like the rest of Life OS; it is never public. The Dashboard shows the thumbnails from there, and the processor reads them on the private network.
- **Retention.** An image is kept as long as a capture refers to it, and captures are never deleted (discarding keeps them), so a capture's photos stay with it. An upload no capture refers to (a share or a composer capture that failed after its photos were stored) is removed a day after its last upload, by a pass every hour inside Inbox, together with any file left without its row. The nightly backups keep the images too: each run copies the ones `inbox_db`'s snapshot names into a shared store and lists them, and `tools/restore-media` puts them back (see [Backup: capture images](backup.md#capture-images)).

`internal/media` has unit tests (recognizing JPEG, PNG, WebP, HEIC, HEIF, AVIF, and other files; references; storing once by hash; limits), and `internal/api` integration tests against `INBOX_TEST_DATABASE_URL`: three formats stored once and served with their headers, the upload limits and refusals leaving nothing behind, captures naming only uploaded images, pruning orphans and stray files while keeping referenced and fresh ones, and migration 000009 down and up.

## Notifications

Inbox tells the owner when a capture needs them, through the Notifications service (`pkg/notify`, as `system:inbox`; see [Notifications](notifications.md#producers)). Inbox owns these state changes, so the processor, Voice captures, retries, and a new review round are all covered by the same two sends:

| When | Category | Title | Link | Dedupe key |
| --- | --- | --- | --- | --- |
| `POST .../human-review` moves an item to `human_review` | `inbox.human_review` | Needs your review | `/inbox#human-review` | `inbox.human_review:<itemId>:<attemptId>` |
| An attempt is recorded `failed`, so the item is `failed` | `inbox.failed` | A capture failed | `/inbox#failed` | `inbox.failed:<itemId>:<attemptId>` |

- Both are `medium`. The body is the capture on one line, shortened to 200 characters, with the reason (`errorSummary`) on the next line. `occurredAt` is the item's state change.
- The dedupe key names the attempt. A repeated request (the processor retrying a call) notifies once; another review round, after the owner's decision or a retry, has a new attempt and notifies again. An edited capture is a new item.
- A `retryable` outcome, a processed attempt, a resolution, and a discard notify nothing.
- The notification carries the item's correlation id, and its causation is the Inbox event (`inbox.human_review.requested` or `inbox.processing.failed`), so the Event Log shows it in the capture's workflow.
- Sending is best effort and never affects the Inbox operation. It starts after the change is stored, on a background goroutine, and Inbox answers without waiting: the processor allows each outcome write 10 s, and the synchronous Activity emission can already take most of that. `pkg/notify` bounds a send to 5 s with brief retries. A send that still fails is logged (`inbox notification not sent`) and recorded as an `inbox.notification.failed` activity event with the error. On shutdown Inbox lets sends in flight finish.
- Configuration: `NOTIFICATIONS_SERVICE_URL` (compose: `http://notifications:8080`). Empty disables notifications.
- Tests: unit tests against a fake Notifications service (payloads, trace headers, a failed or slow send, no URL), and handler tests against the Postgres in `INBOX_TEST_DATABASE_URL` (Human Review once per round, failure for good only, Notifications down or slow, no URL).
