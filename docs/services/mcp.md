# MCP and AI

The Go MCP service is available behind `/api/mcp/mcp` using streamable HTTP, with `/api/mcp/health` and `/api/mcp/ready` probes. Its typed read tools call Finance (monthly summary, accounts, categories, transaction search, the AI's category candidates, the AI's budget plans and a month's planning data), Tasks list/search/get, Inbox list and recent captures, Calendar list/search/get (Tasks and events with their times on the owner's clock, see [Task and event details and moves](#task-and-event-details-and-moves)), and Food (the shopping list, the pantry, the staples, recipes, the meal plan, the cooking preferences, suggestions, and recipe ideas) through the services' HTTP APIs, and saves recipe links through the recipe-import integration. It also provides narrowly scoped mutation tools used by Inbox processing: `task_create`, `task_update`, `task_complete`, `task_reopen`, `calendar_create`, `calendar_update`, `calendar_cancel`, `calendar_delete`, `finance_create_manual_transaction`, `finance_set_ai_categories`, `finance_request_budget_plan`, `finance_claim_budget_plan`, `finance_set_budget_plan_result`, `finance_fail_budget_plan`, `food_add_shopping_items`, `food_update_shopping_item`, `food_mark_bought`, `food_add_pantry_items`, `food_update_pantry_item`, `food_plan_meal`, `food_clear_meal`, `food_add_missing_ingredients`, `food_create_idea`, `food_mark_running_low`, `food_add_staple`, `food_remove_staple`, `recipe_import`, `inbox_start_processing_attempt`, `inbox_record_processing_attempt`, and `inbox_resolve`. It never owns or queries Finance, Tasks, Inbox, Calendar, or Food tables directly; upstream failures become understandable MCP tool errors.

Codex is told that a `taskQuery` is matched as a case-insensitive substring of Task titles and notes, so it proposes the shortest distinctive word from the title ("chicken", "Anna"). A statement that something was done, such as "I called the dentist", is a `task_complete` for the Task it refers to. Groceries stated as bought, such as "I already bought the chicken", are a `food_mark_bought`, which completes the matching open Task when nothing on the shopping list matches (see [Food](#food)). Codex does not need to know the existing Tasks, because identity is resolved here.

The owner writes Tasks in English, Russian, and German, so a Task's title may be in another language or word form than the capture: "I already bought the chicken" has to find "Купить курицу на ужин". Codex therefore adds `taskQueryAlternatives`, up to six more terms for the same thing: translations into the other two languages and distinctive word stems that also match inflected forms (`"chicken"` plus `["куриц", "Hähnchen", "Huhn"]`). It omits them when the capture quotes the exact title.

For an existing Task mutation, the processor sends each term to `task_search` and unions the matching Tasks by id. It searches open Tasks for `task_complete` and `task_update`, and completed Tasks for `task_reopen`, so a finished Task with the same name never makes a capture ambiguous. It proceeds only when the union is exactly one Task:
- no Task: Human Review with no candidates;
- several Tasks, for example "Buy chicken wings" and "Купить курицу для супа": Human Review listing them (at most ten), and nothing changes;
- a plan with only a `taskQuery` is searched with that term alone, as before.

There is no fuzzy scoring: a Task is a candidate only if one of the terms literally occurs in its title or notes. Alternatives shorter than three characters are ignored, and duplicates (case-insensitive) are searched once. The resolved UUID is passed only to the owning Tasks API operation; the search terms never reach it. That includes a Human Review approval, which still carries the alternatives.

`make cross-language-smoke` proves this with the real Codex CLI and whisper.cpp on the verification stack:
- EN "I already bought the chicken." completes "Купить курицу на ужин";
- DE "Ich habe die Milch schon gekauft." completes "Buy milk";
- RU "Я уже вынес мусор." completes "Take out the trash", while unrelated Tasks in each language stay open;
- the spoken English sentence completes "Hähnchen fürs Abendessen kaufen" through Voice, although the completed Russian chicken Task still matches the words;
- with "Купить курицу для супа" and "Buy chicken wings" both open, the same sentence goes to Human Review with exactly those two candidates, and neither changes;
- no Task is created.

The non-interactive processor uses the existing local Codex CLI/ChatGPT login, not an API key. Compose starts it as the `processor` service during normal Life OS startup; it polls the raw Inbox at `LIFE_OS_PROCESSOR_POLL_MILLIS` (default one second), starts once immediately after boot, and exposes private `/health` and `/ready` on port 8081. `SIGTERM` stops polling and shuts that server down gracefully. The one-shot command remains a diagnostic only.

The deployed worker image contains `codex` but contains no authentication. Set `LIFE_OS_CODEX_HOME_HOST_PATH` to the host's existing authenticated Codex directory (normally `~/.codex`) and `LIFE_OS_CODEX_RUNTIME_UID` to its owner (`id -u`) in the ignored `.env`. At start, the service runs as that unprivileged UID, bind-mounts the directory read-only, and copies only `auth.json` plus optional `config.toml` into its own `/tmp` tmpfs. The source session, image, Git repository, and named Docker volumes never receive a copied credential. The worker runs with a read-only root filesystem, no Linux capabilities, and `no-new-privileges`. Check the same runtime context with `docker compose exec processor codex login status`; it must report the existing ChatGPT login before the worker can become operational.

`make processor-smoke` is the acceptance smoke for the actual deployed chain: gateway/Dashboard-style capture → persisted Inbox item → automatic processor polling → authenticated local Codex CLI → MCP `task_create` → Tasks persistence → processed audit record → Inbox resolution. It uses only the isolated `lifeos-verify-*` resources and never manually invokes the processor.

The processor reads raw items through `inbox_list`, asks Codex for a constrained JSON plan, accepts only high-confidence Task, Calendar, and Food actions and strictly validated manual finance transactions, records each attempt through MCP, and resolves an item only after every action succeeds. A planned finance action records cash the owner spent or received ("spent 12 euros at the bakery" is `{"amount": {"amount": -1200, "currency": "EUR"}, "counterparty": "Bäckerei"}`): it needs a non-zero whole number of cents and a currency, may name `counterparty`, `description`, `note`, and an ISO `occurredOn` (only for another day than the capture's), and leaves out `accountId`, so Finance records it in the built-in Cash account (see [Finance](#finance)). Card and bank payments are not recorded from captures, because the bank connection brings them in; the plan prompt sends such items to Human Review. An existing event is changed only when exactly one matches, and an AI-proposed cancellation always waits for the owner's approval (see [Calendar events](#calendar-events)); the processor never deletes an event. Ambiguous, low-confidence, and nothing-to-do plans go to Human Review and are never retried automatically. Technical failures are retried on a durable schedule (see [Retry scheduling](#retry-scheduling)). A retryable operation receives a distinct persisted attempt key while retaining its deterministic base operation key, so prior attempt history remains visible and the Inbox uniqueness constraint cannot block a subsequent retry. A processed base operation is skipped. `go run ./cmd/processor --dry-run` returns proposed MCP actions without creating attempts, mutating core services, or resolving Inbox items. `go run ./cmd/processor --content '...'` is a separate non-mutating diagnostic that prints only Codex's proposed JSON plan.

Each MCP call from the processor carries the Inbox item's `X-Correlation-ID`, the processing attempt's `inbox.processing.started` event as `X-Causation-ID`, and `X-Life-OS-Actor: agent:codex-inbox-processor`. MCP forwards these headers to the owning service. Every mutation tool records `mcp.action.requested` and then `mcp.action.completed` or `mcp.action.failed`, and the owning service's change names the request event as its cause. A caller that sends no actor header (or claims to be `user`) is recorded as `agent:mcp`, and that actor goes with every downstream call, so the owning services' actor gate always passes; a development tool calling MCP with `dev:<name>` keeps its own actor. See [Activity](activity.md).

For every allowed mutation, the processor derives a stable per-action key from the Inbox operation, action index, tool, and canonical arguments. MCP forwards it to Tasks, Calendar, or Finance as `Idempotency-Key`. Those services persist the key and a payload hash with the created row: repeating the same key and payload returns the original row, while reusing a key with materially different content returns `409`. Manual callers may omit the header and retain the usual create behavior. Idempotency metadata is retained with the owned record for its lifetime; it is not in-memory state. Food writes are keyed without the action index (see [Food](#food)).

## Finance

MCP's Finance tools are Finance API operations, the same ones the Dashboard uses; MCP never reads Finance's database (see [Finance](finance.md)):

| Tool | Finance API |
| --- | --- |
| `finance_search_transactions` | `GET /v1/transactions` with typed filters: `q` (words in the counterparty, description, or notes), `accountId`, `categoryId` (an id or `uncategorized`), `from`/`to`, `direction` (`in`/`out`), `amountMin`/`amountMax` (absolute minor units), `status`, `source`, `limit` (default 20), and `cursor`. Ids, dates, and enum values are checked before Finance is called |
| `finance_find_transactions` | `GET /v1/transactions` with the caller's raw URL query (kept for older callers) |
| `finance_list_accounts`, `finance_list_categories` | `GET /v1/accounts` (balances, the built-in Cash account first; `balance` is what there is to spend, `bookedBalance` plus `pending`), `GET /v1/categories` |
| `finance_month_summary` | `GET /v1/summaries/monthly` (`month=YYYY-MM`, optional `currency`, `accountId`) |
| `finance_create_manual_transaction` | `POST /v1/transactions`, with the action's `Idempotency-Key` |
| `finance_list_ai_category_candidates` | `GET /v1/categories/ai/candidates` (`limit` 1 to 100, default 40): the booked transactions nobody categorized that the AI has not looked at, `total`, and the owner's choices by hand as `examples` |
| `finance_set_ai_categories` | `POST /v1/categories/ai/choices` with 1 to 100 `choices` (`transactionId`, `categoryId` or null), UUIDs checked before Finance is called; written by the [AI categories](#ai-categories) job, never by a capture |
| `finance_list_budget_plans`, `finance_get_budget_planning_data` | `GET /v1/ai-budget-plans` (`month`, `state`, `limit` 1 to 50, default 10; with `waiting`), `GET /v1/budgets/{month}/planning-data` (aggregates only); months and states checked before Finance is called |
| `finance_request_budget_plan`, `finance_claim_budget_plan`, `finance_set_budget_plan_result`, `finance_fail_budget_plan` | `POST /v1/ai-budget-plans` (trigger `schedule`, the 1st's plan), `POST /v1/ai-budget-plans/claim`, `PUT /v1/ai-budget-plans/{id}/result` (the checked proposal, ids checked before Finance is called), `POST /v1/ai-budget-plans/{id}/failure` (`error`, `retryAt` RFC3339); written by the [AI budget plans](#ai-budget-plans) job, never by a capture |

`finance_create_manual_transaction` needs only `amount` (`{"amount": <signed minor units>, "currency": "EUR"}`; a decimal amount is refused): without `accountId` the transaction goes to the built-in **Cash** account, so "spent 12 euros at the bakery" is `{"amount": {"amount": -1200, "currency": "EUR"}, "counterparty": "Bäckerei"}`; without `occurredOn` it is dated today in the owner's timezone; without `categoryId` the category rules choose. It also takes `counterparty`, `description`, and `note`. Its field names stay those the processor plans with: MCP sends `occurredOn` as Finance's `bookingDate` and `note` as `notes`. `accountId` and `categoryId` must be UUIDs (an account name is refused with a hint to leave it out for Cash) and `occurredOn` a date, checked before Finance is called. It records `mcp.action.requested`/`completed`/`failed` like every mutation, and Finance records the transaction itself (`finance.transaction.created`, caused by the request event).

## Food

MCP's Food tools are Food API operations, the same ones the Dashboard uses; MCP never reads Food's database (see [Food](food.md)):

| Tool | Food API |
| --- | --- |
| `food_list_shopping_items` | `GET /v1/shopping-items` with typed filters: `state` (`needed` or `bought`), `storeId` or `storeName` (looked up without case among all stores, `GET /v1/stores?includeArchived=true`; a name no store has lists nothing), `aisle`, `limit` (1 to 200), and `cursor` |
| `food_add_shopping_items` | `POST /v1/shopping-items` with the action's `Idempotency-Key`: 1 to 50 items of `name`, `amount`, `note`, `storeName`, and `aisle`, each sent with `source: "capture"` and the call's `sourceRef` (the Inbox item id). The response lists `{item, merged}` per item |
| `food_update_shopping_item` | `PATCH /v1/shopping-items/{id}` with the key: the item's new `name`, `amount`, `note`, `storeName` (a store Food has), or `aisle`, `clear` naming `amount`, `note`, or `store` to remove (sent as `null`); answers Food's item. A new name another needed item already has is Food's 409 `already_on_list`. The processor uses it for a follow-up such as "actually oat milk" (see [Recent captures](#recent-captures)) |
| `food_mark_bought` | `POST /v1/shopping-items/{id}/bought` for each of `itemIds` (1 to 50, each once), each with `<key>.<id>` as its `Idempotency-Key`, so a partly failed call replays the items already marked |
| `food_list_pantry_items` | `GET /v1/pantry-items` with `state`, `location`, `expiringWithinDays` (0 to 366), `limit`, and `cursor` |
| `food_add_pantry_items` | `POST /v1/pantry-items` with the key: 1 to 50 items of `name`, `amount`, `location`, `expiresOn`, `openedOn`, and `note`, with `source: "capture"` and `sourceRef` |
| `food_update_pantry_item` | `state` `used_up`, `thrown_away`, or `in_stock`: `POST /v1/pantry-items/{id}/used-up`, `/thrown-away`, or `/restock`; otherwise `PATCH /v1/pantry-items/{id}` with the given fields, `clear` naming `amount`, `expiresOn`, `openedOn`, or `note` to remove (sent as `null`). A state change and field changes are separate calls. The answer is Food's item with `restock`: what its staple put on the list by itself (`added`, `merged`, or `on_list`, with `message`) |
| `food_list_staples` | `GET /v1/staples`: every staple with its amount, store, aisle, `onList`, `inStock`, and `runningLow` |
| `food_mark_running_low` | `POST /v1/staples/running-low` with the key: `name` (1 to 200 characters) and `addToList`; answers Food's `{changed, staple, pantryItems, restock}` |
| `food_add_staple` | `POST /v1/staples` with the key: `name`, optional `amount` (at most 50 characters) and `storeName` (at most 100); answers `{created, staple}`, and a name already a staple (Food's 409 `staple_exists`) is `created: false` with that staple, not an error |
| `food_remove_staple` | `GET /v1/staples` to find the staple whose normalised name (or name) is `name`, then `DELETE /v1/staples/{id}` with the key; answers `{removed, staple}`, and no such staple, or one gone meanwhile (404), is `removed: false` |
| `food_list_recipes` | `GET /v1/recipes` with `q` (every word in the title, also inside a word), `tag`, `ingredient`, `limit`, and `cursor` |
| `food_list_meal_plan` | `GET /v1/meal-plan` with `from` and `to` (ISO dates, at most 31 days) |
| `food_plan_meal` | `PUT /v1/meal-plan/{date}/{slot}` with the key: `recipeId` or `text`, exactly one, and optional `servings` (1 to 100) and `note`; what the slot held is replaced |
| `food_clear_meal` | `DELETE /v1/meal-plan/{date}/{slot}` with the key; answers `{date, slot, cleared}`, and an empty slot (Food's 404 `not_found`) is `cleared: false`, not an error |
| `food_add_missing_ingredients` | `POST /v1/shopping-items/from-recipes` with the key: `recipeIds` (1 to 50, each once) or `from` and `to` (at most 31 days), and `dryRun`; the response lists each ingredient's status (`added`, `merged`, `in_pantry`, `on_list`) |
| `food_get_preferences` | `GET /v1/preferences`: the preferred cooking methods (most preferred first), the dislikes, the dietary notes |
| `food_list_suggestions` | `GET /v1/suggestions` with `limit` (1 to 50) and `mealSlot`: the saved recipes ranked for the owner's today, with their reasons |
| `food_list_ideas` | `GET /v1/ideas` with `state` (`new`, `saved`, `dismissed`) and `limit` (1 to 100) |
| `food_create_idea` | `POST /v1/ideas` with the key: `title`, `reason`, `ingredients` (`name`, `amount`), `steps` (one per line), `servings`, `tags`, `methods` (Food's), and `source` (`ai`, or `web` with its http(s) `sourceUrl`); checked before Food is called. Food answers 409 `idea_exists` or `recipe_exists` for a title it has; only agents (and system or development tools) write ideas |

Ids must be UUIDs, `aisle`, `location`, `state`, and `slot` Food's values, dates ISO dates, and date ranges at most 31 days, all checked before Food is called, and a name must not be blank. Merging (one needed item per name), stores created by name, and the length limits are Food's. Every write records `mcp.action.requested`/`completed`/`failed`, and Food records its own events, caused by the request event.

**Groceries go to the list; other purchases stay Tasks.** The owner's decision (2026-10-11):
- food, drinks, household, and drugstore items to buy are `food_add_shopping_items`, also when the capture gives a date ("buy milk tomorrow" only puts milk on the list); other purchases ("buy a flash drive tomorrow", "купить зарядку для телефона") stay `task_create`, due when a date is given;
- a capture that explicitly asks for a Task or a reminder ("Create a task: buy milk", "Создай задачу", "Remind me to buy milk at 18:00") stays `task_create`;
- a mixed capture is split: "buy milk and call mom" is a list item plus a Task;
- when it is genuinely unclear whether something is a grocery or household item or another purchase, Codex plans no action and the capture goes to Human Review.

**Planning.** The plan prompt asks for:
- `food_add_shopping_items` with `items`, at most 30: `name` as the owner wrote it, in their language and words, short and without the quantity, never translated ("купить молоко и яйца" is "молоко" and "яйца"; "Milch und 6 Eier" is "Milch" and "Eier" with `amount` "6"); `amount` only when stated; `note` only for a detail about the item; `storeName` only when the capture names the store, as written ("buy toothpaste at dm", "в Lidl купить хлеб"); `aisle` only when certain, otherwise Food's aisle rules place the item;
- `food_mark_bought` for groceries stated as bought ("bought the milk", "купил молоко", "Milch gekauft", "I already bought the chicken"), one per item, with `itemQuery` and `itemQueryAlternatives` chosen like the Task search terms above (`"milk"` plus `["молок", "Milch"]`), and also for a purchase stated as done that may not be a grocery ("I already bought the light bulbs"), since the Task is found either way (below);
- `food_add_pantry_items` for groceries at home, usually with when they expire ("I have 6 eggs until Friday", "в холодильнике йогурт до 14-го", "Joghurt läuft am Freitag ab"): `name` and `amount` as for the list, `location` only when the capture says where, and `expiresOn`, the owner-local ISO date, resolved like every relative date (see [Dates and the owner's timezone](#dates-and-the-owners-timezone));
- `food_update_pantry_item` for a pantry item used up ("used up the milk", "молоко закончилось", "die Milch ist alle": `state: "used_up"`) or thrown away (`"thrown_away"`), with `itemQuery` and `itemQueryAlternatives`; when the capture also says to buy more, a `food_add_shopping_items` as well.

Before anything runs, the processor checks each Food action: only those fields; 1 to 30 items, each with a non-blank `name` of at most 200 characters, text fields as text (or `null`), `aisle` and `location` from Food's values (blank is left out), and `expiresOn` an ISO date; a change has a non-blank `itemQuery`, and a pantry change `state` `used_up` or `thrown_away`. A planned action can never name an item id. An invalid action is unusable model output and retried like any other. The processor adds `sourceRef`, the Inbox item's id, to every add.

**Resolution.** Food has no name search, so for a change the processor reads the needed shopping list items (`food_list_shopping_items`, `state=needed`) or the in-stock pantry items (`food_list_pantry_items`, `state=in_stock`), 200 per page and at most ten pages (a longer list is a failed search, retried; a partial list is never acted on), and matches the names itself, without case, diacritics, or punctuation. A term matches a name it equals, or the start of one of its words, so a stem finds inflected forms ("молок" finds "Молоко") while a short term inside another word does not ("tea" never finds "Steak", nor "Milch" "Hafermilch"). Items a term names exactly win over the others: "milk" means "Milk", not "Milk chocolate". Then:
- exactly one item: `food_mark_bought` with `itemIds: [id]`, or `food_update_pantry_item` with `itemId` and the `state`;
- several items: Human Review listing them (at most ten), the planned action, and "Several shopping list items match: choose the one you bought" (or "Several pantry items match: choose the one you mean"). A candidate carries the item's `id`, `kind` (`shopping_item` or `pantry_item`), `name`, amount, store or location, and expiry, and a `title` the Dashboard shows (`Milch · 2 l · Lidl`, `Joghurt · fridge · expires 2026-10-16`). Approving one runs the action on that item without searching again: Inbox records the choice as `taskId`, which the processor takes as the item's id;
- no item, for `food_mark_bought`: the purchase may be a Task instead ("I already bought the chicken" with the Task "Buy chicken for dinner"), so open Tasks are searched with the same terms, as for `task_complete`. One Task is completed; several go to Human Review with those Tasks. The list is always searched first and wins when it matches, and a pantry change never looks at Tasks;
- nothing at all: nothing is created instead. The attempt records `{"tool":"none","plannedTool":"food_mark_bought","plannedArguments":{…},"reason":"Nothing on the shopping list or among the open Tasks matches, so nothing was marked bought"}` (for the pantry, "Nothing in the pantry matches, so nothing was changed"), the capture's other actions still run, and the item resolves.

A low-confidence or ambiguous plan with one Food change goes to Human Review with the matching items. As for Tasks, when one action of a plan goes to Human Review, the actions before it have already run and the ones after it do not.

**Idempotency.** Every Food write carries a key derived from the Inbox operation, the tool, and the arguments sent (including the resolved item ids and `sourceRef`), but not the action's place in the plan. A retried capture is planned again, and the new plan may list the same write elsewhere, after an action that failed or in another order; it still sends the same key, and Food answers with its first response without writing again (Food keeps keys for 30 days). A plan worded differently ("Milk" instead of "milk") gets another key; then Food's merge rule still keeps one needed item per name.

### Staples and running low

A staple is a name the owner always wants at home; when one runs low, is used up, or is thrown away, Food puts it back on the shopping list by itself (its restock, `source: staple`; see [Food → Staples and running low](food.md#staples-and-running-low)). Codex plans three actions for it (`internal/processor/staples.go`):

- `food_mark_running_low` for something running low but not finished yet ("almost out of milk", "мясо заканчивается", "почти закончилось молоко", "fast keine Milch mehr", "Milch wird knapp"), never `food_update_pantry_item` or `task_create`: `itemQuery` the item as the owner wrote it, untranslated ("мясо"), `itemQueryAlternatives` its translations and stems as for Tasks (`["мяс", "meat", "Fleisch"]`), and `addToList: true` only when the capture also says to buy it ("мясо заканчивается, купи"). Codex never adds a list item for something running low: buying it is `addToList`.
- `food_add_staple` for something that should always be at home ("milk is a staple", "молоко всегда должно быть дома", "Milch immer da haben", "Eier sollen immer im Haus sein"): `name` as the owner wrote it, `amount` and `storeName` only when the capture says; it puts nothing on the list now.
- `food_remove_staple` for something no longer to keep at home ("remove milk from staples", "молоко больше не нужно держать дома", "Milch muss nicht mehr immer da sein"), with `itemQuery` and `itemQueryAlternatives`.

The processor checks them like the other Food actions (only those fields; `itemQuery` non-blank and at most 200 characters, `addToList` a boolean; a staple's `name` non-blank and at most 200, `amount` at most 50, `storeName` at most 100, all text).

**Resolution.** Food compares names only by their exact normalised form ("Milch" is not "Vollmilch"), so the processor matches the words to a name Food knows, as for the other Food changes (the exact name wins, else the start of a word, without case, diacritics, or punctuation). For running low it reads the staples (`food_list_staples`) and the in-stock pantry items (paged as above), one candidate per normalised name (a staple and the pantry items of its name are one); for a removal only the staples:
- exactly one name: `food_mark_running_low` with that name and `addToList`, or `food_remove_staple` with the staple's name. "мясо заканчивается" thus marks the staple "Fleisch" (not "Hackfleisch": "fleisch" does not start its word), and "Почти закончился рис" the pantry's "Reis";
- several names: Human Review with them (at most ten), "Several staples or pantry items match: choose the one running low" (or "Several staples match: choose the one to remove"). A candidate is the staple's id, else its first pantry item's, with `kind` `staple` or `pantry_item`, `name`, and a `title` such as `Milch laktosefrei · staple` or `Milch 3,5% · 1 l · fridge`; the approved choice runs with that name, without searching again;
- none, for running low: the owner's words go to Food as they are. Food flags nothing and changes nothing (`changed: false`, `restock: null`), unless `addToList` puts them on the list, and the capture resolves;
- none, for a removal: nothing is removed (`{"tool":"none", …, "reason":"No staple matches, so none was removed"}`), and the capture's other actions still run.

**Restock and the capture's own list add.** "молоко закончилось, надо купить" plans a used-up pantry item and a list add for the milk. When the pantry item is a staple, Food has already put it back on the list, possibly under another language's name ("Milch" for "молоко"), so the processor leaves the add out: it runs the actions that may restock (`food_update_pantry_item`, `food_mark_running_low`) before the capture's `food_add_shopping_items` (each group in its planned order, only in a plan that has both), reads each answer's `restock` (`added`, `merged`, or `on_list`), and drops from the add every item that is the restocked item: its name, one of the words that named it, or a one-word name such a word starts ("молоко" for "молок"; "milk chocolate" stays). An add left empty records `{"tool":"none", …, "reason":"Already on the shopping list by itself (staple): молоко"}`; otherwise the add records `notAdded` with the names left out. Without a restock (no staple) the add runs as planned. Every staple write carries a key like the other Food writes.

Tests: `staples_action_test.go` (validation; a staple found in another language; a pantry item flagged; the owner's words when nothing matches, with and without `addToList`; several names and an approved choice; staples added and removed; the restocked item left out of the add in either order, also for running low; the matching rule; the reordering; the prompt), the routing corpus in RU, DE, and EN, and `cmd/server/staples_test.go` for the tools. The benchmark seeds the staple "Butter" and "Reis" in the pantry ([AI runtime benchmark](../verification/ai-runtime-benchmark.md)); its captures' words stay out of the prompt (a test checks), and `tools/smoke-processor-codex-actions` marks the seeded staple "Mustard" running low.

### Meals and recipes

Planning what to eat at a meal of a day comes before the grocery rule (P15-05):
- "Lasagne for dinner on Thursday", "на ужин в среду паста", "Mittwoch Abendessen: Pasta" are `food_plan_meal`, never a Task, a Calendar event, or a list item; an appointment to eat with someone at a time or place ("dinner with Anna at 19:00") stays a Calendar event. Codex gives `recipeQuery` (the meal as the owner names it, untranslated), `recipeQueryAlternatives` (its name in the other two languages and its most distinctive word), `date` (resolved like every relative date; the capture's date when no day is named), `slot` from the meal word (breakfast, завтрак, Frühstück; lunch, обед, Mittagessen; dinner, supper, ужин, Abendessen), and only when stated `servings` and `note`. A meal without a meal word goes to Human Review with "Say which meal it is: breakfast, lunch, or dinner.": Codex is asked to answer it so, and the processor sends a planned or cleared meal without a `slot` there too, before validating it. Food replaces a meal already planned in the slot;
- "cancel dinner on Friday", "убери ужин в пятницу" are `food_clear_meal` with `date` and `slot`, never `calendar_cancel`; an empty slot is no failure (`cleared: false`);
- "add the ingredients for the lasagne to the list", "купи всё для борща" are `food_add_missing_ingredients` with `recipeQuery` and `recipeQueryAlternatives`; "buy what I need for this week's meals" is `food_add_missing_ingredients` with `week` (`this` or `next`), or `from` and `to` for other days. The processor turns `week` into Monday through Sunday of the capture's week (or the next) in the capture's timezone, from the capture time;
- without such meal or recipe words the grocery rule stands: "buy pasta" is a list item.

The processor checks these actions like the other Food actions: only those fields; `recipeQuery` non-blank and at most 200 characters (it may become the meal's text), alternatives as text, `date` an ISO date, `slot` `breakfast`, `lunch`, or `dinner`, `servings` a whole number from 1 to 100, `note` text; missing ingredients name exactly one of a recipe, a `week` (`this` or `next`), or a range of at most 31 days. A planned action can never name a recipe id.

**Recipe resolution**, as [Food](food.md#recipes) documents it. For each term (`recipeQuery`, then its alternatives, as for Task search terms) the processor calls `food_list_recipes` with `q` (at most 50 recipes) and unions the recipes found. A recipe whose `normalizedTitle` equals a term normalised the way Food normalises names (NFKC, lower case, "ё" as "е", spacing, surrounding punctuation) is the one, since titles are unique. Otherwise:
- exactly one recipe found: `food_plan_meal` with `recipeId`, or `food_add_missing_ingredients` with `recipeIds: [id]`;
- several: Human Review with the planned action, "Several recipes match: choose the one to plan" (or "…the one whose ingredients to add"), and the recipes as candidates (at most ten: `id`, `kind: "recipe"`, `recipeTitle`, and a `title` with the tags, `Pasta Bolognese · pasta, italian`). Approving one runs the action with it without searching again (Inbox's `taskId` is the recipe id);
- none: a meal is planned as free text, `recipeQuery` trimmed (`text: "суп"`), which the owner can turn into a recipe later; missing ingredients go to Human Review with no candidates and a plain reason, "No recipe is called “борщ”. Add the recipe on the Food page, or say which items to buy.", since the owner expects groceries; nothing is added or created instead, and the capture's other actions follow the usual rule (those before it have run, those after it do not).

Meal writes carry the same Food keys (the operation, the tool, and the arguments sent, with the resolved recipe id or the week's dates), so a retried capture plans or clears its meal once.

`make processor-codex-actions-smoke` covers this with the real Codex CLI: "Buy oat milk." puts exactly one "oat milk" on the list, from that capture; replaying the processor's own Food write with its key returns the first answer and adds nothing; and the same capture again merges into that item (`merged: true`). With a recipe "Oat porridge", "Oat porridge for breakfast on 2026-10-14." plans that recipe as that breakfast, once, and replaying the processor's write returns the same entry. The [AI runtime benchmark](../verification/ai-runtime-benchmark.md) checks the routing in English, Russian, and German.

### Recipe links

A recipe link is saved through the [recipe-import](recipe-import.md) integration, which reads the page and saves the recipe in Food (P15-07). MCP's `recipe_import` takes `url` (http or https with a host, else refused before anything is called), optional `caption`, `title`, and `saveLink`, and the action's `Idempotency-Key`, and uses recipe-import's API, each call with the caller's trace and actor:
- `POST /v1/imports/preview` `{url}` reads the link. A link recipe-import refuses (400, such as a private address) is not saved, with its message as the reason.
- `structured` (a schema.org recipe): `POST /v1/imports` `{url}` with the key, so recipe-import reads the page again and saves it; with a `title`, the preview's draft with that title is saved as `overrides` instead.
- `preview` (no recipe data, such as an Instagram, TikTok, or YouTube post) or `failed` (unreadable, as Instagram often is), with a `caption`: `POST /v1/imports/text` `{text: caption, sourceUrl: url}` reads it, and a draft with ingredients or steps is saved as `overrides`, completed from the page: its title when the caption has none (a given `title` wins), its image and site name; the page's description is left out, since a post's is the caption again. A caption with neither, or with no title to be found, counts as no caption.
- `preview` without a usable caption and with `saveLink` (the owner asked to save the link): the preview's draft, tagged `to-review`, is saved as the stub to review later. A `failed` page has no title to save a stub with, unless `title` gives one.
- Anything else saves nothing.

It answers `{saved, method, reason, recipe, recipeId}`. A save recipe-import answers 409 `recipe_exists` is `saved: true` with `alreadySaved: true` and that `recipeId`; 422 `import_failed` and a 400 Food refusal are `saved: false` with the message; recipe-import or Food unavailable (502) is an error, retried. Nothing saved is `saved: false` with the preview's reason ("Instagram posts can't be read directly: paste the caption to fill in the ingredients and steps."), else "The link has no recipe to read: paste the recipe or its caption, or ask to save the link.". MCP waits up to 45 seconds for recipe-import, which fetches the page while it answers.

**Planning.** A capture whose main content is a recipe link, or that asks to save a recipe from a link, in any language ("save this recipe https://www.chefkoch.de/…", "Rezept speichern: https://…", "сохрани рецепт https://…"), is `recipe_import`, never a Task, an event, or a list item; so is a link to a recipe site (chefkoch.de, lecker.de, bbcgoodfood.com, allrecipes.com, eda.ru, povarenok.ru, …) and a bare instagram.com, tiktok.com, youtube.com, or youtu.be link, such as one shared from the phone. Codex gives `url` (as written, `https://` added when the link has none), `caption` (the text that came with the link and may hold the recipe), `title` only when the owner names the recipe, and `saveLink` only when the owner explicitly asks to save it ("save this", "speichern", "сохрани"). A phone share (`sourceMetadata.via: "share-target"`, P16-01) arrives as its title, text, and link, one per line; the title line names the page or post and is neither caption nor title. A link clearly about something else (a news article, a shop's product page) follows the other rules, and a bare link with no word of what to do and no sign of food goes to Human Review with "What should I do with this link?".

The processor checks a planned `recipe_import`: only those fields, `url` http or https with a host and at most 2000 characters, `caption` text of at most 20,000, `title` non-blank text of at most 200, `saveLink` a boolean. The link must be one the capture holds (a scheme Codex added aside), so a made-up link is never fetched; otherwise the plan is unusable model output, retried. The call carries a Food key like every Food write (the operation, the tool, and the arguments), which recipe-import passes on to Food, so a retried capture saves the recipe once; a capture of a link already saved finds it (`alreadySaved`). An answer with `saved: false` sends the capture to Human Review with no candidates and recipe-import's reason, such as "Instagram posts can't be read directly: paste the caption to fill in the ingredients and steps."; the owner can edit the capture to add the caption. As for every Human Review, the actions planned before it have run and those after it do not.

`make processor-codex-actions-smoke` covers it with the real Codex CLI on the verification stack with the browser tests' fixture overlay: "Save this recipe: http://ics-fixture/smoke-pilaf.html" (a JSON-LD page) saves "Smoke Pilaf" once with that link as its source, replaying the processor's save with its key returns the same recipe, and the same capture again finds it already saved.

### Recipe ideas

The processor runs a second, small job next to capture processing (P15-09, `internal/processor/ideas.go`): recipe ideas for "What can I cook?", following the owner's sources (saved recipes first, then AI ideas, TheMealDB, and maybe the web) and the air fryer as the preferred way of cooking. It is not an Inbox capture.

- **When.** Once a day at `LIFE_OS_IDEAS_TIME` (HH:MM in `LIFE_OS_TIMEZONE`, default 16:00; `off` turns the daily run off), only when the pantry has food in stock, and skipped on a day the job already left ideas (it finds its own in Food, by its actor, so a restarted processor does not run again). A failed daily run is tried again an hour later, at most three times a day. And when the owner asks: "Get ideas" in the Dashboard (`POST /api/processor/ideas/requests`, which the Dashboard passes to the processor's private `POST /ideas/requests` with the owner's actor; a request without an actor is 400 `actor_required`) queues one run, throttled to one every 10 minutes and six a day (the owner's day; 429 `too_soon` or `daily_limit` with `retryAt`). A request while a run waits or runs joins it. The owner's request runs also with an empty pantry, from the preferences alone. The job checks every 30 seconds whether a run is due; runs never overlap, and Codex's slots (`LIFE_OS_CODEX_MAX_CONCURRENCY`) keep a run from planning at the same time as a capture beyond that limit.
- **What Codex is told.** The job reads through MCP, as `agent:codex-recipe-ideas` (every call and idea is attributed to it): `food_get_preferences`; `food_list_pantry_items` (`state=in_stock`), from which it names what expires within 3 days (`expiringSoon`, with the days left); `food_list_suggestions` (the top ten saved recipes, not to repeat); `food_list_ideas` new, dismissed, and saved (not to repeat, and to see whether it ran today); and `food_list_meal_plan` two weeks back and one ahead. The prompt asks for up to three realistic weeknight recipes: the food that expires soonest first (each idea using at least one such item when there is any), in-stock ingredients named exactly as the pantry names them (so Food sees them at home), never a dislike in any form, the dietary notes followed, the preferred methods first (at least 2 of 3 ideas, most of them whatever their number, cooked with the first preferred method wherever the dish suits it, another method only for a dish that truly needs it; in the air fryer the steps give its temperature and time), nothing saved, suggested, or planned lately, the owner's language (that of most pantry names, else English), 3 to 10 concise steps, servings (2 by default), a few tags, the methods the steps use, and one sentence on why now. A run-specific line names the first preferred method: "Here the first preferred method is the air fryer (air_fryer): at least 2 of 3 ideas cook with it." (P15-10, after a run left only one air fryer idea of three). This is a prompt rule, not a filter: a run counts the ideas cooked with the first preferred method and with any preferred one (see Status below).
- **Structured output.** Codex answers to a JSON Schema (`codex exec --output-schema`): `{ideas: [{title, ingredients: [{name, amount}], steps: [...], servings, tags, methods, reason, source, sourceUrl}]}`. The processor then checks every idea and drops any that fails: a title of 3 to 120 characters, 2 to 25 ingredients (names up to 100, amounts up to 50 characters), 2 to 15 steps of up to 300 characters, at most 12 servings, at most 8 tags of up to 40 characters, methods only Food's, a reason of 10 to 300 characters, `source` `ai` (or `web`, only when web search is on, with an http or https page whose host is a name with a dot: not localhost, a bare host name, or an IP address; the processor never fetches it), no disliked ingredient in the title or an ingredient (compared word by word without case, diacritics, or punctuation, also across plural and case endings and inside compounds: "Pilze" catches "Steinpilz" and "Pilzpfanne", "грибы" "грибной"), and no title already saved, suggested, or given in the same answer. At most three are kept.
- **Leaving them.** Each checked idea goes to `food_create_idea` with the Idempotency-Key `ideas-<sha256 of the run and the normalised title>` (the daily run is `daily:<date>`, a request `request:<time>`), so a repeated write of a run is answered with the first. A 409 (`idea_exists`, `recipe_exists`) is skipped. The job never saves or dismisses ideas: the owner does, in the Dashboard.
- **Web search.** The Codex CLI in the processor image (0.160) has a `web_search` setting for `codex exec` (`disabled`, `cached`, `indexed`, `live`; its config parser accepts these and refuses others). Capture planning always runs with `-c web_search="disabled"`; the ideas job runs with `LIFE_OS_IDEAS_WEB_SEARCH` (`disabled` by default, `cached`, or `live`). With search on, the prompt tells Codex to search: at least one idea must be a recipe found on a real recipe page, preferably a site in the owner's language (such as chefkoch.de for German), with `source: "web"` and `sourceUrl`, its ingredients as listed there (pantry names where in stock), and its steps summarized in Codex's own words, never copied; the others may be its own (`ai`). (A first test with search only allowed left three `ai` ideas in under 10 seconds: Codex did not search.) It stays off until one authenticated run confirms it works; to turn it on, set `LIFE_OS_IDEAS_WEB_SEARCH=live` in `.env` and recreate the processor.
- **Status.** `/status` has `ideas`: `dailyAt`, `webSearch`, `nextRunAt`, `running`, `queued`, and `lastRun` (`trigger`, `startedAt`, `finishedAt`, `created`, `skipped`, `rejected`, `failed`, `firstMethod` with `withFirstMethod` and `withPreferredMethod` (created ideas cooked with the first preferred method, and with any preferred one), `fromWeb` (created ideas found on a page), `outcome`: `created`, `none`, `empty_pantry`, `done_today`, or `failed`, and `error`); `GET /ideas` on the private port answers the same. The ideas runs count in the Codex state and token usage like planning runs, and each finished run logs one line ("recipe ideas: daily run created: 3 created (2 with air_fryer, 3 with a preferred method, 1 from the web), 0 skipped, 0 rejected, 0 failed"). The Status page shows "Recipe ideas" (the last run) and "Next recipe ideas" under Automatic processing.
- **What a restart forgets.** The schedule and the owner's requests are kept in memory: a request not yet run and the throttle's counts are lost on a restart, while a daily run is not repeated on a day the job left ideas.

The [AI runtime benchmark](../verification/ai-runtime-benchmark.md) asks for ideas once (with chicken expiring tomorrow and mushrooms disliked) and checks them structurally.

## AI categories

The processor runs a third job next to capture processing (P13-08, `internal/processor/categories.go`): the AI fills the category gaps Finance's rules leave. Finance's rules and merchant category codes categorize first (see [Finance](finance.md#ai-categories)); what is left the job categorizes, marked "by AI", and the owner's corrections always win. It is not an Inbox capture.

- **When.** Every 5 minutes the job asks Finance how many transactions wait (`finance_list_ai_category_candidates`, a count and the first 40: cheap), so a bank sync's new transactions get a category within minutes. With some waiting it categorizes one batch of 40 in one Codex run; while a backlog remains the next batch comes 2 minutes after the last, so captures get Codex in between, and at most 25 batches (1,000 transactions) run per owner-local day; a larger backlog, such as a full history read, drains on the following days from midnight. The job checks every 30 seconds whether a run is due, runs never overlap, and Codex's slots (`LIFE_OS_CODEX_MAX_CONCURRENCY`, 1) keep a batch from planning at the same time as a capture.
- **Switch.** `LIFE_OS_AI_CATEGORIES` (`on`, the default, or `off`; compose passes it to the processor). Off, the job reads and changes nothing, and `/status` says so. The verification stack turns it off unless `LIFE_OS_VERIFY_AI_CATEGORIES=on` (`tools/verify-compose`): its processor uses the real Codex sign-in, and categorizing the browser tests' transactions behind their back would make them flaky.
- **What Codex is told.** The job reads through MCP, as `agent:codex-finance-categories` (every call and choice is attributed to it): the candidates with Finance's `examples` (the owner's latest choice by hand per counterparty, at most 50) and `finance_list_categories` (the active ones). The prompt gives the categories (`id`, `name`, `kind`), the examples (counterparty and category name), and per transaction only a short `ref` (`t1` … `t40`), the date, the direction (`in` or `out`), the amount without its sign ("23.50 EUR"), the account kind, the counterparty (at most 100 characters), and the description (at most 200): no notes, account names, or ids. Before that, IBAN-like strings become `[IBAN]` (two letters, two check digits, and the account, with at least ten digits, so words stay; words after it are kept), anything that looks like a card number becomes `[card]` (12 to 19 digits, maybe grouped or partly masked, such as `XXXX XXXX XXXX 1234`), and other runs of eight or more digits (references, mandates, account numbers) `[number]`. The rules: pick one of the owner's categories by id or null when unsure, never guess; money out to an expense category, money in to an income category, money between the owner's own accounts (Umbuchung, Übertrag, Sparplan, a transfer to themselves) to a transfer category; a refund null; read German bank texts and the merchant behind PayPal, Klarna, Google, or Apple Pay; follow the examples for the same or a similar counterparty; a person's name alone says nothing; Amazon is Shopping unless the text says Prime or a subscription; and a confidence from 0 to 1, null below 0.75. Web search is always off (`-c web_search="disabled"`).
- **Structured output.** Codex answers to a JSON Schema (`--output-schema`): `{choices: [{ref, categoryId, confidence}]}`. The job keeps a pick only for a `ref` of the batch (the first choice for it), one of the owner's active categories, a confidence of at least 0.75, and a kind that fits the money (out: expense or transfer; in: income or transfer). Anything else, and a transaction without a choice, is left without a category.
- **Leaving them.** One `finance_set_ai_categories` call per batch sends every transaction of the batch: the kept pick, or `null`. Finance applies a pick only while no one else chose (the owner, a rule, or a code that landed meanwhile wins, `skipped` with reason `chosen`) and notes the others as looked at, so each transaction goes to Codex once until its text changes; a restarted processor sends nothing twice. Finance records one `finance.ai_categories.applied` event per batch that categorized something, after MCP's `mcp.action.requested`/`completed`.
- **Retries.** As in [Retry scheduling](#retry-scheduling): a failed Codex run waits for the usage reset when the limit is reached, else backs off from 30 s, doubling, capped at an hour, with jitter; so does MCP or Finance being unreachable. An unusable answer is retried the same way, and after 5 in a row the batch is left without categories (and noted as looked at) so the backlog moves on.
- **Status.** `/status` has `categories`: `enabled`, `running`, `nextRunAt`, `waiting` (transactions waiting at the last check, null before it), `lastCheckAt`, `batchesToday`, and `lastRun` (`startedAt`, `finishedAt`, `examined`, `categorized`, `skipped` with `unsure`, `rejected`, and `chosenMeanwhile`, `outcome`: `categorized`, `none`, or `failed`, and `error`). Its Codex runs count in the Codex state and token usage like planning runs, and each batch logs one line ("AI categories: 40 transactions categorized: 31 categorized, 9 skipped (6 unsure, 2 rejected, 1 chosen meanwhile); 120 waiting"). The Status page shows "AI categories" (the last batch) and "Next AI categories" under Automatic processing.

The [AI runtime benchmark](../verification/ai-runtime-benchmark.md) turns the job on and checks three transactions: a restaurant goes to Eating out, a web hosting bill to Subscriptions or Utilities & phone, and a transfer from a person with a bare thank-you is left alone.

## AI budget plans

The processor runs a fourth job next to capture processing (P13-09, `internal/processor/budget_plans.go`): the AI plans a month's budget and says where the owner can spend less. Finance keeps every plan from the request on, checks the AI's proposal, and applies it only when the owner says so (see [Finance](finance.md#ai-budget-plans)); the Dashboard shows it on the Budget tab. It is not an Inbox capture.

- **When.** The owner asks with "Plan my budget" (a Finance request, kept in `finance_db`; nothing goes to the processor directly). Every 30 seconds the job asks Finance how many plans wait (`finance_list_budget_plans`, a count: cheap) and, when some do, claims the oldest (`finance_claim_budget_plan`); Finance hands out one plan at a time, so a plan runs within about a minute and never beside another. On the 1st of each month from 06:00 in `LIFE_OS_TIMEZONE` the job asks for that month's plan itself (`finance_request_budget_plan`, trigger `schedule`); a processor that was down then still asks until the 3rd, and Finance keeps one scheduled plan a month, so a restart asks again harmlessly. When the salary already asked for that month's plan (Finance's [Payday](finance.md#payday)), Finance answers with that one, unless it failed; the job needs no change for it. Runs never overlap, and Codex's slots (`LIFE_OS_CODEX_MAX_CONCURRENCY`, 1) keep a plan from running at the same time as a capture.
- **Switches.** `LIFE_OS_AI_BUDGET_PLANS` (`on`, the default, or `off`) switches the job: off, it reads and changes nothing, the owner's requests wait in Finance as `requested`, and `/status` says so. `LIFE_OS_AI_BUDGET_PLAN_MONTHLY` (`on`, the default, or `off`) switches the plan on the 1st. Compose passes both to the processor. The verification stack turns the job and its monthly plan off unless `LIFE_OS_VERIFY_AI_BUDGET_PLANS=on` (`tools/verify-compose`): the browser tests leave the AI's plans themselves.
- **What Codex is told.** The job reads through MCP, as `agent:codex-budget-plan` (every call and write is attributed to it): the month's planning data (`finance_get_budget_planning_data`: up to 12 complete months of income and spending, per active expense category its spending per month, median, last month, trend, current planned amount, and top 5 merchants with payments, total, and per month; the plan that applies; the confirmed subscriptions; the balance now; never single transactions) and what Food has (`food_list_pantry_items` in stock, `food_list_recipes`, `food_list_ideas` new: counts, up to 20 pantry names, up to 5 idea titles; without Food the plan does without). Categories go by short refs (`c1`, `c2`, …); merchant, subscription, and pantry names pass P13-08's redaction (`[IBAN]`, `[card]`, `[number]`) and are mapped back to Finance's names afterwards, so no IBAN or card number reaches Codex. Amounts are minor units (cents). The rules: an amount for every category from its median, last month, and trend, fixed costs kept and flexible ones lowered where the data show room, rounded to whole euros, each with one sentence; 2 to 5 concrete ways to spend less, the largest first, each tied to a category and, where the data show them, its listed merchants (such as eating out versus groceries, or many small payments at one place), never saving more than they cost; a suggestion to cook more may link to Food's recipes when Food has recipes, ideas, or pantry items; never invented categories, merchants, or numbers; the income estimate, the exact total, and the savings (income minus total); aim for the savings goal when there is one and say when it cannot be reached; be strict when the balance is low; say when the plan is rough (fewer than 2 full months). Web search is always off (`-c web_search="disabled"`).
- **Structured output.** Codex answers to a JSON Schema (`--output-schema`): `{currency, headline, lines: [{category, proposedMinor, reason}], suggestions: [{title, detail, category, merchants, monthlySavingMinor, link}], projectedTotalMinor, incomeEstimateMinor, projectedSavingsMinor}`. The job checks it as Finance will: the data's currency; a headline of 10 to 200 characters; a line for every category with history or a planned amount (a known ref, once, 0 or more, a reason of 5 to 240 characters; one without either may be left out); 2 to 5 suggestions (none needed without spending) with a title of 3 to 80 and a detail of 10 to 300 characters, a saving above 0 and no larger than its category's larger of median and last month, its listed merchants' monthly spending, or all spending without a category, together no larger than all spending; `food_recipes` kept only when Food has something to cook; totals that add up to within one unit of the currency (the job then sends the exact sums). An answer that fails is retried; it is never left.
- **Leaving it.** `finance_set_budget_plan_result` sends the checked plan with Finance's category ids and merchant names; Finance checks it again against the same data (400 `invalid_plan`, retried like an unusable answer) and keeps it, with its own evidence per line, as `ready` for the owner to apply or dismiss. A plan the owner dismissed meanwhile (409 `plan_not_running`) is dropped. The job never applies a plan. MCP audits each write (`mcp.action.requested`/`completed`); the result's audit names the plan and counts only, and Finance records `finance.ai_budget_plan.created`.
- **Retries.** A failed run goes back to Finance with `finance_fail_budget_plan` and `retryAt`, as in [Retry scheduling](#retry-scheduling): a usage limit waits for the reset, anything else backs off from 30 s, doubling per earlier run of the plan, capped at an hour, with jitter. An unusable answer on the plan's 5th run or later, or a Codex or service failure on its 8th, fails the plan for good (no `retryAt`; `finance.ai_budget_plan.failed`). A shutdown hands the plan back to run again at once; a processor that dies mid-run leaves its claim, which Finance hands out again after 15 minutes. MCP or Finance being unreachable backs the job's checks off the same way.
- **Status.** `/status` has `budgetPlans`: `enabled`, `monthly`, `running`, `nextCheckAt`, `nextMonthlyAt` (the next 1st's plan; null when the job or the monthly plan is off), `waiting` (plans waiting at the last check, null before it), `lastCheckAt`, and `lastRun` (`planId`, `month`, `trigger`, `startedAt`, `finishedAt`, `attempt`, `outcome`: `ready`, `retry`, `failed`, or `dropped`, `categories`, `suggestions`, and `error`). Its Codex runs count in the Codex state and token usage like planning runs, and each run logs one line ("AI budget plan: request plan for 2026-11 (run 1) ready: 10 categories, 3 ways to spend less"). The Status page shows "AI budget plans" (the last run) and "Next AI budget plan" under Automatic processing.

The [AI runtime benchmark](../verification/ai-runtime-benchmark.md) seeds three made-up months and checks that the plan is ready, with at least one way to spend less in eating out.

## Calendar events

MCP's Calendar tools are Calendar API operations, the same ones the Dashboard uses; MCP never reads Calendar's database:

| Tool | Calendar API |
| --- | --- |
| `calendar_list`, `calendar_search` | `GET /v1/events`, `GET /v1/events/search` (the caller's URL query, such as `q=Zahnarzt&from=…&timeZone=Europe/Berlin`) |
| `calendar_get` | `GET /v1/events/{id}` |
| `calendar_create` | `POST /v1/events` with `title`, `description`, `location`, `allDay`, `startAt`/`endAt` or `startDate`/`endDate`, `timeZone`, `reminders` (the event's own, added to the owner's default reminders), `useDefaultReminders` (left out: true; `false` with no `reminders`: none at all), `priority` (`low`, `medium`, or `high`; left out: medium), and the action's `Idempotency-Key` |
| `calendar_update` | `PATCH /v1/events/{id}` with only the given fields (`reminders` replaces the event's own, `useDefaultReminders` turns its defaults on or off, `priority` sets how important it is); `clear` names fields to remove (`description`, `location`, `timeZone`, `reminders`, which returns the event to its defaults alone), sent as `null`. A field both set and cleared, an unknown `clear` entry, or nothing to change is rejected before Calendar is called |
| `calendar_cancel` | `PATCH /v1/events/{id}` `{"status":"cancelled"}`: kept as history, restorable. With `recurrenceId` (an occurrence's `occurrence.recurrenceId`: an RFC 3339 instant or a date, else rejected before Calendar is called) it skips only that occurrence of a recurring event: `PATCH /v1/events/{id}/occurrences/{recurrenceId}` `{"status":"cancelled"}` |
| `calendar_delete` | `DELETE /v1/events/{id}`, permanent; for an MCP client acting on the owner's explicit request. The processor never uses it |

`calendar_create` and `calendar_update` take no `recurrence` (the MCP server rejects the field): recurring events are created and changed only in the Calendar (the Dashboard). `eventId` must be a UUID. Every mutation carries the caller's `X-Life-OS-Actor` (or `agent:mcp`) and records `mcp.action.requested`/`completed`/`failed`.

**Planning.** Codex may propose `calendar_create`, `calendar_update`, and `calendar_cancel`. Tasks are to-dos (call, buy, renew, pay, …) with an optional due date; Calendar events are appointments and meetings with a time and maybe a place. "Move the electrician call to Friday" is a Task change. A place goes in `location`, not the title ("Add dentist at Dr. Weber, Friday 15:00 for an hour" is title "Dentist", location "Dr. Weber"). Moving or changing an event is `calendar_update` with an `eventQuery`, `eventQueryAlternatives`, and only the changed fields; cancelling, deleting, or removing one is `calendar_cancel` with only the search terms. A request to be reminded of, or to add a reminder to, an event that already exists is `calendar_update` with an `eventQuery` and `reminders`, also when the item restates the event. The search terms follow the Task rules above: the shortest distinctive word, plus up to six translations and stems in the owner's other languages (`"dentist"` plus `["Zahnarzt", "стоматолог", "зубн"]`). To reschedule, Codex gives the new start, and the end only when the capture states one or a duration, or a `move` relative to the time the event has ("an hour later", "to tomorrow, same time"; see [Task and event details and moves](#task-and-event-details-and-moves)). Relative dates follow the owner's timezone as described in [Dates and the owner's timezone](#dates-and-the-owners-timezone). A planned action can never name an event id: `eventId` or `taskId` in a planned Calendar change makes the plan invalid.

**New events.** A planned `calendar_create` without an end gets the default length, as in Google Calendar: a timed event lasts one hour and an all-day event is its one day ("Add a haircut on Sunday at 11:00" names no duration). Reminders the item asks for are the event's own and add to the owner's default reminders.

**Default reminders stay on.** AI reminders only ever add to the owner's default reminders; turning an event's defaults off or on is the owner's, in the Calendar (the Dashboard). The plan prompt does not offer `useDefaultReminders`, and the processor drops it from every planned or approved `calendar_create` and `calendar_update` before validating, so a plan that sends it does not fail: the field is left out of the MCP call and the attempt's action records `"droppedFields":["useDefaultReminders"]`. (Codex once planned `useDefaultReminders: false` unasked for "Add a haircut … remind me a day before and 3 hours before", which would have dropped the owner's 30-minute default.) An update that only turned the defaults off or on goes to Human Review with no candidates and "Default reminders are turned off or on in the Calendar.". The MCP tools keep the parameter for other clients.

**Restated events (duplicate guard).** A capture sometimes restates an event that already exists to add to it, and Codex still plans a `calendar_create`: "Сегодня в 8 вечера начало свидания с Ирой. Ну, пускай будет 3 часа." created "Свидание с Ирой" 20:00–23:00, and four minutes later "Сегодня в восемь вечера свидания с Ирой. Напомни мне за два часа до этого…" was planned as the same event 20:00–21:00 with a 120-minute reminder (BUG-33). So before every planned `calendar_create` the processor calls `calendar_search` once for the planned title on the planned start's local day (`from`/`to` that day in the capture's timezone, the same `timeZone`, `limit=10`, and the same filter as every event lookup, `changeableEvents`: `editable=true`). Calendar matches words with their diacritics, so each word is searched by its longest part without any ("Zahnärztin" as "rztin"; at most ten words, 200 characters). A found event is a **duplicate** when it is of the same kind and starts when the plan does (a timed event within five minutes, an all-day event on the same date) and its title equals the planned one apart from case, diacritics, punctuation, and spacing ("свидание с Ирой!" is "Свидание с Ирой"; "Свидание с Ирой в кино" is not). Then:
- no duplicate: the event is created as before;
- exactly one: the create becomes a `calendar_update` of that event carrying only what the capture adds: `reminders` as the event's own plus the new ones, each once (as for any AI update, below); `location` and `description` only when the event has none (its own are never overwritten); `priority` when it differs; and a new end only when the plan states one. An end exactly the default length after the planned start (an hour, or the one day of an all-day event) is what Codex fills in when the capture names no duration, so it never cuts a longer event short ("…for two hours" after a one-hour event does set 21:00). The event keeps its title and start. The processing attempt records `{"tool":"calendar_update","arguments":{"eventId":…,"reminders":[…]},"convertedFrom":"calendar_create","plannedArguments":{…}}`. When the event already has everything (the same capture twice), nothing is called and the attempt records `{"tool":"none","convertedFrom":"calendar_create","duplicateOf":…,"reason":"The event already exists and the capture adds nothing to it"}`; the item resolves. A recurring occurrence as the one duplicate goes to Human Review with "Recurring events are changed in the Calendar.";
- several: Human Review with those events as candidates, the planned `calendar_create` as the proposed action, and "This looks like an event that already exists: choose it to update it". Approving one runs the create as the update of that event (the processor reads it with `calendar_get`; nothing is searched or planned again); discarding the item creates nothing.

Events the filter leaves out (feed events, and Google events, which are managed by their source) are never duplicates, so a capture of the same title and time still creates a Life OS event. A failed duplicate search is retried like any failed search, and nothing is created meanwhile.

**Priority.** `calendar_create` and `calendar_update` may carry `priority` (`low`, `medium`, or `high`; the processor refuses any other value as an invalid plan). The plan prompt asks for it only when the item says how important the event is: `high` for important or urgent ("important", "urgent", "wichtig", "важно"), `low` for not important or low priority; otherwise it is left out, so a new event is medium and an update keeps the event's priority. "Das Visum-Gespräch ist wichtig" is a `calendar_update` of the one matching event with only `priority: "high"`. The event's priority becomes the importance of its reminder notifications.

**Resolution.** For each term the processor calls `calendar_search` with `from` set to the start of the capture's day in its timezone (the capture's own, else `LIFE_OS_TIMEZONE`), the same `timeZone`, `editable=true`, and `limit=10`, and unions the events by id. Calendar leaves cancelled events out, so only active events the AI may change from that day on are candidates: Life OS events and, since two-way Google sync (P11-03), Google events of calendars the owner may edit, which Calendar changes like Life OS events while the google-calendar integration writes the change to Google within seconds (a single one is changed like a Life OS event; a recurring one only in the Calendar, see below). Feed (ICS) events, Google calendars the owner can only read, and occurrences of Google rules Calendar cannot hold are managed by their source and are never candidates; last year's appointment of the same name does not make a capture ambiguous. A recurring event is found as one occurrence (the search item carries `occurrence`), its next one not over yet, so there is at most one candidate per series. Then:
- exactly one event and `calendar_update`: the processor calls `calendar_update` with that `eventId` and the changes. When the plan gives only a new start, it keeps the event's length (a timed event's duration, an all-day event's number of days); making an event all-day with only a start date makes it that one day. Planned `reminders` **add** to the event's own ("remind me 2 hours before" keeps the day-before reminder it has): the processor sends the event's own reminders (from the search result, or for an approved update from `calendar_get`) followed by the new ones it lacks, each once, since the MCP tool replaces the list. Only a plan that also names `reminders` in `clear` replaces them (the item asks to remove or replace its reminders, such as "only remind me 2 hours before"; the plan prompt says so in one clause); the processor then sends just the new ones and drops `reminders` from `clear`. A plan whose reminders the event already has sends only its other changes, or when there are none calls nothing and records `{"tool":"none","plannedTool":"calendar_update","eventId":…,"reason":"The event already has these reminders, so nothing changed"}`, and the item resolves;
- several events: Human Review listing them (at most ten), and nothing changes;
- no event: Human Review with no candidates; nothing is created as a fallback;
- `calendar_cancel`: **always** Human Review, even with exactly one match, which is then the only candidate. Nothing is cancelled until the owner approves.

**Recurring events.** The owner decided that recurring events are made and changed only in the Calendar, and that the AI may only skip one occurrence when asked ("Cancel gym today" cancels just today's gym). So:
- a planned `calendar_create` or `calendar_update` that carries a `recurrence` goes to Human Review ("Recurring events are created in the Calendar." or "Recurring events are changed in the Calendar.") and changes nothing; the plan prompt asks Codex to answer a request for a new repeating event with no action and that reason;
- a `calendar_update` whose one match is a recurring event goes to Human Review with no candidates and "Recurring events are changed in the Calendar.", and changes nothing (also when the plan was uncertain); an approved update of an event that turns out to recur (the processor reads it with `calendar_get`) is refused the same way;
- `calendar_cancel` may carry `onDate`, the ISO date of the day the item names ("today" is the capture's local date). Then the processor first searches each term with `from`/`to` set to that local day and takes only recurring occurrences from it, so a recurring match stands for its occurrence on that day; a series without an occurrence that day stands for its next occurrence (the usual search), and so does every recurring match without `onDate`. Single events are found as before. The candidate's title names the occurrence's date (`Gym · Sat 10 Oct 2026 07:00–08:00`) and it carries `recurrenceId`. Because Inbox keeps only the chosen candidate's id (the series id), the proposed action stores `occurrences`, a map from series id to recurrence id (a map the plan brought is replaced). On approval the processor passes the chosen series' recurrence id to `calendar_cancel` as `recurrenceId`, so only that occurrence is skipped, never the series. An approved cancellation of a recurring event without a recorded occurrence (for example from a review made before this) is refused with "Recurring events are changed in the Calendar.".

**Reschedules across domains.** Codex sometimes plans a reschedule for the wrong domain, such as `calendar_update` for "Move the electrician call to 2026-10-21" while "Call the electrician" is a Task. When a `calendar_update` that sets a new start finds no event, the processor searches open Tasks with the same terms; exactly one match runs the equivalent `task_update` (`dueAt` is `startAt` as given, or for a `startDate` the owner-local midnight of that date, like a date-only Task; title and description/notes carry over, event-only fields are dropped). Symmetrically, a `task_update` that sets `dueAt` and finds no open Task searches manual events, and exactly one match runs the equivalent `calendar_update` (an all-day event gets the date; a `dueAt` at the owner-local midnight is a date-only due date, so a timed event moves to that date at its original local time of day, also across a daylight-saving change; the event keeps its length). A planned or approved `calendar_update` that gives only a `startDate` for a timed event is completed the same way. Several matches in the other domain go to Human Review with those candidates and the equivalent action, so approving one runs it; nothing in either domain goes to Human Review with the plan as given ("No open Task or upcoming Calendar event matches…"). The planned domain is always searched first and wins when it matches. Cancellations, completions, reopenings, and changes without a new time never cross domains.

A low-confidence or ambiguous plan with one Task or Calendar change also goes to Human Review with the matching Tasks or events (after the same fallback). If Calendar still refuses a change with `409` `managed_by_source` (for example an approved action on a feed event, or on a Google calendar that became read-only), the item goes to Human Review with no candidates and "This event is managed by its source and can't be changed by capture", never to a technical retry. Calendar calls no provider, so a change never fails because Google is unreachable: the integration writes it to Google afterwards and keeps Google's version if the event changed there meanwhile (the processor stopped matching Calendar's former `google_*` error codes in P11-09). A failed search is retried like any failed action; a partial result is never acted on. Updates and cancellations carry no idempotency key: a retried `PATCH` with the same fields leaves the event the same. As for Tasks, when one action of a plan goes to Human Review, the actions before it have already run and the ones after it do not.

**Human Review.** It uses the existing Inbox mechanism unchanged: the proposed action (with its search terms and changes) and the candidates are stored on the item. A Calendar candidate carries the event's `id`, `kind: "calendar_event"`, the event's own title as `eventTitle`, its times, location, and status, and a `title` the Dashboard shows, saying when (in the owner's timezone) and where: `Dentist · Fri 16 Oct 2026 15:00–16:00 · Dr. Weber`. The `errorSummary` says what waits, for example "Cancelling a Calendar event needs your approval: choose the event to cancel it" or "Several Calendar events match: choose the one to change". Choosing a candidate (`POST /v1/inbox-items/{id}/human-review/resolve`) queues the item again with the approved action, in which Inbox records the chosen candidate as `taskId`, its one selection field. The processor then runs that action on that event without planning or searching again: it takes the id as `eventId`, drops the search terms, and for an update that gives only a new start reads the event (`calendar_get`) to keep its length.

`make calendar-ai-smoke` proves this with the real Codex CLI on the verification stack, with `LIFE_OS_TIMEZONE=Europe/Berlin`:
- "Add dentist at Dr. Weber, Friday 15:00 for an hour" creates one event, 15:00–16:00 Berlin on the next Friday (Monday when run on a Friday), with location Dr. Weber;
- "Move the dentist appointment to next Monday at 9" updates that event (by id) to 09:00 Berlin on the coming Monday (or the one after), still one hour, same title and location, and creates nothing;
- "Cancel the dentist appointment" goes to Human Review with that event as the only candidate, and it stays active; approving it through the Inbox API cancels exactly that event, which stays readable with `cancelledAt`;
- with a 90-minute event titled "Zahnarzt", the English "Move my dentist appointment to the day after tomorrow at 11:30" moves it to 11:30–13:00 Berlin two days after capture;
- with "Team meeting" and "Meeting with Anna", "Move my meeting to Thursday at 14:00" goes to Human Review with both as candidates, and neither changes;
- with the owner's 30-minute default, "Add a haircut … remind me a day before and 3 hours before" gives the new event those two reminders of its own on top of the default;
- with a weekly "Gym" series that has an occurrence today, "Cancel gym today" goes to Human Review with exactly today's occurrence (its `recurrenceId` recorded in the proposed action); approving it cancels only that occurrence, while next week's and the series stay active;
- "Tomorrow at 19:00 dinner with Anna for two hours." and then "Tomorrow at 19:00 dinner with Anna, remind me two hours before." leave exactly one dinner with Anna, 19:00–21:00 Berlin, with a 120-minute reminder of its own: the second capture is resolved by one `calendar_update` of the first event;
- no other event is created.

Writes in the smoke are sent as `X-Life-OS-Actor: dev:smoke-calendar-ai`. The Calendar image must include the P10-01 search API.

## Task and event details and moves

The owning services store instants in UTC, and a date-only Task is the owner-local midnight, so a raw `dueAt` of `2026-10-22T22:00:00Z` means "Friday 23 October, no time" in Berlin. MCP therefore answers every Task and event with its details on the owner's clock, and moves them relative to the time they have, so a caller (Codex, or an MCP client the owner talks to) never converts offsets or does daylight-saving arithmetic. The owner's clock is `LIFE_OS_TIMEZONE` (compose passes it to `mcp`; default UTC; an unknown name falls back to UTC and is logged at startup); a call may name another IANA zone (`timeZone`).

**Task details.** `task_get` (new: `GET /v1/tasks/{id}`, the `taskId` must be a UUID), `task_list`, `task_search`, and the Task every write answers carry the Task as Tasks returns it plus:
- `due`: `null` when unscheduled; else `date`, `weekday`, `hasTime`, `text` ("Mon 19 Oct 2026, 15:30 CEST" or "Fri 23 Oct 2026 (no time)"), and for a Task with a time also `time` ("15:30"), `local` (RFC 3339 with the owner's offset), and `utc`; for an open Task `overdue` (a date-only Task from the next day on, a timed one once its time has passed). Date-only follows the rule of Tasks and the Dashboard: the owner-local midnight, or a UTC midnight on the same calendar day for the owner;
- `timeZone`, `createdAtLocal`, `updatedAtLocal`, `completedAtLocal`, `recurring`, and `recurrenceText` ("every 2 weeks"); `notes` and `recurrence` are Tasks' own. Tasks keep no source or link: a Task does not say which capture made it.

**Event details.** `calendar_get` (with an optional `recurrenceId` it reads one occurrence, `GET /v1/events/{id}/occurrences/{recurrenceId}`), `calendar_list`, `calendar_search`, and the event every write answers carry Calendar's event (location, description, reminders and `effectiveReminders`, priority, status, source, `occurrence`, `recurrence`) plus `timeZone` (the query's `timeZone` for a list or search that names one, else the owner's), `start` and `end` (a timed event's `date`, `weekday`, `time`, `local`, `utc`, `text`, the end exclusive; an all-day event's dates, the end its last day), `durationMinutes` or `days`, `when` ("Fri 23 Oct 2026, 15:00–16:00 CEST", "Sat 24 Oct 2026 (all day)"), `recurring`, and `recurrenceText` ("every week on TU, SA, until Fri 1 Jan 2027").

**Moves.** `task_update` and `calendar_update` take `move` instead of new times (`dueAt`/`clearDueAt`, or `allDay`/`startAt`/`endAt`/`startDate`/`endDate`; giving both is refused). MCP reads the Task or event, works the new time out, and sends it to the same `PATCH` the Dashboard uses, with the update's other fields (a rename and a move are one write):

| `move` | Meaning |
| --- | --- |
| `{"toDate": "2026-10-17"}` | To that date at the time it has: "to tomorrow, same time", "to Friday" (the caller resolves the date) |
| `{"days": 2}` | Two days later at the same time, from its current date (negative: earlier) |
| `{"hours": 1}`, `{"minutes": 30}` | That much later in real time (negative: earlier); 23:30 plus an hour is 00:30 the next day |
| `{"toDate": "2026-10-30", "toTime": "09:00"}` | To that date and time |
| `{"toTime": "18:00"}` | To that time on its date (or with `days`, on the moved date) |
| `{"dateOnly": true}` | Tasks only: keep the date (or `toDate`), drop the time |
| `"timeZone": "Europe/Berlin"` | The zone the dates and times mean; default the owner's |

The day changes first (`days` or `toDate`), then the time of day (`toTime`, else the one it had), then `hours` and `minutes` are added. So days keep the wall-clock time across a daylight-saving change (Saturday 24 October 2026 10:00 CEST plus a day is Sunday 10:00 CET, 25 hours later), while hours are elapsed time (01:30 CEST on Sunday 25 October plus two hours is 02:30 CET). A wall-clock time that does not exist that day is read with the offset before the gap (02:30 on 29 March 2026 is 03:30 CEST), and one that occurs twice is the first, as in iCalendar (RFC 5545). A Task without a time keeps having none (moving it by days or to a date keeps it date-only) unless `toTime` gives one; an unscheduled Task needs `toDate`. A timed event keeps its length in real time, an all-day event its number of days. A recurring event moves only one occurrence, with its `recurrenceId` (from `calendar_search` or `calendar_list`) and nothing else in the call: `PATCH /v1/events/{id}/occurrences/{recurrenceId}` (This event); without one it is refused, since the series is changed only in the Calendar. A move that changes nothing is refused before anything is read, as are `days` with `toDate`, `toTime` with `hours` or `minutes`, `dateOnly` with a time, malformed dates (`YYYY-MM-DD`) and times (`HH:MM`), more than ten years of days or a year of hours, and an unknown zone. A move that does not fit what it found is refused with a reason starting `cannot move:` and nothing is written: hours for a Task without a time ("“Renew passport” is due on Fri 23 Oct 2026 without a time, so it cannot move by hours or minutes: name the time (move.toTime)"), days or hours for an unscheduled Task, a time for an all-day event, `dateOnly` for an event, a series without `recurrenceId`, or `recurrenceId` for an event that does not repeat. A move to the time it already has writes nothing and answers `moved.unchanged`. The answer is the Task or event with its details and `moved`: `from` and `to` in words ("Sat 24 Oct 2026, 10:00 CEST" → "Sun 25 Oct 2026, 10:00 CET").

**Planning.** Codex never sees the existing Tasks and events, so before this it could not keep or shift a time the capture does not say: "move the dentist task to tomorrow, same time" lost the time or was guessed. A separate clause of the plan prompt (`movePrompt` in `internal/processor/moves.go`, after `planPrompt`) offers `move` for `task_update` and `calendar_update` when the item keeps or shifts the time something has: "Move the dentist task to tomorrow, same time" is `{"toDate": <tomorrow>}`, "push the meeting an hour later" `{"hours": 1}`, "postpone the report by two days" `{"days": 2}`, "move the electrician call to Friday" `{"toDate": <the coming Friday>}` (which keeps its time), and "remove the time from the passport task" `{"dateOnly": true}`; a new date and time may be `toDate` with `toTime` or `dueAt`/`startAt` as before. The processor then:
- accepts `move` only as an object of those fields with whole numbers, strings, and a boolean, never with a new time beside it (else the plan is invalid); a `null` move is left out;
- finds the Task or event as for any change, and sends its id with the move, adding the capture's timezone (the browser's, else `LIFE_OS_TIMEZONE`) as `move.timeZone`; MCP works the time out, so an event keeps its length without the processor reading it;
- runs a plan's moves after its other actions: a move is relative, so unlike an absolute change it is not the same when run twice, and a retry after a later action failed would otherwise move again (a failure after the move, such as recording the attempt, can still repeat it on the retry);
- sends a move MCP refuses (`cannot move:`) to Human Review with the reason, without the tool hints and with "Nothing was changed." ("“Renew passport” is due on Fri 23 Oct 2026 without a time, so it cannot move by hours or minutes: name the time. Nothing was changed."), never to a technical retry;
- carries a move across domains like a reschedule ("push the electrician call an hour later" planned as `calendar_update` moves the one matching Task);
- still sends a change of a recurring event to Human Review ("Recurring events are changed in the Calendar."): the owner's rule that the AI only skips occurrences stands for captures, while an MCP client may move one occurrence.

A capture cannot answer: the clause asks Codex to answer a question about a Task or event ("when is the dentist call due?") with no action and "Questions are not answered by capture: see the Tasks or Calendar view.", which goes to Human Review; an MCP client asks `task_get` or `task_search` instead.

`go test ./cmd/server` covers the details (timed, date-only, also as a UTC midnight, overdue, unscheduled, completed; timed, overnight, all-day, and recurring events) and every move: tomorrow at the same time, days, hours, minutes, a date and time, a time alone, dropping the time, 23:30 plus an hour past midnight, the change to winter time on Sunday 25 October 2026 (a day keeps 10:00, hours are elapsed time, a time that occurs twice), the missing hour on 29 March 2026, date-only and unscheduled Tasks, another zone, events keeping their length (timed, across the change, all-day), one occurrence of a recurring event moved through the occurrence API while the series is refused, refusals, and the validation, through the MCP tools against fake Tasks and Calendar APIs. `go test ./internal/processor` covers the plan validation, the capture's timezone, the event move without a computed end, the recurring refusal, the cross-domain carry, a refused move going to Human Review, the order, and the prompt clause. `tools/benchmark-ai-runtime` has four cases (see [AI runtime benchmark](../verification/ai-runtime-benchmark.md)).

## Processor status

The processor's private health port (`8081`, not exposed through the gateway) serves `/health`, `/ready`, and `/status`. Like `/health` and `/ready`, `/status` is an operational endpoint outside the OpenAPI contracts. It holds what the running process has observed since it started, in memory, and resets on restart:

```json
{
  "model": "gpt-5.6-luna",
  "timeZone": "Europe/Berlin",
  "startedAt": "…",
  "poll": {"lastAt": "…", "lastSucceededAt": "…", "lastError": "…"},
  "codex": {
    "state": "ready | usage_limited | unauthenticated | failing | unknown",
    "authenticated": true,
    "authCheckedAt": "…",
    "lastSucceededAt": "…",
    "lastFailedAt": "…",
    "lastError": "ERROR: You've hit your usage limit… try again at 6:22 PM.",
    "consecutiveFailures": 3
  }
}
```

- `authenticated` comes from `codex login status`, checked at startup and every five minutes. It reads local credentials only and uses no model quota.
- `state` is derived as follows:
  - `unauthenticated` when the login check fails;
  - otherwise, after a failed planning run, the failure is classified: `usage_limited` (usage or rate limit), `unauthenticated` (401 or not logged in), or `failing` (anything else);
  - otherwise `ready` after a successful run, or `unknown` when Codex has not run yet.
- `timeZone` is the processor's configured timezone (`LIFE_OS_TIMEZONE`), which captures without their own browser timezone are planned in (see [Dates and the owner's timezone](#dates-and-the-owners-timezone)).
- `ideas` is the recipe ideas job (see [Recipe ideas](#recipe-ideas)).
- `categories` is the AI categories job (see [AI categories](#ai-categories)).
- `budgetPlans` is the AI budget plan job (see [AI budget plans](#ai-budget-plans)).
- The Dashboard Status page (`/status`) renders this, together with the Inbox and Voice backlogs.

### Codex usage and reset information

**Data source.** The processor starts `codex app-server` (stdio JSON-RPC) every five minutes and calls two methods of the Codex CLI's own app-server protocol: `account/read` and `account/rateLimits/read`. Their schema is published by `codex app-server generate-json-schema`, and they are the same data the Codex apps use to show usage. The calls use no model quota. The result appears under `usage.current` on `/status`, and `processor --usage` prints it for diagnostics.

**Reported fields:**
- auth mode, for example `chatgpt` for a subscription sign-in;
- plan, for example `plus`;
- one entry per metered bucket. For example, `codex` with a 5-hour and a weekly window, and a separate `gpt-reserve` bucket. Each window has a used percentage, a window length, and a reset time;
- whether the backend reports a bucket's limit as reached;
- how many one-off "full reset" credits the account has.

The account email is never stored.

**Reliability and limits:**
- The percentages and reset times are the backend's own numbers, shown unchanged; Life OS never estimates them.
- Codex marks the app-server protocol as experimental, so a future CLI version may change it. Today's response shape is pinned in `usage_test.go`, using a real Codex CLI 0.160.0 response.
- The usage is a snapshot that can be up to five minutes old (`usage.current.checkedAt`).
- The response does not say which bucket a given model draws from. For example, the `gpt-reserve` bucket lists `gpt-5.6-luna` as its normal model, while `gpt-5.6-luna` may also count against `codex`. The Dashboard therefore lists every bucket rather than guessing which one applies.
- Reset credits are only counted. Life OS never spends them.

**Fallback.** If a read fails (an older CLI, an unsupported account, or an app-server error), `usage.error` is set and the last good snapshot, if any, is kept with its timestamp. With no snapshot, the Dashboard shows "Codex usage: unavailable" and still relies on the classified `usage_limited` state from failed runs, together with Codex's own "try again at …" text.

The Status page lists these values under Automatic processing. When Codex is usage-limited and a bucket is reported as reached or at 100%, the suggested action names that bucket's reset time.

A failed Codex run keeps only the CLI's own `ERROR:` lines, without the transport retry lines (`Reconnecting… n/5`), in its error and in the Inbox attempt's `errorSummary`. The full output echoes the banner and the prompt, including the user's capture. That buried the actual reason, such as a usage limit, behind text that was then truncated.

If the MCP service restarts, it forgets every session. On the resulting `404`, the processor starts a new MCP session and retries the rejected call once, which the Streamable HTTP transport requires. The rejected request was never processed. Previously the processor kept its stale session and failed every poll until it was restarted itself.

## Dates and the owner's timezone

Each capture is planned in the owner's timezone at the moment of capture: the capturing browser's timezone when the capture names one, else `LIFE_OS_TIMEZONE`, else UTC. The Dashboard's text and voice captures send the browser's IANA zone as `sourceMetadata.timeZone` (the Voice worker carries the upload's `sourceMetadata` over to the Inbox item). The processor uses it when `time.LoadLocation` accepts it (and it is not `Local`); an unknown or missing zone falls back to the configured one, so captures from the Watch, scripts, or MCP clients without metadata keep working as before.

`LIFE_OS_TIMEZONE` (an IANA name such as `Europe/Berlin`; default `UTC`) is the configured fallback. Compose passes it to the processor and also sets the processor's `TZ` to it. Compose passes it to `mcp` too, whose Task and event tools show times and move them on that clock (see [Task and event details and moves](#task-and-event-details-and-moves)); the MCP binary embeds `time/tzdata`. The processor validates it with `time.LoadLocation` at startup; an unknown name is logged and falls back to UTC (as in the Dashboard) rather than stopping capture processing. The processor binary embeds `time/tzdata` and the image installs `tzdata`, so any zone resolves both for the processor and for the Codex CLI.

Every planning prompt states the capture's zone and the local date, time, and weekday, lists the coming seven days with their weekdays and UTC offsets (which covers a daylight-saving change), and gives a worked example ("tomorrow at 10:00 is 2026-10-11T10:00:00+02:00"). Codex is told to:
- resolve "today", "tomorrow", "tonight", "this/next week", and bare clock times in the owner's timezone;
- read a weekday ("on Friday") as its next occurrence that is not already past;
- write `dueAt`, `startAt`, and `endAt` as RFC3339 with the owner's UTC offset on that date, and `startDate`, `endDate`, `occurredOn`, `expiresOn`, and a meal's `date` as the owner's local date.

Relative dates mean what they meant when the owner captured the item, so the reference is the Inbox item's `createdAt`, not the moment Codex runs. A capture taken at 23:59 and planned just after midnight, or retried hours later after a usage limit, keeps its "tomorrow". When planning is more than ten minutes late, the prompt also states the current time. Every Codex run gets `TZ` set to the zone it uses (a planning run the capture's zone; `login status` and usage reads the configured one), so Codex's own environment context agrees with the prompt. The owning services store instants, so an offset time and its UTC equivalent are the same value. `--content` diagnostics have no capture time and use the current time.

`make relative-dates-smoke` proves this with the real Codex CLI on the verification stack, with `LIFE_OS_TIMEZONE=Europe/Berlin`:
- the processor reports the zone on `/status`, and its container resolves it (tzdata);
- "Remind me to call mom tomorrow at 10." creates a Task due at 10:00 Berlin time on the day after capture;
- "dentist on Friday at 15:00 for one hour" creates a 15:00–16:00 Berlin event on the next Friday (Monday when run on a Friday, which would be ambiguous);
- "Anna's birthday the day after tomorrow" creates an all-day event on the Berlin date two days after capture.

Expectations are computed with `TZ=Europe/Berlin date` from each item's own `createdAt`.

## Recent captures

The owner often corrects or adds to what they captured a minute ago: "Buy milk", then "actually oat milk"; "Meeting with Anna at 5", then "make it 6"; "Remind me to call Anna", then "make it tomorrow morning"; "add bread too". The processor therefore plans each capture with the owner's captures from just before it (P5-20, `internal/processor/recent.go`):

- **Reading.** Before Codex runs, the runner reads the captures made in the `INBOX_CONTEXT_MINUTES` (`.env` `LIFE_OS_INBOX_CONTEXT_MINUTES`, default 20, at most 120; 0 turns it off) before the capture's own creation, through MCP `inbox_recent_captures` (Inbox `GET /v1/recent-captures`, see [Inbox → Recent captures](inbox.md#recent-captures)): at most 10, from every source, only settled ones (resolved, waiting for Human Review, or failed), never the capture itself, raw or processing ones, or discarded ones; the same read names the raw and processing ones apart (`unfinished`, see Order below). The read comes first, before the attempt starts. When they cannot be read, the capture is retried later (a dependency failure), as for its images: planned without them, a follow-up would duplicate what they did. An approved Human Review action runs without Codex; it reads them only to link what it changes (below).
- **Order (P5-22).** Each poll takes the due captures oldest first (`inbox_list` with `order=oldest`, so a backlog of more than the page of 50 is planned as it was captured) and plans them one at a time, so a follow-up is planned after the capture it follows and sees what was done for it. One at a time is not enough on its own: when an earlier capture's attempt ends retryable, it waits for its retry while the poll goes on, and a capture still `processing` (a processor that stopped) is not finished either; a follow-up planned then finds no trace of it (only finished captures are listed) and may change whatever was done last instead. So a capture is planned only after every capture of its context window has finished (resolved, waiting for Human Review, failed, or discarded). The same `inbox_recent_captures` read names the window's unfinished ones (`unfinished`, see [Inbox → Recent captures](inbox.md#recent-captures)), so waiting costs no extra read and no Codex run. A capture that waits is left `raw`, without an attempt, and the poll goes on with the next one; a later capture within the window of one that waits waits too, without a read; the next poll looks again (`internal/processor/order.go`). The wait is bounded by `LIFE_OS_PROCESSOR_STALE_AFTER_SECONDS` (default 120 s, counted from the first poll it waited in, in the processor's memory): after it the capture is planned anyway, Codex sees the unfinished captures in the list (state `raw` or `processing`, "still on its way, nothing done yet"), and the processor logs it and records it on the processed attempt's `errorSummary` ("planned without waiting longer: 1 earlier capture still on the way after 2m0s: 17:09:50 “Coffee with Lukas tomorrow at 5 pm.” (raw, retry at 17:10:20)"). The first poll a capture waits in is logged too. An approved Human Review action, which runs without Codex, never waits; with `INBOX_CONTEXT_MINUTES` 0 nothing does.
- **What Codex sees.** A section "Recent captures (context only)" after the owner's time and before the item, only when there are any (a capture without recent ones gets the prompt it always had). Each capture, oldest first, is one JSON object: when it was captured (owner's time) and how many minutes before the item, its source, its text (at most 300 characters), its state, and `done`, what its processed attempt created or changed, read from the recorded actions and the owning services' results: the entity (`task`, `event`, `shopping_item`, `pantry_item`, `transaction`, `meal`, `staple`, `recipe`), its id, the change (`created`, `updated`, `added`, `merged`, `bought`, `completed`, `cancelled`, …), and a summary of at most 120 characters ("Call Sophie · due Sat 2026-10-17 09:00", "Coffee with Lukas · Sat 17 Oct 2026 17:00–18:00", "Milch"); at most 8 entities each. A capture waiting for review says so with its reason, a failed one that nothing was done, one resolved by hand that the owner resolved it, and one still on its way (only after the wait above) that nothing is done yet. The list is at most 6,000 characters; the oldest captures are left out first.
- **The rules.** The list is context only: Codex uses it to understand what the item refers to or corrects, and never plans an earlier capture's action again. When the item clearly corrects, changes, or undoes something a recent capture did, Codex changes that entity instead of creating another: a Task with `task_update` (or `task_complete`, `task_reopen`) and `taskId`, an event with `calendar_update` or `calendar_cancel` and `eventId`, a list item with `food_update_shopping_item` and `shoppingItemId` (its `name`, `amount`, `note`, or `storeName`), each with only what changes. Something new that continues the topic ("add bread too") is a new action. A change of something with no change tool here (a transaction, a meal, a pantry item, a staple, a recipe, deleting a Task) or of what a capture still on its way asks for, or one where it is unclear whether or which recent entity is meant, goes to Human Review with Codex's reason. An unrelated item is planned as if the list were not there.
- **Ids.** A planned change may name its target by id only when that id is one the list showed, for an entity of that kind; any other id makes the plan invalid (a model-output retry), also without recent captures, so Codex can never act on a guessed id. A named Task keeps its `taskId` (no search); a named event is read (`calendar_get`) and changed only while active and not recurring, and a cancellation still waits for the owner's approval with that event as the candidate; a named list item is changed directly. When Codex gives no search terms, the entity's title or name becomes them, so an action sent to Human Review stays valid when approved. A change Codex is unsure about (ambiguous or below 0.8) goes to Human Review with that one entity as the candidate. Food refusing a rename because another needed item has the new name (`already_on_list`), or the item being gone, goes to Human Review rather than a retry.
- **Audit and Activity.** The new capture's actions are recorded as usual, with the same idempotency keys (a rename's Food key covers the item and the new name). Every change whose target a listed capture created or changed (however the target was found, by id or by search) carries `followsUp` (`inboxItemId` of the latest such capture, `entity`, `entityId`) in its audit entry; Inbox records `inbox.item.followed_up` about that capture in the follow-up's workflow, so the Event Log links the two (see [Inbox → Recent captures](inbox.md#recent-captures)). The owning service's own change event (`task.updated`, `calendar.event.rescheduled`, `food.shopping_item.updated`) has the entity as its subject, so it also shows next to the earlier capture's `task.created` under the same subject.

Tests (`recent_test.go`, with a fake Codex and fake MCP tools): the list is built oldest first, without the item, capped at 10 captures, 8 entities, and 6,000 characters (the oldest left out), with texts clipped, review and failure notes, and each tool's entities; the runner reads the right window, gives Codex the section (and nothing when off), retries when it cannot read them, and the dry run plans with them; the prompt has the section between the owner's time and the item, and is unchanged without recent captures; a rename, a move (keeping the event's length), and a reschedule by id run as updates without a search or a new entity and are linked, and so is an approved cancellation of a recent capture's event; a change found by search is linked too, a new item next to them is not; an id the list did not show, of another kind, or on another tool is invalid; a cancellation, an unsure change, a cancelled event, and a name already on the list go to Human Review; polled captures are planned oldest first; `INBOX_CONTEXT_MINUTES` is read and checked. `order_test.go`: the poll asks for the oldest first; a capture behind one still on its way waits (no attempt, no Codex run, logged once, one read per poll) and is planned with what it did once that one is done; after the bound it is planned anyway, with the unfinished capture in Codex's list, the note on the attempt, and a log line; a later capture of the window waits without a read, one outside it is planned, an approved action runs, and a later capture whose own wait is over is read and planned; without an order or with the context off nothing waits; and a capture that stopped coming up is forgotten, and the default bound is two minutes. The AI runtime benchmark has four follow-up pairs (see [AI runtime benchmark](../verification/ai-runtime-benchmark.md)).

## Retry scheduling

The processor polls only due work (`inbox_list` with `state=raw&due=true`). It classifies each failure and asks Inbox to persist when the item may be retried (`nextRetryAt`, `retryReason`):

| Failure | Example | Next attempt |
| --- | --- | --- |
| Codex usage limit | `ERROR: You've hit your usage limit…` | At the reset time the Codex CLI reports for the exhausted bucket (`account/rateLimits/read`, read fresh and cached for a minute), plus up to a minute of jitter. Reason `usage_limited`. Without a reported reset, it backs off. |
| Other Codex failure | sign-in, transport, CLI error | Backoff. |
| Dependency unavailable | MCP or an owning service unreachable | Backoff. |
| Unusable model output | invalid JSON, a disallowed tool, an action the owning service rejects | Backoff. After 5 attempts the item becomes `failed` (operator attention). |
| Ambiguous, low confidence, or nothing to do | a quotation, an unclear request | Human Review. Never a technical retry. |

Backoff is 30 s, doubling per earlier attempt of the item, capped at one hour, with ±20% jitter. Reason `backoff`. A retry adds an audit attempt; it never repeats a processed operation. Retry-After headers and explicit recovery intervals are not exposed by the current dependencies, so the only explicit recovery time used today is the Codex usage reset. A nothing-to-do capture appears in the Human Review queue with Codex's reason and no candidates; the user can discard it there, or capture it again with more detail.

`make retry-schedule-smoke` proves the following on the verification stack, with real Inbox, MCP, processor, Codex, and Tasks:
- ambiguity goes to Human Review;
- no retry happens before a reported reset, even across a processor and Inbox restart;
- the work completes after the reset;
- backoff runs 30 s, then 60 s.

A usage limit cannot be triggered on demand, so `tools/fixtures/codex-limit-simulator` simulates one at the Codex CLI boundary for that smoke only.

## Codex runtime

The routine planning profile is `gpt-5.6-luna` with reasoning effort `medium` (`LIFE_OS_CODEX_MODEL`, `LIFE_OS_CODEX_REASONING_EFFORT`), chosen by the [AI runtime benchmark](../verification/ai-runtime-benchmark.md). The effort is passed to Codex as `-c model_reasoning_effort=…`; empty keeps the Codex configuration's default. Attempts record the profile as `model/effort`, and `/status` reports the effort and the token usage Codex reports per run.

Codex is the processor's agent runtime. It runs as a managed subprocess of the machine's existing ChatGPT sign-in, with no API key (`internal/processor/codex.go`). Every planning run gets:

- **Binary.** `LIFE_OS_CODEX_COMMAND` is resolved once at startup. A missing CLI stops the processor with exit code 78.
- **Working directory.** The explicit `LIFE_OS_CODEX_WORKDIR`, in a read-only sandbox (`-s read-only`).
- **Environment.** Only `PATH`, `HOME`, `USER`, `CODEX_HOME`, locale, `TZ` (the capture's timezone when it names one, else the configured one), `TMPDIR`, and CA settings. API keys, service URLs, and other secrets are never inherited.
- **MCP servers.** None: `-c mcp_servers={}` ignores servers in the host Codex config.
- **Process group.** Each run has its own process group, so nothing it starts can outlive it.
- **Deadline.** `LIFE_OS_CODEX_TIMEOUT_SECONDS` (default 300).
- **Cancellation.** Graceful: `SIGTERM` to the group, then `SIGKILL` after 5 s. The whole group is killed after every run.
- **Concurrency.** At most `LIFE_OS_CODEX_MAX_CONCURRENCY` runs at once (default 1).
- **Structured output.** `--json` events give the Codex session id (`thread.started`) and the failure reason (`turn.failed`). `-o` captures the final plan.
- **Images.** A capture's photos, as files with `--image` (see [Images](#images)).
- **Web search.** Off for capture planning, the AI categories job, and the AI budget plan job (`-c web_search="disabled"`, whatever the copied Codex configuration says); only the recipe ideas job may search, with `LIFE_OS_IDEAS_WEB_SEARCH` (see [Recipe ideas](#recipe-ideas)). The ideas, AI categories, and AI budget plan runs answer to a JSON Schema (`--output-schema`, a temporary file removed with the run).

### Images

A capture can carry photos ([Inbox → Capture images](inbox.md#capture-images)): shared to Life OS from the phone, or attached in the composer. Codex reads them with the capture's text (`internal/processor/images.go`):

- **Reading.** Before planning, the runner reads the capture's `mediaReferences` from Inbox on the private network (`GET /v1/media/{sha256}` at `INBOX_SERVICE_URL`, `http://inbox:8080`; 30 s per image). A run gets at most five images and 25 MiB in total; one Inbox no longer has, a non-image answer, or one beyond the limits is left out and counted. When Inbox cannot answer, the capture is retried later (a dependency failure) rather than planned without its photos. References that are not Inbox images are ignored, and a capture without images does not ask Inbox.
- **Handing them over.** `CodexCLI` writes them to a directory of its own inside `LIFE_OS_CODEX_WORKDIR` (`capture-images-…/image-1.jpg`, `image-2.png`, …; in Compose the workdir `/workspace` is a 128 MB tmpfs of the read-only processor container) and passes each with `--image <file>`, before `-o`, which ends the list ahead of the prompt. The directory is removed when the run ends, however it ends; the deadline, cancellation, and process-group handling are unchanged.
- **Prompt.** One line, only for a capture with images, just before the item: "The item comes with N attached image(s), which are part of the capture: read them together with its text.", plus how many could not be attached. The photos inform the same plan the text would get, with the rules for letters and receipts below.

- **Keys.** A capture's image references (content hashes) are part of its processing key, the base of its attempts' and actions' idempotency keys, since photo captures often share the composer's placeholder text "Photo"; a capture without images keeps the key it always had.

Tests: `images_test.go` checks the arguments and files a run gets (in the workdir, before `-o`, removed afterwards, the prompt line, none without images), the reading limits and failures, and that the runner plans with the images or retries when Inbox cannot give them.

### Letters and receipts

The owner lives in Germany and photographs paper letters (from authorities, insurers, the landlord, doctors; mostly in German) and receipts, shared from the phone or taken in the composer, often with no words (the text is then the composer's placeholder "Photo" or "2 photos", which the plan prompt treats as no text) or a short note such as "handle this" or "разберись". The plan prompt (P16-03) tells Codex, for images that show a document:
- **A letter with a deadline** ("bis zum 30.10.2026", "innerhalb von 14 Tagen ab Zugang", Frist, Zahlungsziel) is `task_create` due that day (00:00 in the owner's timezone unless the letter names a time), titled with the sender as printed and the action, in the language of the capture's text, else English ("Finanzamt: send tax documents"). Its notes are 2 to 4 short lines: what the letter is about, its reference numbers (Aktenzeichen, Steuernummer, Kundennummer, Rechnungsnummer), any amount, and for a relative deadline whether it counts from the letter's printed date or, without one, from the capture date.
- **An appointment** (Termin with a date, a time, and a place) is `calendar_create` with the place as `location`; a letter with both is both actions.
- **A bill** (Rechnung with an amount, an IBAN, and a due date) is `task_create` "Pay <sender> <amount>" due on the due date. Life OS never pays; payments stay manual.
- **A cash receipt** (Kassenbon showing BAR, Bargeld, or cash) is `finance_create_manual_transaction`: the total (SUMME) as the negative amount in cents, the receipt's currency, the merchant as `counterparty`, and `occurredOn` the receipt's date, in the Cash account (see [Finance](#finance)).
- **A card receipt** (EC, Karte, girocard, Visa, Mastercard, kontaktlos) is a card payment: no action, and Human Review with "Card and bank payments arrive from the bank connection.", since the bank connection brings it.
- **Anything unclear**, a document Codex cannot read or classify or one with nothing to do, goes to Human Review with a short description of it as the reason ("A letter from AOK with no deadline: what should I do with it?").
- **The capture's text steers** and wins over these defaults: "just save the deadline" plans only that Task, "это оплачено" leaves nothing to pay. Other photos (a handwritten note, a shopping list, a product) follow the usual rules for what they show.
- **Privacy.** A document's text is never copied into a title or notes: Codex summarizes and keeps only the key numbers.

The actions are the usual ones and validated as such; nothing else is image-specific. Receipts' items are not matched against the shopping list (that would mark items bought from abbreviated receipt lines, one list read per line, and fall back to Tasks; left out on purpose).

The [AI runtime benchmark](../verification/ai-runtime-benchmark.md) photographs three synthetic documents drawn by `tools/fixtures/documents` (a Finanzamt letter with a deadline, a REWE cash receipt, a girocard receipt), and `make processor-codex-actions-smoke` captures the cash receipt end to end: one −23.47 EUR REWE transaction on 10 October 2026 in the Cash account.

### Lifecycle

The Inbox processing attempt is the durable job record. It exists in Inbox before Codex is spawned, and moves through these runtime states:

`spawning` → `running` (with the Codex session id once reported) → `completed` / `failed` / `timed_out` / `cancelled`.

The processor heartbeats every 30 s until the attempt's outcome is stored. Outcomes are always stored, even during shutdown:

- **Normal stop (`SIGTERM`, for example `docker compose stop` or a redeploy).** The run is cancelled and the capture is handed back as retryable, with reason `cancelled`, due now. The processor has a 30 s stop grace period.
- **Timeout.** The run is stopped and the capture backs off, like any other Codex failure.
- **Crash (`SIGKILL`, OOM, host reboot).** The attempt keeps its last runtime state and stops heartbeating. Every 30 s, and at startup, the processor reconciles attempts that another instance owned and whose heartbeat is older than `LIFE_OS_PROCESSOR_STALE_AFTER_SECONDS` (default 120). They become retryable, with reason `recovered`, due now. This also recovers captures orphaned before runtime tracking existed.

**Resume.** `codex exec resume` requires a persisted session. The processor's Codex home is a tmpfs, runs are `--ephemeral`, and a crash loses the session anyway. Planning is a single read-only turn, so the safe fallback is to plan again. The recorded session id stays on the attempt for audit. Re-planning cannot duplicate a domain change: Codex never executes actions, and the processor sends every Task, Calendar, Finance, or Food create, and every Food change, with a deterministic idempotency key derived from the operation. Each instance gets a unique id (`runtimeOwner`), so reconciliation never takes over a run the current processor still owns.

`/status` reports the runtime under `runtime`:
- the instance, binary, timeout, and concurrency;
- the run in progress, with its state, session, and start time;
- counts of completed, failed, timed-out, cancelled, and recovered runs since start;
- the last reconciliation error.

`make codex-runtime-smoke` proves the lifecycle with the real Codex CLI on the verification stack:
- normal execution;
- the sanitized environment of a live run, read from `/proc`;
- cancellation when the processor stops mid-run;
- a 2 s deadline, leaving no Codex process behind;
- `SIGKILL` crashes, both before and after Codex reports its session, reconciled by the next processor.

Each scenario ends with exactly one Task. The real CLI reports its session within a fraction of a second, so the spawned-but-no-session window is held open by the smoke-only wrapper `tools/fixtures/codex-limit-simulator` (mode `slow-start`). It waits 45 s, then runs the real CLI.
