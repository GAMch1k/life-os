# Calendar service

Calendar owns events and calendar sources in `calendar_db` and is their only source of truth: clients (the Dashboard, MCP, the Inbox processor) use its API, never its database. Gateway base: `/api/calendar`. The contract is `services/calendar/api/openapi.yaml`; `/health` and `/ready` are available.

## Events

An event has a `title`, optional `description` (notes/details) and `location`, its time (below), optional `recurrence` and `reminders`, a `priority`, a `status`, and a `source`. Calendar Events are not Tasks.

**Time.** A timed event (`allDay: false`) has `startAt`/`endAt`, RFC 3339 instants: any offset is accepted, and they are stored and returned in UTC (`2026-11-17T09:30:00+01:00` comes back as `2026-11-17T08:30:00Z`); `endAt` must be after `startAt`. It may carry `timeZone`, the IANA zone it was scheduled in (for example an ICS `TZID`), as a display hint. An all-day event (`allDay: true`) has `startDate`/`endDate`, local dates with `endDate` inclusive (a one-day event has both equal; ICS and FullCalendar use an exclusive end, so adapters subtract or add a day). All-day dates mean those days in the owner's timezone and take no `timeZone`.

**Owner's timezone.** Reads that compare all-day dates with instants (listing, search) take a `timeZone` parameter and default to `LIFE_OS_TIMEZONE` (set for the Calendar container in `compose.yaml`; unset or unknown means UTC, logged at startup). An all-day event spans midnight of its first day to midnight after its last day in that zone, so daylight-saving changes are respected. The Dashboard passes the timezone it shows the owner.

**Status.** `active` or `cancelled`. Cancelling (`PATCH {"status":"cancelled"}`) keeps the event as history: it stays readable by id but leaves listings and search unless `includeCancelled=true`; `cancelledAt` records when. `PATCH {"status":"active"}` restores it. `DELETE` removes an event permanently.

**Source.** `source.kind` is `manual` (created in Life OS), `ics` (an ICS/iCal feed), or `google` (Google Calendar). Imported events also carry `source.sourceId` (the Calendar source they came from, see [Sources](#sources-ics-feeds)), `source.name` (that source's current name, such as "ZAW", which the Dashboard shows as the event's origin), and `source.externalUid` (their identity there: the ICS `UID`, or `<UID>#<RECURRENCE-ID>` for one occurrence of a recurring ICS event); a source holds each `externalUid` once, so refreshes update in place. The API only creates `manual` events (a `source` in a request body is ignored) and updates never change the source. **Feed events are read-only:** a `PATCH` that names anything but their reminders (`reminders`, `useDefaultReminders`) and `priority`, and any `DELETE`, return 409 `managed_by_source`; only their source changes, cancels (`removedFromSourceAt`), and restores them. Google events of calendars the account may edit are changed through the API and written to Google; the others are read-only like feed events (409 `google_read_only`); `editable` and `readOnlyReason` say which (see [two-way sync](#google-calendar-two-way-sync)). The legacy `externalReference` (`provider`/`externalId`) is still accepted and returned but deprecated.

**Reminders** reach the owner: Calendar sends each effective reminder through Notifications when it is due (see [Reminder delivery](#reminder-delivery)). Each reminder is either `{"kind":"relative","minutesBefore":30}` (before the start; an all-day event starts at owner-local midnight) or `{"kind":"localTime","daysBefore":1,"localTime":"19:00"}` (at 19:00 on the owner's wall clock, one calendar day before the event's start date, resolved in the owner's timezone when due, so a pickup on 17 November at 06:00 reminds on 16 November at 19:00, whatever daylight saving does). They work like Google Calendar's notifications: an event follows its calendar's default reminders while `useDefaultReminders` is true (the default) and adds any number of its own (`reminders`, at most 10) on top, so "1 day before, 3 hours before, 30 minutes before" can all apply at once. The defaults are an imported event's source's `defaultReminders` and, for an event created in Life OS, the owner's defaults from [settings](#settings), one list for timed and one for all-day events. Every returned event has `reminders` (its own), `useDefaultReminders`, `defaultReminders` (the defaults for this event, whether it uses them or not), and `effectiveReminders`: the defaults when used, then its own, each reminder once. Every effective reminder is sent.

**Priority** says how important an event is, `low`, `medium`, or `high`, and so how important its reminder notifications are. Every returned event has `priority`, the one that applies, and `defaultPriority`, the one it has without a priority of its own: its source's `defaultPriority` for an imported event (medium unless the source sets another), `medium` for an event created in Life OS. The effective rule is: the event's own priority, else `defaultPriority` (for an occurrence of a recurring event: its own, else the series'). Create, `PATCH`, This event, and This and following take `priority`; `null` is refused (400 `priority cannot be null`), and setting the default is how an event goes back to it. Calendar stores an event's own priority (`events.priority`) only while it differs from its default, so an imported event follows later changes of its source's default unless the owner gave it another priority, which refreshes keep, like the owner's reminders. Sources store `default_priority` (migration 000011; existing events have no own priority and read as medium, existing sources default to medium). A priority change is an ordinary update in Activity (`changes: ["priority"]`).

### Settings

`GET /v1/settings` returns the owner's default reminders for the events they create, `defaultReminders.timed` and `defaultReminders.allDay` (at most 10 each, none until first set), and `updatedAt` (null until the first change). `PATCH /v1/settings` replaces the lists it names, for example `{"defaultReminders":{"timed":[{"kind":"relative","minutesBefore":30}]}}`; every Life OS event that uses its defaults follows. The settings live in `calendar_settings`, a single row. Changing them, like changing a source's configuration, is not recorded in Activity.

**Recurrence** (`frequency` `daily`/`weekly`/`monthly`/`yearly`, `interval`, and optionally `byWeekday`, `count`, or `until`) is stored once with the event (the series) and follows iCalendar (RFC 5545) rules: a timed event keeps its wall-clock time in its `timeZone` (else the owner's) across daylight-saving changes. Weekly repeats on the start's weekday, or on each of `byWeekday` (`MO`…`SU`, weekly only, must include the start's weekday in the event's timezone; returned in week order). Monthly repeats on the start's day of the month and skips months without it (the 31st); yearly repeats on the start's date, so an all-day event on 17 September repeats "annually on September 17" (a birthday; 29 February only in leap years). A series ends after `count` occurrences (1–1000, "ends after N times"), or at `until` (the latest start of an occurrence, inclusive, not before the event's start; an all-day series compares its dates with until's date in the owner's timezone), or never; not `count` and `until` together. Listing and search **expand** recurring events (below). Only events created in Life OS recur this way; Google sync of recurring events is not done yet (Phase 11).

### Recurring events: scopes and occurrence changes

A change to a recurring event has one of three scopes, as in Google Calendar:

- **This event**: `PATCH /v1/events/{id}/occurrences/{recurrenceId}` changes one occurrence: title, description, location (`null` clears them for this occurrence), its start and end (the series' kind: `startAt`/`endAt` or `startDate`/`endDate`), reminders and `useDefaultReminders`, `priority`, or `status`: `cancelled` skips it (kept as history), `active` brings it back. The occurrence's own changes are stored as an **exception** (`event_exceptions`: only the fields it overrides, explicit nulls for cleared notes or location, and `cancelled_at` while skipped), keyed by its `recurrenceId`, which stays its original start even when it is moved. A field set back to the series' value stops being an override, and an occurrence with nothing of its own left has no exception. `allDay`, `recurrence`, and `timeZone` belong to the series (400). The write checks that `recurrenceId` is a real occurrence (404 `occurrence not found`; a non-recurring event is 404 `this event does not repeat`).
- **This and following**: `POST .../{recurrenceId}/split` ends the series with the occurrence before (its `until` becomes that occurrence's start, or for an all-day series midnight of its day in the owner's timezone, and `count` is removed) and creates a new series (new id) starting at the occurrence's original time with the body's changes (an `UpdateEventRequest`; times in the body are the new start; without `recurrence` it repeats like the old one, a `count` keeping the occurrences still to come; `recurrence: null` makes it a single event). On the first occurrence nothing is split: the body changes the series itself (200, like `PATCH /v1/events/{id}`). `POST .../{recurrenceId}/truncate` deletes this and following: the series ends before the occurrence and the exceptions from it on are removed; on the first occurrence the series is deleted.
- **All events**: `PATCH /v1/events/{id}` and `DELETE /v1/events/{id}` on the series (`recurrence: null` stops it repeating: it keeps its first occurrence's times and loses every exception).

`recurrenceId` in these paths is accepted URL-encoded or with literal colons (the Dashboard's proxy decodes path segments), and a timed one in any RFC 3339 offset.

Exceptions survive changes as long as their occurrence exists, meaning the series still has an occurrence with the same original start. An all-events change of the start, the kind, the time zone, or the rule removes the exceptions of occurrences it ends or moves (a new start time moves them all; a later `until` or extra weekdays keep them); a title or length change keeps every exception, and an exception's own override wins over the series' new value. A split moves the exceptions from the occurrence on to the new series when their occurrence still exists there (the same time, kind, time zone, and rule) and drops the others; the fields the split body sets replace the split occurrence's own changes to them. Deleting a series deletes its exceptions. These writes run in one transaction holding the event row, so a concurrent series change cannot leave an exception of an occurrence that no longer exists.

Recurring feed events are stored one event per occurrence and are not series: the occurrence endpoints answer 409 `managed_by_source` for writes and 404 for reads. A recurring Google event whose rule fits the model is a series and takes the same scopes, written to Google; one expanded per occurrence is read-only.

## Listing, search, and occurrences

`GET /v1/events?from&to` returns the events overlapping `[from, to)`, soonest start first. A recurring event appears once per occurrence that overlaps the range, in its place in the order: the item is the recurring event (same `id`, title, recurrence, and so on) with that occurrence's `startAt`/`endAt` (or `startDate`/`endDate`) and `occurrence: {seriesId, recurrenceId, modified}`, where `recurrenceId` is the occurrence's original start (a UTC instant, or a date for all-day events) and is unique within the series. Clients that key items should use `id` plus `occurrence.recurrenceId`. Each occurrence's own changes apply: a moved occurrence is listed at its new time (also when it moved into the range from outside it, and not when it moved out), an edited one with its own fields and effective reminders, both with `modified: true`; a skipped occurrence is left out unless `includeCancelled`, then listed with `status: cancelled` and `cancelledAt`. Ordering and cursors use an occurrence's time after its own changes. Non-recurring events are returned as stored, without `occurrence`. Paging (`limit`, `nextCursor`) runs over occurrences and events alike, so Home, MCP, and the Calendar UI see the same items. `GET /v1/events/{id}/occurrences/{recurrenceId}` returns one occurrence as listed, whatever its status.

`GET /v1/events/search?q` matches every word of `q` in the title, location, or description. A matching recurring event is returned as occurrences too: every occurrence in the range when both `from` and `to` are given, otherwise one item, its next occurrence that is not over yet (or its last one, if it has ended). Occurrences carry their own changes as in listing, and a skipped occurrence is passed over (the next one stands for the series) unless `includeCancelled`. Words are matched against the series' title, location, and description only, not against one occurrence's own changes to them.

Recurring ICS events are not stored as rules: each occurrence is imported as its own event (see below), so they list like any other event.

## Sources (ICS feeds)

A **source** is an external feed whose events Calendar imports and keeps refreshed. Sources belong to the Calendar domain (registry plus adapters inside this service). Feeds are kind `ics`; every Google calendar chosen to sync is a source of kind `google` too (see [Google Calendar sync](#google-calendar-sync)), sharing the reconciliation and the listing filters (`sourceKind`, `sourceId`), but managed and listed under `/v1/google/calendars`, not `/v1/sources`.

A source has a `name` (the label shown with its events, such as "ZAW"), the feed `url` (https; `webcal://` is accepted and means https), `enabled`, a type `filter`, optional `defaultReminders`, `defaultPriority` (the priority of its events that have none of their own; `medium` unless set), `preset` (read-only: set for a source Calendar configures itself, see [ZAW waste collection](#zaw-waste-collection)), and its read-only `refresh` state: `nextRefreshAt`, `lastAttemptAt`, `lastSuccessAt`, `lastOutcome` (`imported`, `not_modified`, `failed`), `lastError`, `consecutiveFailures`, `lastCounts` (feed events, imported, inserted, updated, removed, restored, unchanged, skipped), the `etag`/`lastModified` validators, and `refreshing`. Everything is stored in `calendar_sources`, so the schedule and state survive restarts.

**Filter.** A term matches an event when it equals one of its `CATEGORIES` or occurs in its `SUMMARY` (case-insensitive). With `filter.include` terms only matching events are imported; then events matching `filter.exclude` are dropped; empty lists import everything. For example a waste feed whose summaries name the waste type can keep `["Bioabfall", "Gelber Sack", "Papier"]`.

**Refresh.** Calendar refreshes every enabled source daily at a quiet hour in the owner's timezone (`CALENDAR_SOURCE_REFRESH_AT`, default 04:30), right away when a source is added, re-enabled, or gets a new URL or filter, and on demand with `POST /v1/sources/{id}/refresh` (the Dashboard's "Refresh now", which returns the source with the outcome). The scheduler inside the Calendar service checks for due sources every minute and refreshes one at a time. One refresh per source runs at a time: concurrent requests share it, and a lease in the database (`refreshing_until`) keeps other processes out until it is released or expires, so a crash mid-refresh cannot block a source. When the server sent an `ETag` or `Last-Modified`, the next refresh is conditional and a `304 Not Modified` changes nothing (`lastOutcome: not_modified`).

**Reconciliation** (one transaction per refresh, idempotent):

- an event whose UID is new is inserted (active, or cancelled if the feed says `STATUS:CANCELLED`);
- an event whose feed entry changed is updated in place (same id; the owner's reminders and priority stay);
- a **future** event that is no longer in the feed (or that the filter now excludes) is cancelled and marked `removedFromSourceAt`: it leaves active views but stays as history — never deleted, never silently kept active;
- a removed event whose UID comes back is restored (`active`, `removedFromSourceAt` and `cancelledAt` cleared);
- past events (started before the refresh) are left as they are, so feeds that list only upcoming dates do not cancel history.

**Failures** keep the last good data: an unreachable feed, an HTTP error, a response that is not a complete iCalendar document (an HTML error page, a cut-off download), or an empty calendar where there were upcoming events records `lastOutcome: failed` and `lastError`, and the source is retried after 15 minutes, doubling up to 6 hours but never later than the next daily slot. The next good refresh resets `consecutiveFailures`.

**Activity.** Each refresh records `calendar.source.refreshed` or `calendar.source.refresh_failed` in Activity (when `ACTIVITY_SERVICE_URL` is set), attributed to the source as `system:ics-<name>` (for example `system:ics-zaw`), with the counts or the error. The feed URL, which can carry personal data such as a street, is never put in Activity, logs, or `lastError`. It is one summary event per refresh, also when nothing changed (the feed answered 304 or its events were all unchanged), so the Event Log shows that the daily refresh ran; the events a refresh imports, changes, cancels, or restores get no events of their own (see [Activity](#activity)). The Dashboard labels it with what changed ("Source refreshed: ZAW — 3 added, 1 cancelled") and shows each source's refresh health on Status.

**ICS normalization.** Parsing uses [golang-ical](https://github.com/arran4/golang-ical) for the document structure and [rrule-go](https://github.com/teambition/rrule-go) for recurrence rules:

- `DTSTART;VALUE=DATE` events are all-day; the exclusive `DTEND` becomes an inclusive `endDate` (`DURATION` and a missing end are handled).
- `TZID` times are resolved as an IANA zone, through the `VTIMEZONE`'s `X-LIC-LOCATION`, as a Windows zone name, from an IANA name at the end of a longer identifier (`/mozilla.org/…/Europe/Berlin`), or from the `VTIMEZONE` rules themselves; the IANA name becomes the event's `timeZone`. UTC times are taken as is; floating times are in the calendar's `X-WR-TIMEZONE`, else the owner's timezone.
- A timed event without an end gets a nominal one-minute duration; `DURATION` days are nominal (same wall-clock time).
- A recurring event (`RRULE`, `RDATE`, `EXDATE`) is imported as one event per occurrence from a year back to a year ahead (at most 1,000 per event; the window moves with each refresh), keyed `<UID>#<RECURRENCE-ID>` with the occurrence's original start (`20261017T040000Z`, or `20261017` for all-day). An override (`RECURRENCE-ID`) replaces its occurrence; `STATUS:CANCELLED` cancels it.
- Unreadable events (no start, a repeated UID) are skipped and counted; an event without a `UID` is keyed by its start and summary. A feed may hold at most 10,000 events.

**Safe fetching.** Feeds are downloaded only over https and only from public addresses: after DNS resolution, every connection to a loopback, private (including the Docker networks), link-local (including cloud metadata at 169.254.169.254), unique-local, or other special-purpose address is refused, and every redirect (at most 5) is checked again. Downloads are capped (`CALENDAR_ICS_MAX_BYTES`, default 5 MiB, also after decompression) and time-limited (`CALENDAR_ICS_TIMEOUT_SECONDS`, default 30), and never go through an environment proxy. `CALENDAR_ICS_ALLOW_PRIVATE_URLS=true` lifts the address and https rules for local development and verification against a local feed only.

**Deleting** a source deletes the events imported from it; set `enabled: false` instead to stop refreshing and keep them.

## ZAW waste collection

ZAW's Abfallkalender is served by MyMüll, which exports a personal iCal feed per street (`https://service.mymuell.de/api.php?m=zaw&r=ical&city_id=<city>&area_id=<area>&reminder=0&time=&city_name=<town>&street_name=<street>`): one timed event per pickup at 06:00 Europe/Berlin, the waste type only in `SUMMARY`, followed by the address (`Bioabfall - <town>, <street>`), which is also the `LOCATION`. The server sends no `ETag` or `Last-Modified` (`cache-control: no-store`), so every daily refresh is a full download, reconciled like any feed. No ZAW-specific scraping or storage is involved: ZAW is an ordinary ICS source plus a preset.

**Preset.** When `CALENDAR_ZAW_ICS_URL` is set (compose passes `LIFE_OS_ZAW_ICS_URL` from `.env`; the URL names a street, so it lives only there and is never logged), Calendar ensures at every start, before its scheduler runs, that exactly one source has `preset: "zaw"`:

- if there is none, a source added through the API with the same URL is taken over; otherwise a new one is added, enabled and due right away, so the first import happens within moments of the start rather than at the next 04:30;
- the preset sets `name` "ZAW", the `url`, `filter.include` `["Bioabfall", "Gelber Sack", "Papier", "Restmüll Tonnen und Container 14-täglich"]` (the feed's names for the bins; the weekly "Restmüll Container wöchentlich" for large containers and the "Schadstoffmobil" are left out), and `defaultReminders` `[{"kind":"localTime","daysBefore":1,"localTime":"19:00"}]` (the evening before each pickup, owner-local);
- the configuration last applied is stored with the source (`preset_config`). A later start changes only the settings whose configured value changed since (a new URL in `.env`, or a release that changes the types or reminders); a new URL or filter makes the source due right away. Anything else edited through the API (`PATCH /v1/sources/{id}`: name, filter, reminders, `enabled`) stays, and `enabled` is never changed by the preset;
- concurrent starts are serialized (an advisory lock, and a unique index on `preset`), so restarts never add a second source.

Unset, Calendar leaves an existing ZAW source as it is (and logs that); to remove it, unset the variable, restart, then disable or delete it. Deleting it while the variable is set brings it back at the next start.

**Filtering in Life OS.** The types are chosen by Life OS's own filter on the summary rather than by MyMüll's `trash=ZAW_BIO,ZAW_GELB,ZAW_PAP,ZAW_REST_2W` URL parameter, so the full feed is downloaded (`lastCounts.feedEvents` counts every pickup) and the selection can be changed on the source without touching the URL. Adding `trash=` to the URL also works, but then a type left out there cannot be brought back by the filter.

**Titles.** For this source only, the trailing ` - <town>, <street>` is removed from each title when it repeats the event's location, which keeps it (`Bioabfall`, `Gelber Sack`, `Papier Tonnen und Container`, `Restmüll Tonnen und Container 14-täglich`). This happens before filtering, so a street whose name contains a waste type cannot bring back an excluded type.

**Removed pickups** (a date ZAW moves or drops) are cancelled by the source and kept as history, like any feed's. The events are read-only in the Calendar UI, labelled "ZAW"; only their reminders and priority can be changed (add your own reminders, turn the ZAW default off for one pickup, or make one pickup high priority). The preset sets no default priority: ZAW's is medium until the owner changes it in Reminder defaults, and a restart keeps that choice.

## Google Calendar connection

Calendar connects to the owner's one Google account (P11-01), imports the events of the calendars chosen to sync (P11-02, see [Google Calendar sync](#google-calendar-sync)), writes changes made in Life OS back to them, and exports the events created in Life OS to a dedicated "Life OS" Google calendar (P11-03, see [Google Calendar two-way sync](#google-calendar-two-way-sync)). Owner setup (Google Cloud project, consent screen, OAuth client, `.env`) is in [Google Calendar setup](../operations/google-calendar.md).

**Flow.** The Dashboard's Calendar page asks Calendar to start an authorization (`POST /v1/google/connection/authorize`) and opens the returned consent URL. Google returns the owner to the Dashboard route `/calendar/google/callback` (the OAuth redirect URI), which posts the `code` and `state` to Calendar (`POST /v1/google/connection`) through the Dashboard's `/api/calendar` proxy as `user`. Calendar checks the state, exchanges the code at Google's token endpoint, identifies the account from its calendar list (the primary calendar's id is the account's address, so no profile scope is needed), stores the encrypted refresh token and the calendar list, and the Dashboard returns to `/calendar?google=connected`. Connecting another account replaces the connection and its calendar choices; reconnecting the same account keeps them.

**Scopes.** `calendar.calendarlist.readonly` (which calendars exist), `calendar.events` (read and write events), and `calendar.app.created` (the calendars Life OS creates), with `access_type=offline` and `prompt=consent` so Google issues a refresh token every time. Google lets the owner untick permissions: without `calendarlist.readonly` the connection is refused (403 `google_scope_missing`) and the grant revoked; other missing scopes are stored and reported as `missingScopes`.

**Security.**

- *State and PKCE.* Each authorization has a fresh 256-bit `state` and an S256 PKCE verifier. Calendar stores only the state's SHA-256 with the verifier (`google_oauth_states`), valid for 10 minutes and deleted when used, so a state works once; expired ones are swept at the next authorization. A forged, replayed, or late state is refused (400 `invalid_state`) before any call to Google. The code is useless without the client secret and the verifier, both of which only Calendar holds.
- *Encryption at rest.* The refresh token is encrypted with AES-256-GCM under `LIFE_OS_GOOGLE_TOKEN_KEY` (32 bytes, base64), with a random nonce per encryption stored beside it and a fixed additional-data label; a changed key or an altered ciphertext fails to decrypt (status `error`: reconnect). Access tokens are kept in memory only (their expiry is stored for reference); after a restart the first use refreshes one.
- *No secrets out.* Tokens and the client secret never appear in responses, logs, errors, or Activity; errors keep Google's error code and description only. The callback URL's one-time code is dropped from the browser's address bar at once, the page sends no referrer, and the gateway does not log the callback request.

**Token lifecycle.** An access token is refreshed on demand when it has less than 5 minutes left (`RefreshMargin`), one refresh at a time; a rotated refresh token is re-encrypted and stored. A calendar-list call answered 401 refreshes once and retries. When Google refuses the refresh token (`invalid_grant`: it expired, or the owner removed Life OS in their Google Account) the connection becomes `expired` with a `lastError` ending "reconnect Google in Calendar", records `calendar.google.expired` once, and stops asking Google until the owner reconnects. Another refusal (such as `invalid_client` after a changed client secret) sets `error`; an outage (unreachable, 5xx) changes nothing and answers 502 `google_unavailable`. A later successful refresh returns the connection to `connected`. The sync worker uses the token every few minutes, so an expiry shows within minutes; while the connection is `expired` the worker asks Google nothing, and reconnecting makes every synced calendar due at once.

**Calendars.** The list is stored as Google last listed it (hidden and deleted entries left out), primary first, then by name. A newly listed primary calendar starts with `syncEnabled` true, every other calendar false; a refresh keeps the owner's choices, updates names, colors, and access roles, and drops calendars Google no longer lists (with the events synced from them). A list without a primary calendar is a fault at Google and is refused (502 `google_rejected`), so a glitch cannot drop every calendar.

**Not configured.** Without all of `LIFE_OS_GOOGLE_CLIENT_ID`, `LIFE_OS_GOOGLE_CLIENT_SECRET`, and a valid `LIFE_OS_GOOGLE_TOKEN_KEY`, Calendar starts normally and logs why; `GET /v1/google/connection` says `configured: false`, and authorize, connect, and refresh answer 503 `google_not_configured`. A connection stored earlier can still be disconnected (it is then only forgotten: without the key the token cannot be decrypted to revoke it).

| Request | Behavior |
| --- | --- |
| `GET /v1/google/connection` | `{configured, status: not_connected\|connected\|expired\|error, accountEmail, scopes, missingScopes, connectedAt, lastError}`. |
| `POST /v1/google/connection/authorize` | `{url}`: Google's consent page with a new single-use state and PKCE challenge (a reconnect adds `login_hint`). 503 when not configured. |
| `POST /v1/google/connection` | `{code, state}` → the connection (200). 400 `invalid_state` or `google_code_rejected`, 403 `google_scope_missing`, 502 `google_rejected`/`google_unavailable`, 503 `google_not_configured`. |
| `DELETE /v1/google/connection` | Revokes the refresh token at Google (best effort; a failure is noted in the Activity summary) and deletes the connection with its calendars (204, also without a connection). |
| `GET /v1/google/calendars` | `{items}`: the stored list with `id` (Calendar's), `googleCalendarId`, `summary`, `color`, `accessRole`, `primary`, `syncEnabled`, and `sync` (see [sync state](#google-calendar-sync)). Empty without a connection. |
| `POST /v1/google/calendars/refresh` | Reads the list from Google again and returns it. 409 `google_not_connected` or `google_expired`, 502, 503. |
| `PATCH /v1/google/calendars/{id}` | `{syncEnabled}` → the calendar; 404 for an unknown id. On: due for a full sync now. Off: its synced events are removed from Life OS. |
| `POST /v1/google/calendars/{id}/sync` | Syncs now (`?full=true`: lists every event again) and returns the calendar (200, whatever the outcome: read `sync`). 409 `google_sync_disabled`, `sync_in_progress`, `conflict`, `google_not_connected`, `google_expired`; 503 `google_not_configured`. |

Activity records `calendar.google.connected` (summary "Google Calendar connected: owner@example.com (3 calendars)", attributed to the request's actor), `calendar.google.disconnected` (with `revokedAtGoogle`), and `calendar.google.expired` (attributed to `system:calendar`, outcome failed), all with subject `google_connection`; their `data` holds the account address and, for a connection, the granted and missing scopes.

The integration tests (`internal/api/google_integration_test.go`) run the whole flow against an in-process fake Google (`internal/google/fakegoogle`), never the real one: state reuse and expiry, PKCE, refresh margin, restarts, `invalid_grant`, rotation, a changed key, and checks that no response, Activity event, or stored column holds a token or the secret.

## Google Calendar sync

Every calendar chosen to sync (`syncEnabled`) is imported into Calendar and kept up to date from Google (P11-02). Its events are imported events: `source.kind` `google`, `source.sourceId` the calendar's source, `source.name` the calendar's name as the owner sees it in Google (renaming it there renames it here at the next sync), `source.externalUid` the Google event id; searchable and listed like any event. Changes made to them in Life OS are written to Google (P11-03, see [two-way sync](#google-calendar-two-way-sync)).

**Data.** Migration `000010_google_sync` (reversible: going down deletes the synced events and keeps feeds and Life OS events) adds:

- `calendar_sources.google_calendar_id`: a `google` source belongs to its Google calendar (one each); deleting the calendar row (unticking it, disconnecting, Google no longer listing it, another account connected) deletes the source and, through `events.source_id`, its events and their occurrence exceptions. Its `url` is the calendar's events endpoint at Google, for reference only; feeds' scheduler and `/v1/sources` (list, get, update, delete, refresh) leave `google` sources alone (404).
- Sync state on `google_calendars`: `sync_token` (from the last complete listing), `sync_window_start` (the start of the last full listing's time window), `next_sync_at` and the lease `syncing_until`, `last_sync_attempt_at`, `last_synced_at` (last success), `last_sync_error`, `sync_failures`, `last_sync_counts`, `time_zone` (the calendar's, as Google reports it), and `derived_at`. Calendars chosen before the migration are due right away.
- `google_events`: the calendar's events as Google last sent them (only the fields Calendar maps), a single event, a recurring event's master, or one changed or cancelled instance (`recurring_event_id`). Calendar's events are derived from all of them, so a series and its changed instances that arrive in different syncs come together, and a restart resumes from the stored token without listing again.
- `events.source_reminders`: the reminders the source last gave the event, to tell the owner's own reminder change from an event still following its source.

**Sync.** A worker in the Calendar process (`internal/google/sync.go`) syncs each chosen calendar every `CALENDAR_GOOGLE_SYNC_SECONDS` (default 120) while Google is configured and the connection is not `expired`, one calendar after another:

1. It takes the calendar's lease (one sync per calendar across processes; concurrent syncs in one process share one run; a crashed sync's lease expires after 5 minutes).
2. It lists the calendar with `events.list` (`singleEvents=false`, so a recurring event comes as its master plus its changed or cancelled instances; `showDeleted=true`, so deletions are reported; 100 a page, `pageToken` up to 250 pages, at most 16 MiB a page). Without a sync token it lists **in full**: every event ending after a year ago (`timeMin`, `SyncLookback`), with no upper bound, so every future event; otherwise **incrementally** with `syncToken`, only what changed since. Google answering 410 (token expired) drops the token and lists in full right away. A 401 refreshes the access token once; `invalid_grant` makes the connection `expired` (P11-01).
3. In one transaction holding the calendar row it stores the listing (a full listing replaces `google_events`; an incremental one updates them, a deleted event and its instances are forgotten, a cancelled instance is kept as a skip), derives the calendar's events from all stored ones, and reconciles them with the source's events, then records the new sync token and the outcome. Nothing is written when the calendar was switched off or resynced meanwhile.
4. Reconciliation is the feeds' (`sources.Reconcile`), with the rules of an authoritative source: a new event is inserted, a changed one updated in place (past ones too), one that is gone is cancelled and marked `removedFromSourceAt` (kept as history), and restored when it comes back; an event that ended before the window of the last full listing is left as it is when a new full listing no longer has it. It is idempotent, so a full listing after a 410 changes nothing that did not change and never duplicates. Events are derived again only when the listing changed something, after a full listing, or every 12 hours (expanded occurrences move with the window). Derivation reaches back to the last full listing's window start but never more than a year, so occurrences do not pile up over months of incremental syncs; older history stays as it is.

A failed listing changes no event: the calendar records `lastError` and one more failure and is retried after the interval, doubling up to an hour (2, 4, 8 … 60 minutes); the next good sync resets the failures. A listing that cannot be saved ("the events read from Google could not be saved in Calendar") is a failure the same way, and the next attempt lists the same changes again. A full resync requested while the calendar is syncing answers `sync_in_progress` and makes the running sync give way to a full listing. The calendar's default reminders (popup and email lead times) become its source's `defaultReminders` at each sync.

**Mapping.**

| Google | Calendar |
| --- | --- |
| `id` | `source.externalUid` (`iCalUID` is kept with the stored event only; it is shared by a series' instances and by copies of an invitation in other calendars) |
| `summary`, `description`, `location` | `title` ("Untitled event" when empty), `description`, `location`, clipped like feeds' (500, 10,000, 500 characters). A description edited on the web is HTML: tags are dropped, line breaks kept, links keep their address ("the doc (https://…)"), entities decoded. |
| timed `start.dateTime`/`end.dateTime` with `timeZone` | `startAt`/`endAt` (instants) and `timeZone` (the start's zone, else the calendar's). An end not after the start gets one minute. |
| all-day `start.date`/`end.date` (end exclusive) | `startDate`/`endDate` (end inclusive) |
| `status: cancelled` | the event is gone: removed as above (a deleted series with all its occurrences) |
| `reminders.useDefault` | `useDefaultReminders`, with the calendar's `defaultReminders` as the source's defaults |
| `reminders.overrides` (popup or email, minutes) | own relative reminders, each lead time once, at most 10 |
| `transparency`, `visibility`, attendees, colors, conference data | ignored |
| `eventType: workingLocation` (Home, Office) | not imported: status markers, not events (focus time, out of office, birthdays are) |

**Recurring events.** A master's `recurrence` maps to Calendar's series (stored once, listed as occurrences) when it is exactly one RRULE (plus EXDATEs) that the model holds: `FREQ` DAILY, WEEKLY, MONTHLY, or YEARLY with `INTERVAL`, `COUNT` (at most 1,000) or `UNTIL`, and for a weekly rule `BYDAY` with plain days that include the start's (`WKST` other than Monday only matters, and then does not fit, for several days every 2+ weeks); a `BYMONTHDAY` or `BYMONTH` that only repeats the start's day or month is accepted. `UNTIL` in UTC is the series' until; a date `UNTIL` of an all-day series is stored as noon of that date in the owner's timezone (an all-day series compares its dates with until's date there). EXDATEs become skipped occurrences, a cancelled instance (`recurringEventId` + `originalStartTime`) too, and a changed instance becomes that occurrence's own changes (title, description, location, start and end, reminders, as far as they differ from the series), keyed by its original start like any occurrence exception. An instance whose original start is not an occurrence of the series as Calendar repeats it is imported as an event of its own.

Rules outside the model — monthly or yearly `BYDAY` such as "second Tuesday" or "last Friday", `BYSETPOS`, `BYYEARDAY`, `BYWEEKNO`, hourly or finer, `RDATE`, several RRULEs, an instance switching between timed and all-day — are imported as one read-only event per occurrence from the full listing's window start to 400 days ahead (`ExpansionHorizon`), expanded by the feed parser (rrule-go), keyed as Google names its instances (`<id>_20261013T160000Z`, `<id>_20261013` all-day); a changed instance replaces its occurrence and a cancelled one removes it. The window moves forward as days pass (re-derived at least every 12 hours). `EXRULE` (deprecated, not written by Google) is ignored.

**Reminders.** A new event gets Google's reminders: its overrides as its own and `useDefaultReminders` as Google says, so the calendar's defaults apply when the event follows them. Google's API does not expose the default notifications of all-day events (a calendar's defaults are for timed events), so an all-day event following its defaults gets none rather than wrong ones. When Google changes an event's reminders, the event follows only while its reminders still equal `source_reminders`; an editable event's reminders are changed in Google (two-way), so they always follow, while the owner's own reminders on a read-only event (a calendar the account can only read) stay, like a feed's, and every other field still follows Google.

**Priority.** Google has no priority: Life OS keeps an event's own priority in its private extended property `lifeosPriority` (written by Life OS, see [two-way sync](#google-calendar-two-way-sync)). A listed event that carries it gets that priority (none, or the source's default, follows the default); one without it keeps whatever priority it has in Life OS (the source's default unless the owner chose another, as on a read-only calendar). A changed instance with another priority than its series' becomes that occurrence's own priority.

**Switching off and disconnecting.** Unticking a calendar deletes its source, its events (they stay in Google), and its stored Google events, and records `calendar.source.removed` ("Family no longer syncs from Google: 42 events removed from Life OS", attributed to the owner, `data.reason` `sync_disabled`, `removedEvents`). Ticking it again lists it in full again. Disconnecting Google (reason `disconnected`), Google no longer listing a calendar (`calendar_unlisted`), and connecting another account (`account_replaced`) remove the synced calendars' events the same way, one `calendar.source.removed` per calendar.

**Sync state.** `GET /v1/google/calendars` gives each calendar `sync`: `state` (`off`, `pending` before its first sync, `synced`, `failing`), `sourceId`, `lastAttemptAt`, `lastSyncedAt`, `nextSyncAt`, `lastError`, `consecutiveFailures`, `lastCounts` (of the last sync that derived events), and `syncing`.

**Activity.** A sync records one `calendar.source.refreshed` (subject the calendar's `calendar_source`, actor `system:google-calendar`, `data.sourceKind` `google`, `counts`, `full`, `trigger`) when it changed events ("Synced Owner from Google: 3 new, 1 changed, 0 removed, 0 restored"), on the first sync, and on the first good sync after failures; a sync that changed nothing records nothing, so polling every two minutes leaves the Event Log alone. A failure records one `calendar.source.refresh_failed` ("Syncing Owner from Google failed: …") when a failure streak starts or the error changes; repeated identical failures are only counted on the calendar. An expired connection is recorded once, as `calendar.google.expired`.

**Limits.** History older than a year before the first full listing is not imported. Free/busy-only calendars give events without details. Event colors are not shown (the Dashboard labels events with the calendar's name). A calendar of more than 25,000 events in the window fails its listing (250 pages).

## Google Calendar two-way sync

Since P11-03 Google Calendar and Life OS sync both ways (owner decisions in Notion P11-03). Who owns what:

| Event | Lives in | Edited in Life OS | Written to Google | Changes made in Google |
| --- | --- | --- | --- | --- |
| Created in Life OS (`source.kind` `manual`) | Life OS; a copy in the **Life OS** calendar | Yes, stored locally first | Exported afterwards through the outbox (retried while Google is unreachable) | Applied to the Life OS event (Google wins a conflict) |
| In a synced calendar the account may edit (`accessRole` owner or writer): single events and series Calendar holds | Google | Yes (`editable: true`), Google first | Every change, with the stored etag (`If-Match`) | Synced as before |
| In a synced calendar the account can only read (reader, freeBusyReader, holidays) | Google | Reminders and priority only, in Life OS (`editable: false`, `readOnlyReason`) | Never | Synced as before |
| One occurrence of a Google rule Calendar cannot hold (expanded, `<id>_<start>`), or a lone instance | Google | Reminders and priority only (`editable: false`) | Never | Synced as before |
| From a feed (`ics`, such as ZAW) | The feed | Reminders and priority only | Never exported | — |

**Writing a synced event.** `PATCH /v1/events/{id}` merges and validates the change as for any event, then sends Google a PATCH with only the fields the change names (title → `summary`, notes, place, start and end with the event's zone, all-day dates with an exclusive end, `recurrence` as an RRULE built from the series plus the EXDATEs Google already has, `reminders` as `useDefault` and popup overrides, priority as `extendedProperties.private.lifeosPriority`), so attendees, conference data, colors, and anything else Calendar does not map stay as they are. The request carries the etag Calendar stored for the event (`If-Match`). Google's answer is stored with the calendar's Google events and the calendar's events are derived again, as a sync would, in one transaction holding the calendar: the event in Life OS is Google's version. The scopes work the same way: **This event** writes the occurrence's instance (read from Google by its instance id, else through `instances?originalStart`; an instance Calendar stored is written with its stored etag), and skipping it cancels the instance; **This and following** creates the new series in Google first (carrying the skips as EXDATEs and the changed occurrences as changed instances when the change keeps their times), then ends the old one with an UNTIL before the occurrence (if that fails, the new series is deleted again) and deletes the old series' changed instances from there on; **truncate** ends the series with an UNTIL (on the first occurrence deletes it); `status: cancelled` and `DELETE` delete the event in Google (cancelled: Life OS keeps it as cancelled history, removed from its source; restoring it sends `status: confirmed`; an event deleted in Google must be restored before it can be changed, 409 `google_deleted`). Reminders Google cannot hold are refused with 400 before anything is written: Google keeps at most five notifications, each minutes before the start, and a reminder at a time of day only on an all-day event, at least a day before (it becomes minutes before its first midnight). Nothing changes in Life OS when Google is not written: unreachable or 5xx is 502 `google_unavailable`, an expired connection 409 `google_expired`, a 403 (the calendar became read-only) 409 `google_read_only` with the reason.

**Conflicts.** Google holds the current version of events in Google calendars. A write answered 412 (the event changed in Google since Calendar read it) is not retried: Calendar reads the event from Google, stores and shows that version, records `calendar.google.conflict` (subject the event, attributed to the request's actor, outcome failed, `data.calendar`), and answers 409 `google_conflict` with "Changed in Google meanwhile; showing the latest version". An event deleted in Google meanwhile (404/410) is removed from Life OS and answers 409 `google_deleted`. Changes are never written over Google's.

**Loop prevention.** Every write stores Google's answer (its `etag` and `updated`), and the next sync recognizes its own writes: a listed event whose etag is the stored one is skipped (not stored again, not derived, no Activity). A listing read before a write cannot undo it either: stored events are only replaced by a version with a later `updated`. A sync that only brings Calendar's own writes back records nothing.

**The Life OS calendar.** When Google is connected with export on (the default), the export worker creates a secondary calendar named "Life OS" (`calendars.insert`, the owner's timezone; scope `calendar.app.created`), or adopts an owned calendar of that name (after disconnecting and connecting again), stores its id on the connection (`lifeOsCalendar`), and adds it to the calendar list with sync on, so events created in it in Google are imported like any synced calendar's and changes to the copies come back. Activity records `calendar.google.calendar_created`. If the owner deletes it in Google, the next export finds it gone (404), creates it again, queues every exported event again, and says so in `lifeOsCalendar.note` ("The Life OS calendar was deleted in Google; Life OS created it again on … and exports your events to it again.") and in Activity (`data.recreated`). A calendar that cannot be created (such as a missing permission) shows its reason as `export.lastError`. Disconnecting leaves the calendar in Google.

**Exporting Life OS events.** Every create, change, occurrence change, split, truncate, cancel, and delete of a Life OS event is stored locally first and queued in the outbox (`google_exports`, one row per event); the worker (every sync interval, and woken at once by a change) writes the event's latest state to the Life OS calendar: its whole copy (title, notes, place, times in the event's zone, the series' RRULE with EXDATEs for skipped occurrences, the reminders that apply to it as popup overrides — at most five, minutes before; a time-of-day reminder of a timed event cannot be held and is left out — and the private properties `lifeosEventId` and `lifeosPriority`) under the fixed id `lifeos<event uuid hex>`, then each changed occurrence as a changed instance (and an occurrence back to its series' values as its instance put back). The copy is written with its etag (`If-Match`); a copy changed in Google meanwhile (412) is not overwritten: Google's version is applied to the Life OS event and the conflict recorded (`calendar.google.conflict`, `data.kind` `export`). A crash between Google's answer and recording it is harmless: inserting the fixed id again finds the copy (409) and updates it. Cancelling deletes the copy, restoring writes it again (Google's deleted copy is restored), deleting the event deletes the copy and then the outbox row. A failed attempt (Google unreachable, 5xx, 429) keeps the local change, marks the export `failed` with the error, and retries after the sync interval, doubling up to an hour; Activity records `calendar.google.export_failed` when a failure streak starts or the error changes. An expired connection parks exports until it is reconnected (connecting makes them due at once). Exporting is switched by `PATCH /v1/google/connection {exportEnabled}` ("Export events created in Life OS", on by default); switched off, nothing more is written (the copies stay in Google), switched on again, the upcoming events are queued.

**Backfill.** Exporting covers the Life OS events that already exist, not only those created afterwards: when export is on and the connection has not been backfilled (`export_backfilled_at` null: a connection made before this release, after the deploy), the worker queues once every active Life OS event that is not over, series included (a series without an end or ending after now; one ending after a count of occurrences counts as lasting count times its interval at most), through the same outbox. Connecting and switching export on do the same. Queuing is idempotent (an event that already has an export row is left as it is), and past events stay in Life OS.

**Changes made to copies in Google.** The Life OS calendar's sync does not import the copies (events carrying `lifeosEventId`) as Google events. A copy, or one of its instances, that a listing reports changed in Google (not Calendar's own write) is applied to its Life OS event: title, notes, place, times, time zone, rule, priority, and the occurrence changes and skips; the Life OS event's reminders stay Life OS's (Google holds them only as minutes). Activity records `calendar.event.updated` or `calendar.event.rescheduled` (actor `system:google-calendar`, `data.changedIn` `google`). A copy deleted in Google cancels its Life OS event (kept as history, `calendar.event.cancelled`) and unlinks it; restoring the event in Life OS exports it again. A Life OS change still waiting to be exported when Google's change arrives loses: Google's version is kept and the conflict recorded.

**Data.** Migration `000013_google_two_way` (reversible: going down forgets the links and stops exporting; the copies stay in Google) adds to `google_connections` `export_enabled` (default true), `export_backfilled_at`, `lifeos_calendar_id`, `lifeos_calendar_created_at`, and `lifeos_calendar_note`, and the `google_exports` outbox: per Life OS event its connection, the copy's calendar and event id (both or neither), etag and `google_updated`, the exported occurrence changes, `state` (`pending`, `synced`, `failed`), `deleted`, `requested_at` (a change queued while an export runs keeps it pending), `next_attempt_at`, a lease (`exporting_until`), `attempts`, `last_error`, and `exported_at`. The row has no foreign key to the event, so a deletion is exported after the event is gone; it goes with the connection.

**API.** Every event says `editable` and, when it is not, `readOnlyReason` (for the owner, such as "“Holidays in Germany” is a Google calendar you can only read, …"), and `google`: `{calendarId, calendarName, lifeOs, state, error}` where it is in Google — a Google event's calendar (`synced`), a Life OS event's export (`pending`, `synced`, `failed` with `error`); null when it is not in Google. `GET /v1/events` and `/v1/events/search` take `editable=true` for only the events that can be changed (Life OS events and editable Google events; the AI searches this way). `GET /v1/google/connection` adds `exportEnabled`, `lifeOsCalendar` (`googleCalendarId`, `calendarId`, `summary`, `createdAt`, `note`), and `export` (`pending`, `failed`, `lastError`, `lastExportedAt`), shown on the Status page; `GET /v1/google/calendars` marks the Life OS calendar `lifeOs: true`.

**AI.** The rules for the AI are unchanged in substance: it may create Life OS events (they are exported), change a single editable Google event like a Life OS event (found with `editable=true`; a recurring one is changed only in the Calendar, Human Review), and every cancellation waits for the owner (a Google occurrence is skipped through Google's instance). See [MCP](mcp.md).

**Limits.** Google's version wins every conflict, also over a Life OS change waiting to be exported (it is in Activity). Reminders of Life OS events are Life OS's: the copy carries them as popup minutes, and a reminder change made to a copy in Google is not brought back. A split of a Google series carries skips and changed occurrences to the new series only when the change keeps their times. Converting a Google series into a single event writes an empty recurrence. Orphan copies (of Life OS events deleted while Google was disconnected) stay in the Life OS calendar. Event colors, attendees, and conference data are not written.

## Reminder delivery

Calendar sends every effective reminder of every active event and occurrence to the owner through [Notifications](notifications.md) (`pkg/notify`, the one notification path) when it is due. The owner can add as many reminders as they like ("1 day before, 3 hours before, 30 minutes before") and each one is sent. There are no quiet hours.

- **Dispatcher.** A goroutine in the Calendar process (`internal/reminders`, beside the source scheduler) runs every `CALENDAR_REMINDER_INTERVAL_SECONDS` (30 s). Each run computes the reminders due in `(last run, now]`. It reads the events and occurrences that start from a day before that window to 29 days after it (the largest reminder offset is 28 days), with indexed queries for single events and the same recurrence expansion and occurrence exceptions as listing (`ReminderOccurrences` in `internal/api`), and their `effectiveReminders` resolved as listing resolves them: an imported event's source defaults (ZAW: the evening before at 19:00; a synced Google calendar: its default reminders), a Life OS event's owner defaults for timed or all-day events, plus its own, each once.
- **Due times.** `relative`: the start minus `minutesBefore`, an exact duration; an all-day event starts at owner-local midnight of its first day. `localTime`: `localTime` on the owner's wall clock on the start's owner-local date minus `daysBefore`, resolved in `LIFE_OS_TIMEZONE`, so the evening-before reminder stays at 19:00 across daylight saving changes. A wall time skipped when the clocks go forward is the same time after the jump (02:30 becomes 03:30); one that occurs twice is the first.
- **Occurrences and changes.** Every occurrence of a recurring event reminds on its own. A skipped occurrence sends nothing; one with its own changes uses its own times, title, and reminders. Cancelled and deleted events send nothing. Changes take effect at the next run: a moved event or occurrence reminds again at its new time (a reminder already sent for the old time stays sent), and a reminder added before its time fires. A reminder whose time has already passed when it is added, or when its event is moved, is not sent.
- **Exactly once.** Each reminder's dedupe key is `calendar:reminder:<eventId>:<recurrenceId or single>:<start>:<reminder>`, where start is the occurrence's start instant in UTC or its first date, and reminder is `rel:30` or `local:1:19:00`. Notifications stores a key once. Calendar also keeps its cursor (`calendar_reminder_dispatch.last_run_at`) and every handled key (`calendar_reminder_log`: sent, missed, or failed; pruned after 30 days), so restarts and overlapping runs neither repeat nor skip a reminder. One process runs at a time: a run holds a lease on the state row (two minutes, at least four intervals), and another Calendar process skips its run meanwhile.
- **Failures.** When Notifications is unreachable or answers 5xx, the run stops at that reminder and keeps the cursor just before it, so the next run retries it; reminders already sent are not sent again. A notification Notifications refuses (4xx) is recorded as failed, logged, and not retried. Either error is kept as `lastError`.
- **Missed while down.** After Calendar was down, the first run handles everything due since the last run, at most 7 days back. A reminder up to `CALENDAR_REMINDER_GRACE_MINUTES` (120) late is sent, phrased from the time it is sent and ending with "(late)"; an older one is not notified but recorded in Activity as `calendar.reminder.missed`. A reminder counts as late when it is sent more than two intervals (at least a minute) after its time. The very first run after deployment only starts the cursor.
- **Off without Notifications.** With `NOTIFICATIONS_SERVICE_URL` unset the dispatcher does not run (logged at startup). Once it is set, reminders that came due meanwhile are handled like those due while Calendar was down.

| Notification field | Value |
| --- | --- |
| `title` | The event's (or occurrence's) title. |
| `body` | When the event starts, seen from the reminder time, in the owner's timezone with a 24-hour clock, then its location: "In 30 minutes · 15:00–16:00 · Dr. Weber", "In 3 hours · 15:00–16:00", "Tomorrow at 15:00 · Dr. Weber", "Thu 15 Oct at 09:00"; all-day "Tomorrow, all day", "Today until Sun 18 Oct". Events of the ZAW source leave the location (the owner's street) out: "Papier" with "Tomorrow at 06:00". |
| `importance` | The event's effective `priority`, `low`, `medium`, or `high` (its own, for an occurrence its own or else the series', else its `defaultPriority`: its source's for an imported event, `medium` for a Life OS one). |
| `category` | `calendar.reminder` |
| `link` | `/calendar?date=<the start's owner-local date>` |
| `occurredAt` | The reminder time. |
| `dedupeKey` | As above. |

`calendar.reminder.missed` has subject `calendar_event` (the event's id), actor `system:calendar`, outcome `failed`, `occurredAt` the reminder time, a summary such as "Reminder for “Standup” due Sat 10 Oct 2026, 12:10 CEST was missed: Calendar was not running", and `data` with the `title`, `dueAt`, the start, the reminder, `recurrenceId`, `sourceKind`/`sourceId`, and `dedupeKey`; its id is derived from the dedupe key, so it is recorded once. A sent reminder records nothing in Calendar's name: Notifications records `notification.created`.

`GET /v1/reminders/status` reports the delivery's health for the Status page: `enabled`, `intervalSeconds`, `graceMinutes`, `handledThrough` (the cursor), `lastRunAt`, `lastSuccessAt`, `lastError` with `lastErrorAt` (current while later than `lastSuccessAt`), and `lastSentAt`.

`internal/reminders` holds unit tests (due times of relative and localTime reminders across both daylight saving changes, skipped and repeated wall times, all-day events, the window, dedupe keys, bodies and late phrasing, importance) and integration tests against `CALENDAR_TEST_DATABASE_URL` with an in-process Notifications that deduplicates like the real one: every effective reminder sent once, recurring occurrences with skipped and moved exceptions, all-day and imported (ZAW and another feed) defaults, Google-synced events (the calendar's defaults plus the event's own, a series with an occurrence cancelled in Google), importance from the effective priority (own, a source's default, an occurrence's own), late and missed reminders after downtime, a lost cursor, failing and refusing Notifications, moves, cancellations, deletions, added reminders, the lease and two processes at once, and migration 000012 down and up.

## Activity

When `ACTIVITY_SERVICE_URL` is set, every event change made through the API records exactly one Activity event once it is stored, with subject `calendar_event` and the event's id. It is attributed to the request's `X-Life-OS-Actor` (`user` for the owner in the Dashboard, `agent:<name>` for the AI through MCP, `dev:<name>` for development tools) and carries the request's `X-Correlation-ID` and `X-Causation-ID`, so a change the agent makes appears in its capture's workflow in the Event Log, after the MCP action that caused it.

| Type | Recorded for |
| --- | --- |
| `calendar.event.created` | `POST /v1/events`. Its id is derived from the event's, so an idempotent replay is recorded once. |
| `calendar.event.rescheduled` | A `PATCH` that changes the start, the end, or all-day (with whatever else it changes, unless it also changes the status). |
| `calendar.event.cancelled` / `calendar.event.restored` | A `PATCH` that changes `status`. |
| `calendar.event.updated` | Any other `PATCH` that changes something: title, notes, location, time zone, repetition, reminders, or priority (also an imported event's reminders and priority). |
| `calendar.event.deleted` | `DELETE /v1/events/{id}`, or a truncate at a series' first occurrence. |

A change of one occurrence (This event) records `calendar.event.cancelled`, `restored`, `rescheduled`, or `updated` on the series with `data.recurrenceId` and that occurrence's times, such as "Event “Gym” on Sat 10 Oct 2026, 07:00 CEST cancelled". A split records `calendar.event.updated` on the old series (`changes: ["recurrence"]`) and `calendar.event.created` for the new one with `data.splitFrom` (the old series' id); a truncate records `calendar.event.updated` (`changes: ["recurrence"]`).

Two-way Google sync adds `calendar.google.conflict` (a change not written because the event changed in Google meanwhile), `calendar.google.calendar_created` (the Life OS calendar created, or created again), and `calendar.google.export_failed` (a Life OS event that could not be exported, once per failure streak); changes made in Google to exported Life OS events record `calendar.event.updated`, `rescheduled`, or `cancelled` attributed to `system:google-calendar` (see [two-way sync](#google-calendar-two-way-sync)).

A `PATCH` that changes nothing, and any refused request (invalid, 404, 409 `managed_by_source`, `google_read_only`, `google_conflict`), records nothing as an event change. `data` holds the `title`, the times (`startAt`/`endAt` or `startDate`/`endDate`), `allDay`, `timeZone`, `status`, `sourceKind` and `sourceId`, and `recurrence`; an update adds `changes` (the changed fields) and, when renamed, `previousTitle`; a reschedule adds `previous` (the old times). Notes, location, and reminders are not copied into Activity. The summary is a sentence with times in the owner's timezone, such as "Event “Dentist” moved to Thu 19 Nov 2026, 09:00 CET".

Source refreshes record one summary event per refresh (see [Sources](#sources-ics-feeds)), not one per imported event: a first import brings dozens of events, and the refresh's counts say what changed. Google syncs record one only when they changed something or failed, and `calendar.source.removed` when a synced calendar's events leave Life OS (see [Google Calendar sync](#google-calendar-sync)).

Reminder delivery records only reminders it could not send in time, as `calendar.reminder.missed` (see [Reminder delivery](#reminder-delivery)).

## API

| Request | Behavior |
| --- | --- |
| `POST /v1/events` | Creates an active manual event (201). Requires `title` and `allDay` plus that kind's start and end; optional `priority` (default medium). `Idempotency-Key`: an identical repeat returns the original event; reuse with a different body is 409. |
| `GET /v1/events/{id}` | The event, whatever its status. |
| `PATCH /v1/events/{id}` | All events for a series (see [scopes](#recurring-events-scopes-and-occurrence-changes)). Changes only the named fields; `null` clears a nullable field (`description`, `location`, `timeZone`, `recurrence`, `reminders`, and the start/end fields). Changing `allDay` switches kind: the other kind's fields are cleared and the new kind's start and end must be given. The merged event is validated as a whole, holding the event so concurrent changes wait for each other. `reminders: null` returns the event to its defaults alone (no own reminders, `useDefaultReminders` true unless the body sets it). Feed events and read-only Google events: only `reminders`, `useDefaultReminders`, and `priority` (else 409 `managed_by_source` or `google_read_only`). An editable Google event is written to Google first (409 `google_conflict`, `google_deleted`, `google_expired`; 502 `google_unavailable`); a Life OS event's change is exported afterwards. |
| `DELETE /v1/events/{id}` | Deletes a Life OS event permanently (204), for a series every occurrence and exception (All events), and its copy in Google afterwards; an editable Google event is deleted in Google first; feed and read-only Google events return 409 `managed_by_source` / `google_read_only`. |
| `GET /v1/events/{id}/occurrences/{recurrenceId}` | One occurrence with its own changes applied, whatever its status; 404 `this event does not repeat` or `occurrence not found`. |
| `PATCH /v1/events/{id}/occurrences/{recurrenceId}` | This event: the occurrence's own changes or skip (`status`); returns the occurrence. 400 for `allDay` other than the series', `recurrence`, or `timeZone`; 409 `managed_by_source` for feed events; for a Google series written to its instance in Google. |
| `POST /v1/events/{id}/occurrences/{recurrenceId}/split` | This and following: ends the series before the occurrence and returns the new series (201), or on the first occurrence changes and returns the series (200). |
| `POST /v1/events/{id}/occurrences/{recurrenceId}/truncate` | Deletes this and following (204); on the first occurrence deletes the series. |
| `GET /v1/events?from&to` | Events and occurrences overlapping `[from, to)` (`to` must be after `from`), soonest start first. Optional `timeZone`, `includeCancelled`, `sourceKind`, `sourceId`, `editable`, `limit` (1–100, default 50), and `cursor`. |
| `GET /v1/events/search?q` | Events whose title, description, or location contain every word of `q` (case-insensitive substring, up to 10 words), across all dates. Optional `from`/`to` (either may be open), `timeZone`, `includeCancelled`, `sourceKind`, `sourceId`, `editable`, `limit` (1–100, default 20), and `cursor`. |
| `PATCH /v1/google/connection` | `{exportEnabled}`: exporting Life OS events to the Life OS calendar on or off (on queues the upcoming ones); 409 `google_not_connected`. |
| `GET /v1/sources` | Every feed (ICS source) with its refresh state; synced Google calendars are listed under `/v1/google/calendars`. |
| `POST /v1/sources` | Adds a source (201): `name`, `url`, optional `enabled` (default true), `filter`, `defaultReminders`, `defaultPriority` (default medium). Its first import is due right away. |
| `GET /v1/sources/{id}` | The source. |
| `PATCH /v1/sources/{id}` | Changes the named fields (`defaultReminders: null` removes them; `defaultPriority` cannot be null). A new `url` or `filter` drops the validators and schedules a full refresh now. |
| `DELETE /v1/sources/{id}` | Deletes the source and its events (204). |
| `GET /v1/settings`, `PATCH /v1/settings` | The owner's default reminders for timed and all-day Life OS events (see [Settings](#settings)). |
| `GET /v1/reminders/status` | Reminder delivery's health (see [Reminder delivery](#reminder-delivery)). |
| `POST /v1/sources/{id}/refresh` | Refreshes now and returns the source (200, whatever the outcome); 409 `source_disabled`, `refresh_in_progress`, or `conflict` (the source changed meanwhile). |

Search ranks a word found in the title 3, in the location 2, in the description 1, most relevant first; among equals, events not over yet come first (soonest first), then past ones (most recent first). Listing and search page with an opaque `nextCursor`: pass it back as `cursor` with the same parameters; no `nextCursor` means the last page. A search cursor also keeps the moment that split upcoming from past, so paging stays consistent while time passes.

Every write needs `X-Life-OS-Actor` (see [API overview](../api/overview.md)). Invalid requests return 400 with an error message saying what to fix; unknown ids return 404.

## Configuration

| Variable | Default | Meaning |
| --- | --- | --- |
| `LIFE_OS_TIMEZONE` | `UTC` | The owner's timezone (all-day matching, recurrence wall clock, refresh schedule, floating ICS times). |
| `CALENDAR_SOURCE_REFRESH_AT` | `04:30` | Daily source refresh time, HH:MM owner-local (compose passes `LIFE_OS_CALENDAR_SOURCE_REFRESH_AT`). |
| `ACTIVITY_SERVICE_URL` | empty | Activity service for event changes and refresh outcomes; empty records nothing. |
| `NOTIFICATIONS_SERVICE_URL` | empty | The Notifications service reminders are sent to (compose: `http://notifications:8080`); empty turns [reminder delivery](#reminder-delivery) off. |
| `CALENDAR_REMINDER_INTERVAL_SECONDS` | `30` | How often due reminders are looked for (5 to 300). |
| `CALENDAR_REMINDER_GRACE_MINUTES` | `120` | How late a reminder is still sent after Calendar was down (10 to 1440); older ones are recorded as missed. |
| `CALENDAR_ICS_MAX_BYTES` | `5242880` | Largest feed download. |
| `CALENDAR_ICS_TIMEOUT_SECONDS` | `30` | Time limit of one download. |
| `CALENDAR_ICS_ALLOW_PRIVATE_URLS` | `false` | Development only: allow http and private/loopback feed addresses. |
| `CALENDAR_ZAW_ICS_URL` | empty | The owner's MyMüll iCal feed for the ZAW source (compose passes `LIFE_OS_ZAW_ICS_URL`); empty configures none. See [ZAW waste collection](#zaw-waste-collection). |
| `LIFE_OS_GOOGLE_CLIENT_ID`, `LIFE_OS_GOOGLE_CLIENT_SECRET` | empty | The owner's Google OAuth Web client. Secret: never logged or returned. See [Google Calendar connection](#google-calendar-connection). |
| `LIFE_OS_GOOGLE_TOKEN_KEY` | empty | 32-byte key, base64 (`openssl rand -base64 32`), that encrypts the stored refresh token. A new key means reconnecting. |
| `LIFE_OS_GOOGLE_REDIRECT_URI` | `https://lifeos.gamch1k.com/calendar/google/callback` | The redirect URI registered on the OAuth client: the Dashboard's callback route (https; http only for localhost). |
| `CALENDAR_GOOGLE_SYNC_SECONDS` | `120` | How often each Google calendar chosen to sync is synced, 30 to 86400 (compose passes `LIFE_OS_CALENDAR_GOOGLE_SYNC_SECONDS`). |
