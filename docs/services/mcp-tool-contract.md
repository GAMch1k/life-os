# MCP tool contract

The MCP service exposes semantic, structured operations only. It calls the owning HTTP API and never SQL, shells, files, or another service's storage. Tool outputs are JSON-shaped entity/list results or the service error envelope; inputs use the corresponding OpenAPI request fields.

| Tool | Service API | Safety |
| --- | --- | --- |
| `inbox_list`, `inbox_get` | list/get inbox items | read-only |
| `inbox_resolve`, `inbox_discard` | resolve/discard item | state-changing; record audit reason |
| `task_create`, `task_list`, `task_search`, `task_update`, `task_complete`, `task_reopen` | Tasks endpoints | creates/changes work through the same Task operations as the Dashboard; completion and reopening are explicit; an existing Task is changed only when `task_search`, run with each of the plan's search terms (`taskQuery` and its cross-language `taskQueryAlternatives`), finds exactly one Task in total (see [editable entities](../architecture/editable-entities.md) and [MCP and AI](mcp.md)); there is no Task delete tool: `DELETE /v1/tasks/{taskId}` stays a deliberate Dashboard action |
| `calendar_list`, `calendar_search`, `calendar_get` | `GET /v1/events`, `GET /v1/events/search`, `GET /v1/events/{id}` | read-only |
| `calendar_create`, `calendar_update`, `calendar_cancel` | `POST /v1/events`, `PATCH /v1/events/{id}` (changed fields, `clear` → `null`, `priority` only when the item says how important the event is; cancel is `status: cancelled`) | the same Calendar operations as the Dashboard; an existing event is changed only when `calendar_search`, run with each of the plan's search terms (`eventQuery` and its cross-language `eventQueryAlternatives`), finds exactly one active event from the capture's day on (searched with `editable=true`: Life OS events and Google events of calendars the owner may edit, which Calendar writes to Google; a recurring event is changed only in the Calendar); every AI-proposed cancellation goes to Human Review and runs only after the owner approves it (see [Calendar events](mcp.md#calendar-events)) |
| `calendar_delete` | `DELETE /v1/events/{id}` | destructive and permanent; only on the owner's explicit request; the processor never proposes it |
| `finance_month_summary`, `finance_find_transactions` | Finance reads | read-only |
| `finance_create_manual_transaction` | Finance transaction create | cash spending or income with an explicit amount; without an account it goes to the built-in Cash account, without a date it is today |
| `food_list_shopping_items`, `food_list_pantry_items` | `GET /v1/shopping-items` (`state`, `storeId` or `storeName`, `aisle`), `GET /v1/pantry-items` (`state`, `location`, `expiringWithinDays`) | read-only |
| `food_add_shopping_items` | `POST /v1/shopping-items` (1 to 50 items: `name`, `amount`, `note`, `storeName`, `aisle`; sent as `source: capture` with `sourceRef`) | groceries only (food, drinks, household, drugstore); other purchases are `task_create`; a name already needed merges into that item (`merged: true` per item), an unknown store is created |
| `food_mark_bought` | `POST /v1/shopping-items/{id}/bought` per id | marks existing items bought; the processor marks one only when its search terms match exactly one needed item |
| `food_add_pantry_items` | `POST /v1/pantry-items` (1 to 50 items: `name`, `amount`, `location`, `expiresOn`, `openedOn`, `note`; `source: capture`) | pantry items never merge |
| `food_update_pantry_item` | `POST /v1/pantry-items/{id}/used-up`, `/thrown-away`, `/restock`, or `PATCH /v1/pantry-items/{id}` | ends an item (kept as history) or edits it; the processor only ends one, when its search terms match exactly one in-stock item |
| `food_list_recipes`, `food_list_meal_plan` | `GET /v1/recipes` (`q`, `tag`, `ingredient`), `GET /v1/meal-plan` (`from`, `to`, at most 31 days) | read-only |
| `food_plan_meal` | `PUT /v1/meal-plan/{date}/{slot}` (`recipeId` or `text`, `servings`, `note`) | replaces what the slot held; the processor names a recipe only when its words resolve to exactly one, else plans them as text, and asks about several |
| `food_clear_meal` | `DELETE /v1/meal-plan/{date}/{slot}` | an empty slot is `cleared: false`, not an error |
| `food_add_missing_ingredients` | `POST /v1/shopping-items/from-recipes` (`recipeIds` or `from`/`to`, `dryRun`) | adds only what is neither in the pantry nor already on the list; per-ingredient status. Recipes are never created or edited by the AI |

Example routing: “Remind me to call the insurer tomorrow” becomes `task_create` with title and due time. “Add a dentist appointment next Tuesday” becomes `calendar_create`. “Move the dentist appointment to Monday at 9” becomes `calendar_update` of the one matching event; “Cancel the dentist appointment” becomes a Human Review asking the owner to approve `calendar_cancel` of it. “Spent 12 euros at the bakery” becomes `finance_create_manual_transaction` in the Cash account with structured Money (`-1200 EUR`); “Paid 45 euros by card at REWE” is left to the bank connection and goes to Human Review. “Buy milk and 6 eggs” becomes `food_add_shopping_items` with “milk” and “eggs” (amount “6”), and “buy milk tomorrow” too (a date does not make groceries a Task); “Buy a flash drive tomorrow” stays `task_create`, and “buy milk and call mom” is split into both. “I bought the milk” becomes `food_mark_bought` of the one needed list item that matches, also “Молоко” (else the one matching open Task is completed; else nothing happens). “Йогурт в холодильнике до пятницы” becomes `food_add_pantry_items` with `expiresOn` the coming Friday, and “молоко закончилось” `food_update_pantry_item` with `state: used_up` of the one matching in-stock item. “Lasagne for dinner on Thursday” becomes `food_plan_meal` of the recipe “Lasagne” (or the text “Lasagne” when no recipe matches) in Thursday's dinner slot, “cancel dinner on Friday” `food_clear_meal`, and “купи всё для борща” `food_add_missing_ingredients` of the borscht recipe; “buy what I need for this week's meals” takes Monday to Sunday of the capture's week. See [MCP and AI](mcp.md#food) and [Meals and recipes](mcp.md#meals-and-recipes).

The processor records a processing attempt before actions and resolves an Inbox item only after a successful downstream API action. Ambiguous requests go to Human Review; retries use the audit/idempotency mechanism rather than duplicate actions. `inbox_record_processing_attempt` accepts `nextRetryAt` (RFC3339) and `retryReason` with a `retryable` status, and Inbox persists them as the item's retry schedule. `inbox_record_attempt_runtime` records an attempt's runtime state, owner, and Codex session, and refreshes its heartbeat. `inbox_list_stale_attempts` lists attempts abandoned by a stopped processor.
