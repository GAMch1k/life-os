# Tasks service

Tasks owns actionable work in `tasks_db`: title, optional notes/due date, completion timestamps, and optional daily/weekly/monthly recurrence. It accepts dashboard/API input and returns Task JSON; it does not interpret Inbox items or access any other database. Gateway base: `/api/tasks`.

Create/list tasks, patch editable fields, then use the explicit completion and reopen actions. These operations are the single Task lifecycle. The Tasks workspace and MCP's `task_update`, `task_complete`, and `task_reopen` tools both call them; this is the reference implementation of the [editable-entity rule](../architecture/editable-entities.md). An open Task may have no `dueAt`: it remains a valid, findable Task and no artificial date is assigned. To intentionally return a scheduled Task to Unscheduled, send `clearDueAt: true` to `PATCH /v1/tasks/{taskId}`; it cannot be combined with `dueAt`. A `dueBefore` listing includes undated Tasks by default so attention views do not hide them; clients that need a strict scheduled-date-only result send `includeUndated=false`. Input limits and date/recurrence validation produce 400; unknown UUIDs produce 404. A create request with `Idempotency-Key` persists its payload identity: repeating the same request returns the original Task, while the same key with a different payload returns 409. `/health` and `/ready` support operations. MCP calls these APIs, never tables.

Every successful create, update, complete, and reopen records a `task.*` activity event carrying the caller's correlation, causation, and actor (user, or the agent behind MCP). An idempotent create replay records nothing new. See [Activity](activity.md).

`GET /v1/tasks?query=…` performs a case-insensitive title-or-notes search. MCP uses that API query only to resolve an existing Task for a mutation; it performs the mutation only when exactly one Task matches.
