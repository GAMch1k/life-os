# Tasks service

Tasks owns actionable work in `tasks_db`: title, optional notes/due date, completion timestamps, and optional daily/weekly/monthly recurrence. It accepts dashboard/API input and returns Task JSON; it does not interpret Inbox items or access any other database. It reminds the owner of due and overdue Tasks and sends the daily morning summary (see [Notifications](#notifications)). Gateway base: `/api/tasks`.

Create/list tasks, patch editable fields, use the explicit completion and reopen actions, and delete a Task. These operations are the single Task lifecycle. The Tasks workspace and MCP's `task_update`, `task_complete`, and `task_reopen` tools both call them (delete is the workspace's alone, see [Deleting a Task](#deleting-a-task)); this is the reference implementation of the [editable-entity rule](../architecture/editable-entities.md). An open Task may have no `dueAt`: it remains a valid, findable Task and no artificial date is assigned. To intentionally return a scheduled Task to Unscheduled, send `clearDueAt: true` to `PATCH /v1/tasks/{taskId}`; it cannot be combined with `dueAt`. A `dueBefore` listing includes undated Tasks by default so attention views do not hide them; clients that need a strict scheduled-date-only result send `includeUndated=false`. Input limits and date/recurrence validation produce 400; unknown UUIDs produce 404. A create request with `Idempotency-Key` persists its payload identity: repeating the same request returns the original Task, while the same key with a different payload returns 409. `/health` and `/ready` support operations. MCP calls these APIs, never tables.

Every successful create, update, complete, reopen, and delete records a `task.*` activity event carrying the caller's correlation, causation, and actor (user, or the agent behind MCP), with the Task's title in `data`. An idempotent create replay records nothing new. See [Activity](activity.md).

`GET /v1/tasks` lists open Tasks first, soonest due first with undated ones after the dated ones (newest first), then completed Tasks, most recently completed first. It returns at most `limit` (1–100, default 50) Tasks; when more match, the response carries `nextCursor`, which the client passes back as `cursor` with the same filters for the next page. The cursor is the last row's position in that order (completion time, due date, creation time, id), so Tasks added or changed between requests do not shift the unchanged ones into a skipped or repeated position; a malformed cursor is a 400. Filters combine: `completed`, `dueBefore` with `includeUndated`, `undated=true` (only Tasks without a due date) or `undated=false` (only Tasks with one), and `query`.

`GET /v1/tasks?query=…` performs a case-insensitive title-or-notes search. MCP uses that API query only to resolve an existing Task for a mutation; it performs the mutation only when exactly one Task matches.

## Deleting a Task

`DELETE /v1/tasks/{taskId}` removes a Task, open or completed, and answers 204 with no body. A recurring Task is one Task, so deleting it deletes the series; there is no per-occurrence delete. An unknown or already deleted Task is a 404 (`not_found`), and like every write it needs `X-Life-OS-Actor` (400 `actor_required` otherwise). It records `task.deleted` (summary "Task “Pay rent” deleted", `data` with the title, `completed`, and `dueAt`), once per Task: its id is `EventID("task.deleted", taskId)`. Completing a Task keeps it as history; deleting is for mistakes and test leftovers, and cannot be undone.

The delete is hard: the row is removed, as Calendar removes a deleted event. Nothing references a Task (no foreign keys), the notification log names one only inside a dedupe key and prunes itself after 30 days, and every list, search, `dueBefore` view, reminder, daily list, and summary reads the `tasks` table when it runs, so a deleted Task is in none of them from then on without a `deleted_at` filter to keep in every query. Activity keeps the record of what was deleted. The create `Idempotency-Key` lives on the row and goes with it, so a create replayed with that key after the delete creates the Task again, as for a deleted Calendar event.

Deleting is a deliberate Dashboard action: the Tasks workspace offers it behind a confirmation ("Delete “Pay rent”? This can't be undone."), and MCP has no tool for it (see [Dashboard](../frontend/dashboard.md) and the [MCP tool contract](mcp-tool-contract.md)). Development tools may delete through the API with their `dev:<name>` actor.

`internal/api` holds integration tests against `TASKS_TEST_DATABASE_URL` (as for the notifications below): a deleted dated, recurring, or completed Task is gone from get, every list filter, search, and `dueBefore`; a repeat, an unknown id, or a change of a deleted Task is a 404 and records nothing; a delete without an actor deletes nothing; each delete records one `task.deleted` with its actor, correlation, and title; and a create replayed after the delete creates the Task again.

## Notifications

Tasks tells the owner about their Tasks through [Notifications](notifications.md) (`pkg/notify`, the one notification path). There are no quiet hours. Every time below is on the owner's wall clock (`LIFE_OS_TIMEZONE`), resolved each day, so 09:00 stays 09:00 across daylight saving changes (a wall time skipped when the clocks go forward is the same time after the jump; one that occurs twice is the first, as for Calendar's reminders).

**Timed or date-only.** A Task is date-only when its `dueAt` stands for a whole day, by the rule the Dashboard shows due dates with: it is the owner-local midnight (how the Dashboard and the AI store a date without a time), or a UTC midnight that falls on the same calendar day for the owner (how a bare date is often sent; west of UTC that instant is the previous evening, a time). Every other `dueAt` is timed. A date-only Task is due on its owner-local date; it is overdue from the next day on. A timed Task is overdue once its time has passed.

| Message | When | Content | Importance, category | Dedupe key |
| --- | --- | --- | --- | --- |
| Timed reminder | `TASKS_TIMED_LEAD_MINUTES` (30) before each open timed Task is due, one per Task and due time. | Title: the Task's title. Body: "Due in 30 minutes · 15:00" (a due time on another day names it: "Due in 30 minutes · Sun 11 Oct 00:10"). | `medium`, `tasks.due` | `tasks:due:<taskId>:<dueAt in UTC, RFC 3339>` |

Titled "Tasks for today", or "Overdue tasks" when nothing date-only is due today. | `medium`, `tasks.morning` | `tasks:morning:<local date>` |
| Evening list | Daily at `TASKS_EVENING_TIME` (19:00), when it names anything. | One message, "Tasks for tomorrow": the date-only Tasks due tomorrow, one title per line. | `medium`, `tasks.evening` | `tasks:evening:<local date it is sent>` |
| Morning summary | Daily at `TASKS_SUMMARY_TIME` (08:00), unless there is no event and no Task at all. | "Your day", one line per list: "Events: Birthday (all day) · 09:00 Dentist · 20:00 Свидание с Ирой", "Tasks: Renew passport · 15:00 Call mom" (today's date-only Tasks, then the timed ones still ahead, with their time), "Overdue: Pay rent (since Tue 6 Oct)". - **Overdue repeats.** An open overdue Task is in the morning list (and the summary) every morning until it is completed. A Task due today at a time has its own reminder and is not in the morning list; it is in the summary.
- **Summary and morning list at the same time.** When `TASKS_SUMMARY_TIME` equals `TASKS_MORNING_TIME`, only the summary is sent; it already names today's and overdue Tasks. It is then `medium` when it names a date-only Task due today or an overdue Task (what the morning list would have said), else `low`.
- **Lists.** Each list names at most 10 Tasks or events, then "and 10 more". Titles are shown as written, on one line, shortened to 120 characters in lists. Links: `/tasks` for the Task messages, `/` (Home, with today's Tasks and events) for the summary.
- **Events.** The summary reads the day's events from Calendar over HTTP (`GET /v1/events` for the owner-local day, with `timeZone`, through `CALENDAR_SERVICE_URL`): recurring events already expanded, an occurrence with its own title and time, cancelled ones left out. All-day events, and timed ones lasting the whole day, read "(all day)"; one that started the day before reads "Party (until 01:00)". When Calendar does not answer (one retry, 10 s), the summary is sent without events and says "Events: Calendar unavailable"; a summary with nothing else is not sent. Without `CALENDAR_SERVICE_URL` there is no events line.
- **Changes.** The lists are read when a message is sent, so completing or deleting a Task removes it from every later message (a deleted timed Task is not reminded), and reopening it makes it eligible again. A timed reminder's key holds the due time: a changed due time reminds again at the new time (a reminder already sent for the old time stays sent); a title change does not. A reminder whose time has already passed when the Task is created, reopened, or moved is not sent, as for Calendar's reminders.

**Delivery.** A goroutine in the Tasks process (`internal/notifications`) runs every `TASKS_NOTIFY_INTERVAL_SECONDS` (30) and handles what came due in `(last run, now]`: the reminders of open timed Tasks due within the window plus the lead, and the day's summary, morning, and evening messages. It follows Calendar's [reminder delivery](calendar.md#reminder-delivery):

- **Exactly once.** Notifications stores a dedupe key once. Tasks also keeps its cursor (`task_notification_dispatch.last_run_at`) and every handled key (`task_notification_log`: sent, missed, failed, or empty; pruned after 30 days), so restarts and overlapping runs neither repeat nor skip a message. One process runs at a time: a run holds a lease on the state row (two minutes, at least four intervals).
- **Failures.** When Notifications is unreachable or answers 5xx, the run stops at that message and keeps the cursor just before it, so the next run retries it. A message Notifications refuses (4xx) is recorded as failed, logged, and not retried. Either error is kept as `lastError`.
- **Missed while down.** The first run after Tasks was down handles everything due since the last run, at most 7 days back. A message up to `TASKS_NOTIFY_GRACE_MINUTES` (120) late is sent, its lists read when sent; a late timed reminder is phrased from the time it is sent and ends with "(late)" ("Due in 15 minutes · 10:45 (late)", "Was due 20 minutes ago · 15:00 (late)"). An older one is not notified but recorded in Activity as `tasks.notification.missed`. A daily message that would have named nothing is recorded as empty, never as missed. The very first run after deployment only starts the cursor.
- **Off without Notifications.** With `NOTIFICATIONS_SERVICE_URL` unset the dispatcher does not run (logged at startup).

`tasks.notification.missed` has actor `system:tasks`, outcome `failed`, `occurredAt` the time the message was due, and an id derived from the dedupe key (recorded once). A timed reminder's subject is the `task`, with `data.title` and `data.taskDueAt`, and a summary such as "Reminder for task “Take pills” due Sat 10 Oct 2026, 07:45 CEST was missed: Tasks was not running"; a daily message's subject is `task_notification` with the dedupe key as id and `data.day`, for example "Morning summary due Sat 10 Oct 2026, 08:00 CEST was missed: Tasks was not running". `data` also holds `kind` (`due`, `morning`, `evening`, `summary`), `dueAt`, and `dedupeKey`.

`GET /v1/notifications/status` reports the delivery's health: `enabled`, `calendarConfigured`, `intervalSeconds`, `graceMinutes`, the schedule (`timeZone`, `summaryTime`, `morningTime`, `eveningTime`, `timedLeadMinutes`, `mergedMorning`), `handledThrough` (the cursor), `lastRunAt`, `lastSuccessAt`, `lastError` with `lastErrorAt` (current while later than `lastSuccessAt`), and `lastSentAt`. The Dashboard Status page shows it as the Task reminders part of the Notifications check (see [Dashboard](../frontend/dashboard.md)).

`internal/notifications` holds unit tests (timed versus date-only, also for a UTC-midnight date east and west of UTC; wall times and day boundaries across both daylight saving changes; the window; the lists for a day; messages, caps, late phrasing, the merged summary's importance, empty lists skipped; the Calendar client's query, paging, retries, and timeout) and integration tests against `TASKS_TEST_DATABASE_URL` (a throwaway Postgres; each test creates and drops its own schema and applies every migration) with an in-process Notifications that deduplicates like the real one and a Calendar stand-in: the first run only starts the cursor, a timed reminder sent once (also with another process and a cursor set back), the morning list with today's and overdue Tasks and the evening list, overdue Tasks every morning but once a day, completing, reopening, moving, and deleting Tasks, late and missed messages after downtime, the summary with events, one merged message with Calendar down, failing and refusing Notifications, the lease and two processes at once, and migration 000004 down and up.
